Part 4 . Evaluation context and DAX

09Row context and filter context

After this chapter you will be able to look at any DAX expression in the Meridian model and say which context it is running in. You will be able to say what the engine did to produce that context, and why two expressions that look almost identical return 62.0 and 52.0.

The production controller wants a technician scorecard for the quarter. One row per technician, hours booked, sorted. You build it, and the total under the column reads 52.0. On the same page, a card showing total labor hours reads 62.0. Both numbers come out of the same eight labor rows, and you wrote both of them yourself.

Most DAX that returns a wrong number is not doing wrong arithmetic. It is doing correct arithmetic over the wrong set of rows. Everything in this chapter exists to let you predict, before you press enter, exactly which rows the engine will hand your aggregation. By the end of it you will know where those ten hours went, and you will be able to say whether 52.0 or 62.0 is the number the production controller actually asked for.

There are two independent mechanisms at work, and the whole of DAX rests on telling them apart. Once you can, a result that looked arbitrary becomes one you can derive on paper before the engine ever runs it.

Two different questions

Filter context
The set of rows currently visible on every table in the model. It is created by slicers, by report and page filters, by the rows and columns of a visual, and by CALCULATE. A slicer is the on-page control a user clicks to choose values. The filter context is what a measure sees, and a measure is a calculation the engine runs once for every cell of a visual. A filter context always exists, even if it is empty, and an empty filter context means every row of every table is visible.
Row context
A pointer to one specific row of one specific table. It is created by a calculated column and by any iterator function. An iterator is a function that walks a table one row at a time. A row context leaves every row of the table visible. Its only job is to say which row the words FactLabor[Hours] refer to right now.

Here is the sentence to write on the whiteboard. A row context knows which row you are on. A filter context knows which rows exist. Those are different questions. DAX keeps them separate on purpose, because collapsing them would make it impossible to write an expression that compares one row against the whole table.

A row context leaves an aggregation free to see everything. This is the part that gets missed on a first read, so say it out loud: being positioned on row L-505 still lets SUM ( FactLabor[Hours] ) return 62.0. Position and visibility stay unrelated until you deliberately connect them, and connecting them is what the second half of this chapter is about.

Filter context, seen on the Meridian report

The finance manager wants one number for the month. Hours booked at MSP in January, and he does not care how you get it. You give him a matrix so he can see the other months too.

Put Dimension DimStation[StationCode] on the rows of that matrix, put DimDate[MonthName] on the columns, and drop a Labor Hours measure into the values. The MSP and January cell returns 22.5. Trace where that came from. The visual applies two filters, one from each axis. DimStation is cut to the single row MSP. DimDate is cut to the 31 rows of January. Those filters then travel along the relationships in the direction the arrows allow: DimStation to Fact FactWorkOrder, which leaves WO-1001, WO-1002, WO-1006 and WO-1008; then FactWorkOrder to FactLabor along the header to line relationship; and separately DimDate straight into FactLabor[WorkDate].

What survives both filters is three labor rows: L-501 at 7.5 hours, L-502 at 6.0 and L-503 at 9.0. That is 7.5 plus 6.0 plus 9.0, which is 22.5. The finance manager has his number. The measure asked what was left, summed it, and returned. Filter context did all of that work on its own.

Rule of thumb

Every number in a visual is one measure evaluated once per cell, in a filter context assembled fresh for that cell. If you cannot list the filters in a cell, you cannot debug the number in it. Write them down before you write DAX.

Row context, seen on the same rows

Now add a calculated column to FactLabor. A calculated column is worked out once per row when the model refreshes, and the answer is stored in the model like any other column.

DAXLineCost, calculated column on FactLabor
// Evaluated once per row at refresh time.
LineCost =
    FactLabor[Hours] * FactLabor[HourlyRate]
Line 3
Two bare column references with no aggregation around them. In a measure this would fail. Here it works, because a calculated column is given a row context automatically, once for every row of the table it sits on.
Result
On L-501 the row context points at 7.5 and 95, so the column stores 712.50. On L-507 it points at 12.0 and 120, so it stores 1,440.00. Eight rows, eight independent evaluations, and the column total is 6,326.50, the same figure the Labor Cost measure returns.
Name
LineCost and not Labor Cost. The model already carries a measure called Labor Cost, and a column may not share a name with a measure in the same table. Chapter 4 and Chapter 10 weigh up whether to store this column at all. The point here is only that the expression compiles as a column and would not compile as a measure.

Look at what the calculated column actually did. It resolved two column names against a row pointer and multiplied. There was no slicer to consult, because slicers do not exist at refresh time. The rest of the model still saw all eight rows of FactLabor throughout. That is the entire behaviour of a row context.

A measure begins with no row context at all

This is the cleanest proof that the two mechanisms are separate.

DAXOne works, one cannot
// Works. SUM walks the visible rows itself.
Labor Hours = SUM ( FactLabor[Hours] )

// Fails. No row context exists, so DAX cannot decide
// which of the eight values of Hours you meant.
Broken Hours = FactLabor[Hours]
Line 2
SUM is an aggregator that opens its own internal row context over the column you hand it, walks every visible row, and folds the values together. That internal context lives and dies inside the function.
Line 6
A measure is evaluated once per cell, not once per row. With eight visible rows of FactLabor and no pointer to any of them, the engine refuses. It reports that a single value for column Hours in table FactLabor cannot be determined. That error message is the engine telling you, in its own words, that there is no row context.
Why this and not that

SUM here, because the expression to be summed is a plain column with nothing computed per row. SUMX would give the same 62.0, but it would open a row context you do not need and evaluate an expression eight times instead of scanning one column. On a real fact table that costs. Reach for SUMX only when the thing you are summing has to be worked out row by row, such as Hours multiplied by HourlyRate.

Where row context comes from

Two sources, and only two. Calculated columns get one for free. Iterators create one over whatever table you pass as their first argument, and they create it fresh for every row of that table. These are the iterators you will actually meet in this model.

SUMX
Sums an expression evaluated per row. Chosen over SUM whenever the per row expression involves more than one column, because SUM accepts a single column reference and nothing else.
AVERAGEX
Same shape, averaging instead. Chosen over AVERAGE for the same reason, and also because AVERAGE would average the eight Hours values instead of the eight computed costs.
FILTER
Returns a table, keeping the rows where a condition evaluated in row context is true. Chosen over a plain boolean predicate inside CALCULATE when the condition compares two columns of the same table, or calls a measure, neither of which a simple predicate can express.
ADDCOLUMNS
Returns the source table plus new evaluated columns. Chosen over SELECTCOLUMNS when you want to keep everything you already had and add to it, because SELECTCOLUMNS discards any column you do not list.
RANKX
Ranks each row of a table by an expression. Chosen over the newer RANK window function when you are writing a calculated column or a measure outside a query with a defined window, since RANK expects an ordering and partition supplied by the surrounding query shape.
MAXX
Largest value of an expression across rows. Chosen over MAX when the value has to be computed for each row, because MAX takes a column or two scalars and cannot take an expression over a table.
GENERATE
For each row of the first table, evaluates the second table in that row context and joins the results. Chosen over CROSSJOIN when the second table must depend on the current row, which CROSSJOIN cannot do because it evaluates both sides once.

Look at the two panels first. Both draw the same five labor rows, L-501 through L-505, so whatever differs between them is the mechanism and not the data. On the left, under the heading Row context, one row is outlined and carries a small arrow beside it. The other four are drawn exactly as they always were: still there, still visible, still countable. That is row context, a cursor. On the right, under the heading Filter context, three of the five rows are greyed out and two stay lit. The two that stay lit are the ones booked to TECH-04, which is the selection that panel's note names. Nothing is marked as current, because nothing needs to be. That is filter context, a knife. The card running the full width underneath is context transition, and its arrow runs from the words row context to the words filter context with CALCULATE sitting on it. That is the only thing in DAX that turns the first picture into the second. The last line of that card states a result this chapter reaches later, that SUMX ( DimTechnician, [Labor Hours] ) returns 52.0 and not 62.0. Hold the question until Hours C, which is where the production controller's scorecard gets settled.

Context transition, which is the hard part

When CALCULATE is invoked while a row context is open, it does something before it does anything else. It takes the current row context on the table being iterated. It converts that into a filter context which cuts the table down to that row, using every column of the table. Then, with the new filter in place, it evaluates its expression.

That conversion is called context transition. It cannot be switched off, and it happens even when CALCULATE has no filter arguments at all. CALCULATE ( [Labor Hours] ) written inside an iterator is doing real work despite looking like it does nothing.

Two consequences trip up almost everybody.

  1. A measure referenced inside an iterator gets an implicit CALCULATE wrapped around it by the engine. Writing [Labor Hours] is exactly the same as writing CALCULATE ( [Labor Hours] ). So the measure undergoes context transition automatically, every time, whether or not you wanted it. This is why SUMX ( FactLabor, [Labor Hours] ) does not do what a beginner expects.
  2. Context transition on a table with no unique key filters to every row that matches on every column. A unique key is a column whose values never repeat. Without one, two identical rows are indistinguishable to the transition and both stay visible. Your iteration then silently includes more rows than you intended, and the total comes out too high with no error and no warning.
Interview-level insight

Context transition also overwrites, rather than intersects with, any existing filter on the columns of the transitioned table. This matters when a measure containing an iterator sits inside a visual that already filters that same table. The iterator still only walks rows visible in the outer filter context, so the slicer still controls the loop. Inside each iteration, though, the row filter replaces the outer one on those columns. Saying which of those two rules applies to a given expression is the fastest way to demonstrate you actually understand CALCULATE.

Three expressions on the Meridian rows

Define the measure once and leave it alone for the rest of the chapter.

DAXLabor Hours
Labor Hours = SUM ( FactLabor[Hours] )
Line 1
One aggregation over one column, with no filter modifier and no iterator. SUM because there is nothing to compute per row, so SUMX would open a row context for no gain. Plain SUM with no CALCULATE wrapper, because nothing here changes a filter. Whatever filter context the measure is called in, it sums the Hours values that survive it.
Baseline
With no slicers and no visual axes, the filter context is empty, all eight rows are visible, and the measure returns 62.0. Every result later in this chapter is a variation on that one number.

These are the eight rows it will be working over. FactLabor is LaborEntries with TechnicianID trimmed, which is what repaired L-505 back onto TECH-04.

The shaded row is L-506, whose technician TECH-07 does not exist in the HR extract. Hold on to that row. It is what makes the third expression interesting, and it is where the production controller's ten hours are hiding.

DAXThree expressions, two results
// 1. Row context only. No transition anywhere.
Hours A = SUMX ( FactLabor, FactLabor[Hours] )

// 2. Measure inside an iterator. Implicit CALCULATE,
// so context transition on every one of the 8 rows.
Hours B = SUMX ( FactLabor, [Labor Hours] )

// 3. Same measure, different table iterated.
Hours C = SUMX ( DimTechnician, [Labor Hours] )
Line 2
First argument is a table, second is an expression evaluated in the row context that table opens. SUMX rather than SUM because SUM accepts only a column reference and cannot be handed an expression to work out per row.
Line 6
The only change from line 2 is the second argument. Here it is a measure reference in [Name] form, where line 2 had a column reference in Table[Column] form. That single difference is what invites the implicit CALCULATE and therefore context transition.
Line 9
Identical expression to line 6, iterating Dimension DimTechnician instead of Fact FactLabor. Nothing else moves. The result does.

Hours A, 62.0, no transition

SUMX opens a row context over FactLabor and moves through the eight rows. On each one, FactLabor[Hours] resolves against the row pointer and yields a stored number. The engine reads 7.5, 6.0, 9.0, 8.0, 4.5, 10.0, 12.0 and 5.0 straight off those eight rows, and adds them to 62.0. Every value comes from storage exactly as it sits there. The one thing that could convert a row context into a filter is CALCULATE, and this expression contains none, explicit or implicit. This is the boring case, and boring is what you want.

Hours B, also 62.0, for a completely different reason

Same eight iterations, but the second argument is a measure, so the engine rewrites it as CALCULATE ( [Labor Hours] ). On the first iteration the row context is sitting on L-501. Context transition takes that row and builds a filter on FactLabor covering every column of it: LaborID equals L-501, WorkOrderID equals WO-1001, TechnicianID equals TECH-02, WorkDate equals 7 January 2025, Hours equals 7.5, HourlyRate equals 95. Only one row in the table satisfies all six conditions, because LaborID alone is already unique. FactLabor is now filtered to a single row. Only then does SUM ( FactLabor[Hours] ) run, over a table of one row, returning 7.5.

Repeat that seven more times and you get 6.0, 9.0, 8.0, 4.5, 10.0, 12.0, 5.0, and the outer SUMX adds them to 62.0. The number is identical to Hours A and the machinery underneath is a different animal. A read of a stored value happened eight times in A. In B, eight filter contexts were constructed, eight filtered scans of the fact table were performed, and eight aggregations were run. The result agrees only because the transition happened to isolate exactly one row each time.

Performance note

Hours B is the expensive way to get 62.0. On eight rows nobody notices. On a labor table with two million rows, an iterator with a transitioning measure inside it can force the engine out of its fast column scan and into a much slower row by row evaluation, and query time can go from milliseconds to minutes. Reserve transition inside an iterator for when you genuinely need per row aggregation of related data, and never write it just because it reads nicely.

Hours C, 52.0, and this one is genuinely useful

This is the scorecard the production controller asked for, and here is where its 52.0 comes from. Change nothing but the iterated table. Take DimTechnician at the point in the build where it holds the six cleaned rows from the HR extract, TECH-01 through TECH-06. SUMX now walks six rows, not eight. On each one the implicit CALCULATE transitions that technician row into a filter on DimTechnician. Because TechnicianID is unique in that table, the transition isolates one technician. That single row filter then propagates down the one to many relationship into FactLabor, cutting it to that technician's labor rows, and SUM ( FactLabor[Hours] ) totals whatever is left.

12.0 plus 16.5 plus 0 plus 10.5 plus 13.0 plus 0 is 52.0. The ten hours on L-506 are simply never reached, because the loop is over technicians and TECH-07 is not a technician as far as this table is concerned. The engine reports this as a clean success. No error is raised and no blank row appears. The number is quietly ten hours short of the fact table total, which is why the scorecard and the card beside it disagree.

One precision point before you use Table 09.3 as gospel. For TECH-03 and TECH-06, SUM over an empty set returns BLANK, not zero. The table above shows 0 because that is the arithmetic contribution, and SUMX treats blank as zero when it adds the six values together. In a matrix visual those two technicians would show an empty cell where this table shows 0, and by default their rows would disappear from the visual entirely.

Trace this by hand, row by row

Six iterations of SUMX ( DimTechnician, [Labor Hours] ). Read the middle column as the filter that context transition installed on DimTechnician, and the right column as what survived in FactLabor after that filter propagated across the relationship.

  1. Row context lands on TECH-01. Implicit CALCULATE fires. Transition filters DimTechnician to TechnicianID = TECH-01, Name = R. Okafor, HomeStation = MSP, EmployeeType = Staff. That is one row. Propagation cuts FactLabor to L-507 only. SUM ( FactLabor[Hours] ) returns 12.0.
  2. Row context moves to TECH-02. Transition isolates M. Halvorsen. FactLabor keeps L-501 and L-503. 7.5 plus 9.0 gives 16.5.
  3. Row context moves to TECH-03. Transition isolates J. Prieto. Propagation leaves FactLabor with zero rows, because J. Prieto logged no time in the quarter. SUM over nothing returns BLANK, which contributes 0.
  4. Row context moves to TECH-04. Transition isolates D. Sandoval. FactLabor keeps L-502 and L-505. 6.0 plus 4.5 gives 10.5. Note that L-505 only arrives here because the trailing space in its TechnicianID was trimmed in Power Query. Without that trim this iteration would return 6.0 and the grand total would be 47.5.
  5. Row context moves to TECH-05. Transition isolates K. Ibrahim. FactLabor keeps L-504 and L-508. 8.0 plus 5.0 gives 13.0.
  6. Row context moves to TECH-06. Transition isolates L. Petrov. No labor rows survive, so the result is BLANK and contributes 0.

The outer SUMX adds 12.0, 16.5, 0, 10.5, 13.0 and 0, and returns 52.0. L-506 was never visited by any of the six iterations, so its 10.0 hours are absent by construction. Nothing malfunctioned. The loop simply never went near that row.

Now the inconvenient part. In the finished Meridian model, DimTechnician has seven rows, because an Unknown technician member was added for TECH-07 exactly so that orphan facts have somewhere to land. Run the same expression against that seven row version. A seventh iteration isolates TECH-07, reaches L-506, and returns 10.0. That brings the total to 62.0, matching the fact table. The 52.0 belonged to an incomplete dimension all along, and SUMX was doing its job both times. That is why the unknown member work in Part 3 earns its keep.

Common mistake

Building a technician scorecard by iterating the dimension, then reconciling it against a plant total that iterates the fact table, and concluding that DAX is unreliable when the two disagree. They disagree because they are answering different questions. Iterating a dimension answers "how much for each of these people", which by definition excludes anyone not in the list. Iterating the fact answers "how much in total". Decide which question the business is asking before you decide which table to iterate. If the answer is the first, then the completeness of your dimension has just become a reporting requirement, and you should write it into the spec as one.

When transition cannot isolate one row

The planner wants planned hours compared across trades, with the month taken out of the way. She builds a small helper table that strips the month columns off capacity, points a measure at it, and asks you why MSP airframe now shows 72 planned hours when the source workbook says 44. Nothing on her screen is flagged. Both iterated tables so far had a unique key, and hers does not.

DAXCapByTrade, calculated table
CapByTrade =
    SELECTCOLUMNS (
        FactCapacity,
        "StationCode", FactCapacity[StationCode],
        "Trade", FactCapacity[Trade],
        "PlannedHours", FactCapacity[PlannedHours]
    )
Why this and not that

SELECTCOLUMNS rather than SUMMARIZE, and the choice is the whole point. SUMMARIZE would group the rows and collapse the duplicates, which hides the problem and produces a table with a natural key again. SELECTCOLUMNS keeps every one of the 28 rows exactly as they were, minus the two month columns, which is what a rushed modeller actually ends up with.

MSP planned 14 airframe hours in January and 14 again in February. Drop the month and those two rows become MSP, Airframe, 14 and MSP, Airframe, 14, identical in all three remaining columns. March is MSP, Airframe, 16, still distinct. Now compare two ways of totalling the MSP airframe hours.

DAXThe same total, two ways
Planned Trade Hours = SUM ( CapByTrade[PlannedHours] )

// Row context only. Correct.
MSP Airframe A =
    SUMX (
        FILTER (
            CapByTrade,
            CapByTrade[StationCode] = "MSP"
                && CapByTrade[Trade] = "Airframe"
        ),
        CapByTrade[PlannedHours]
    )

// Transition on a table with no unique key. Inflated.
MSP Airframe B =
    SUMX (
        FILTER (
            CapByTrade,
            CapByTrade[StationCode] = "MSP"
                && CapByTrade[Trade] = "Airframe"
        ),
        [Planned Trade Hours]
    )
MSP Airframe A
Three rows survive the FILTER. The iterator reads 14, 14 and 16 straight off each row and returns 44. That agrees with the source workbook, where MSP planned 14 airframe hours in January, 14 in February and 16 in March.
MSP Airframe B
Same three rows, but the measure triggers transition. On the January row the filter becomes StationCode = MSP, Trade = Airframe, PlannedHours = 14. Two rows match that, so the measure returns 28. On the February row the filter is character for character the same, so it returns 28 again. The March row is unique and returns 16. 28 plus 28 plus 16 is 72, which is 28 hours of capacity that Meridian does not have.

The planner had the B version. No error, and no warning triangle. Any utilisation percentage sitting on top of that number now divides by 72 where it should divide by 44. Every airframe utilisation figure at MSP therefore reads about 61 percent of its true value, and the shop manager is told there is slack that does not exist. The defence is a unique key on any table you intend to iterate with a transitioning expression. In practice that means keeping MonthKey on FactCapacity instead of throwing it away for tidiness.

Nested row contexts, and why EARLIER exists

The shift supervisor wants to know, for each work order, which labor line was the biggest. He is chasing a pattern in who gets handed the long jobs. That is a ranking inside each work order, and writing it is where row contexts start sitting on top of one another.

Row contexts nest. If you write a calculated column on FactLabor, you already have one row context over FactLabor. If that column then calls FILTER ( FactLabor, ... ), the FILTER opens a second row context over the same table. Inside the FILTER, a bare reference to FactLabor[Hours] resolves to the inner context, the row FILTER is currently testing. The outer row is shadowed. The value you actually want, the one belonging to the row the column is being computed for, can no longer be reached by name.

EARLIER exists to reach past the shadow. It means "the value this column had in the row context one level out". The name misleads on first reading, because it sounds temporal and it is not. Here is a ranking column on FactLabor that ranks each labor entry by hours within its own work order.

DAXHours Rank in WO, the EARLIER form
Hours Rank in WO =
    COUNTROWS (
        FILTER (
            FactLabor,
            FactLabor[WorkOrderID]
                = EARLIER ( FactLabor[WorkOrderID] )
                && FactLabor[Hours]
                >= EARLIER ( FactLabor[Hours] )
        )
    )
Lines 5 and 6
The bare FactLabor[WorkOrderID] on the left of the comparison is the row FILTER is testing. The EARLIER ( FactLabor[WorkOrderID] ) on the right is the row the calculated column is being written for. Same column name, two different rows, and nothing in the syntax tells you which is which except the wrapper.
Line 8
Greater than or equal, not greater than, so that the largest entry counts itself and ranks 1. Plain greater than would rank it 0.
Line 2
COUNTROWS turns the surviving table into the rank. Written this way the whole expression is correct and almost unreadable, which is the case against EARLIER.

The same logic, with the outer values captured by name instead.

DAXHours Rank in WO, the VAR form
Hours Rank in WO =
    VAR CurrentWO = FactLabor[WorkOrderID]
    VAR CurrentHours = FactLabor[Hours]
    RETURN
        COUNTROWS (
            FILTER (
                FactLabor,
                FactLabor[WorkOrderID] = CurrentWO
                    && FactLabor[Hours] >= CurrentHours
            )
        )
VAR lines
The two variables are evaluated in the outer row context, before FILTER opens anything, and their values are then fixed. A variable in DAX is a constant once assigned, so no later context can change what CurrentWO means.
FILTER line
Inside FILTER, FactLabor[WorkOrderID] refers to the row being tested, and CurrentWO refers to the row being computed. The comparison reads left to right as English, which the EARLIER version never manages.
COUNTROWS
Counting how many rows in the same work order have hours greater than or equal to this row's hours gives that row's rank, with 1 for the largest.

Both forms return the same values. L-501 ranks 1 and L-502 ranks 2 within WO-1001, since 7.5 beats 6.0. L-504 ranks 1 and L-505 ranks 2 within WO-1003, since 8.0 beats 4.5. L-503, L-506, L-507 and L-508 each rank 1, being the only labor line on their work order. That column answers the supervisor's question: filter it to rank 1 and he has the biggest line on every work order, with the name attached. Use the second form in all new code. EARLIER still works and is still supported, but it forces the reader to count nesting levels in their head. It takes an optional second argument for skipping more than one level that almost nobody remembers. And it breaks the moment somebody wraps your expression in another iterator.

Why this and not that

COUNTROWS rather than COUNT. COUNT counts non blank values in one column, so it would silently undercount any row where the counted column happened to be blank. COUNTROWS counts rows regardless of content, which is what a rank needs. And FILTER in place of a boolean predicate inside CALCULATE, because the condition compares a column against a value captured from a different row of the same table, which a simple predicate cannot express.

The calculated column trap that follows from all this

The production controller wants the work order list to carry two extra columns: how many labor lines each order has, and how many hours they add up to. It sounds like a five minute job. The first attempt fails to compile, and the reason is the rule this chapter opened with.

Row context points at a row and leaves every other row visible. Say it once more, because this is where it produces its most confusing symptom. In a calculated column, a reference to a column of a related table on the many side resolves to all the rows that match. That is a table, and DAX will not put a table into a scalar column.

Which function you need depends entirely on which side of the relationship you are reaching towards.

The wrong way

A column on FactWorkOrder to see how much labor each order absorbed.

DAXDoes not work
Labor Lines =
    RELATED ( FactLabor[LaborID] )
Line 2
RELATED promises a single scalar. It can only deliver one when the target sits on the one side.

FactLabor is on the many side of the header to line relationship. WO-1001 has two labor rows, so there is no single LaborID to return and the expression is rejected outright.

The fix

Ask for the table, then aggregate it.

DAXLabor Lines, column on FactWorkOrder
Labor Lines =
    COALESCE (
        COUNTROWS (
            RELATEDTABLE ( FactLabor )
        ),
        0
    )
Line 4
RELATEDTABLE returns the labor rows belonging to the current work order, as a table.
Lines 3 and 2
COUNTROWS reduces that table to a number, and COALESCE turns the blank into 0 for WO-1005 and WO-1008.
Why this and not that

RELATEDTABLE rather than FILTER ( FactLabor, FactLabor[WorkOrderID] = FactWorkOrder[WorkOrderID] ), because RELATEDTABLE uses the relationship the model already holds. The FILTER version rebuilds that join by hand, which is longer to read and much slower on a large fact table. Under the hood RELATEDTABLE is CALCULATETABLE of the target table, so it performs context transition and then lets the filter propagate along the relationship. That is the same mechanism as Hours C, applied to a table result instead of a scalar. And COALESCE in place of IF ( ISBLANK ( ... ), 0, ... ), because COUNTROWS of an empty table returns BLANK and not zero. COALESCE handles that in one evaluation, where the IF form makes you write the count expression twice.

That table is the production controller's two columns, finished. The Labor Hours column is the same idea with a different aggregator, written as SUMX ( RELATEDTABLE ( FactLabor ), FactLabor[Hours] ). SUMX here, and not a bare SUM ( FactLabor[Hours] ), and the reason is the whole subject of this chapter. SUM reads the filter context. A calculated column on FactWorkOrder supplies a row context, and row context does not travel across a relationship. So a bare SUM would see all eight labor rows on every single work order and write 62.0 into all eight cells. SUMX over RELATEDTABLE states the row set explicitly instead of hoping one arrives. CALCULATE ( SUM ( FactLabor[Hours] ) ) would also work, by forcing the transition, and it is the shorter form. It also hides the mechanism behind a function that looks like it is doing nothing. The two shaded rows are WO-1005 and WO-1008, which have no labor at all. Without COALESCE those cells would be blank, and a blank in a numeric column has a way of turning into an unexpected gap in a chart later.

Reaching the other direction is easier, and it works across more than one hop.

DAXAircraft Type, column on FactLabor
// Two hops: FactLabor to FactWorkOrder to DimAircraft.
// Both hops go many to one, so RELATED can follow them.
Aircraft Type =
    RELATED ( DimAircraft[AircraftType] )
Hop 1
FactLabor[WorkOrderID] is on the many side of the relationship to FactWorkOrder[WorkOrderID]. One work order per labor row, so the value is unambiguous.
Hop 2
FactWorkOrder[ACREG] is on the many side of the relationship to Built DimAircraft[ACREG]. One aircraft per work order, again unambiguous, so RELATED keeps walking and returns the type.
Limit
RELATED follows a chain only while every step goes from many to one. The instant one step goes the other way, it fails, and you need RELATEDTABLE plus an aggregator for that step.
Why this and not that

RELATED, and not LOOKUPVALUE ( DimAircraft[AircraftType], DimAircraft[ACREG], RELATED ( FactWorkOrder[ACREG] ) ). Both return the same string. LOOKUPVALUE performs its own search and does not require a relationship, which makes it the right tool when no relationship exists. Here one does, and RELATED uses the relationship the engine has already indexed. Choosing LOOKUPVALUE when a relationship is available is paying for a search you have already paid for once.

Grouped by type that is 23.5 hours on the A320-200 fleet, 9.0 on the B737-800, 17.5 on the E175 and 12.0 against the recovered tail N338WA. L-507 returns a value at all because DimAircraft was built as an append of the registry and the distinct tails from the work orders. N338WA is therefore a real dimension row with placeholder attributes. Against the raw registry, RELATED would find nothing and those 12.0 hours would vanish from every type breakdown on the report.

One last honest caveat about calculated columns generally. Every column here is computed at refresh and stored in the model, so it costs memory in proportion to its cardinality and it cannot respond to a slicer. Aircraft Type on FactLabor is a reasonable trade, since the model already stores the same values on DimAircraft and the dictionary is tiny. Labor Lines on FactWorkOrder is fine at eight rows and would be worth questioning at eight million. At that size a measure using COUNTROWS over the filtered fact table gives you the same answer without materialising anything. Reach for a calculated column when you need the value on a slicer or an axis. Reach for a measure otherwise.

What to remember
  • A row context knows which row you are on. A filter context knows which rows exist. Neither one implies the other.
  • Calculated columns and iterators create row context. Slicers, visual axes, report filters and CALCULATE create filter context. A measure starts with filter context only, which is why SUM ( FactLabor[Hours] ) works and a bare FactLabor[Hours] does not.
  • Context transition is CALCULATE converting the current row into a filter on all columns of the iterated table. Any measure reference inside an iterator triggers it, because the engine wraps measures in an implicit CALCULATE.
  • SUMX ( FactLabor, FactLabor[Hours] ) and SUMX ( FactLabor, [Labor Hours] ) both return 62.0 by completely different routes, and only the first is cheap.
  • SUMX ( DimTechnician, [Labor Hours] ) returns 52.0 over the six HR technicians, because TECH-07 on L-506 is not in the dimension and is never iterated. Add the Unknown member and it returns 62.0. What you iterate decides what you can possibly count.
  • Transition on a table without a unique key filters to every row matching on all columns, which inflates totals with no error. Keep a key on anything you intend to iterate.
  • Use VAR to capture the outer row value instead of EARLIER in all new code. Same result, and it survives being nested inside somebody else's iterator.
  • In a calculated column, RELATED reaches towards the one side across any chain of many to one hops, and RELATEDTABLE with an aggregator reaches towards the many side. Wrap the count in COALESCE unless you want blanks for work orders with no activity.
