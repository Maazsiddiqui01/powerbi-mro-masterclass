Part 3 . Relationships and filter flow

07How a filter actually travels through the model

After this chapter you will be able to point at any number in any visual and say which rows of which tables survived, in what order the engine eliminated the rest, and why a slicer that looks connected sometimes does nothing at all.

The production controller wants labor hours by aircraft type before the morning meeting. You build the matrix in about thirty seconds. E175 comes back 17.5 hours, and he asks the one question that matters: which jobs is that? Nothing in the measure mentions aircraft. Nothing in the labor table mentions aircraft either. This chapter answers him, row by row.

A filter is a set of surviving rows.

You almost certainly learned filtering in Excel. A condition sits on a column, rows that fail it get hidden, and everything else stays visible. That picture holds up fine when you have one table. It stops working the moment you have twelve tables and a measure that reads from one of them while the slicer sits on another. Keep the Excel picture and filter propagation will feel like a rule you memorised. Replace the picture and it becomes something you can work out from first principles.

Here is the replacement. In the tabular engine, a filter context is a set of surviving rows on every table in the model at the same time. Twelve tables, twelve row sets, all decided at once. Before a single measure runs, the engine has already worked out for each table exactly which rows are in play. DimAircraft Dimension might be down to two rows out of seven while DimStation still holds all five. A dimension table is a list of the things you describe work by, one row each, so DimAircraft holds one row per aircraft. FactLabor Fact might be down to three rows out of eight. A fact table holds events, and one FactLabor row is one booking of hours by one technician against one work order. That whole collection of row sets, one per table, is the filter context. Only then does the measure evaluate, and it evaluates against those sets.

Every cell in a visual gets its own filter context, built from scratch. A matrix with four visible rows evaluates the measure four times for the body and once more for the total. Five separate contexts, five separate sets. Nothing carries over between cells. The only thing they share is the model itself.

Rule of thumb

When a number surprises you, do not ask "why is this measure wrong". Ask "which rows survived". The measure is almost never the problem. The set it was handed usually is.

The order of operations inside one cell

Three things happen, always in this order, and the order is why propagation behaves the way it does.

  1. The engine collects every filter that applies to this cell and applies each one directly to the table that owns the column being filtered.
  2. The engine follows relationships outward from those tables, narrowing other tables as it goes, until nothing more can be narrowed.
  3. The measure runs, reading only the rows that survived on whichever table it aggregates.

Step two is propagation. It is a graph walk, and the rule for whether a hop is legal is short: you may cross a relationship from the one side to the many side. Crossing the other way is not allowed unless you explicitly enable it. Everything else in this chapter follows from that single restriction.

Read the top row of boxes left to right and look at where the arrowheads sit. Both arrows point the same way. Each is marked 1 at the end it leaves and * at the end it arrives, so every hop runs from the one side to the many side. Only the first arrow leaves a dimension. The second leaves FactWorkOrder and lands on FactLabor, header to line, and it is legal for the same reason: one work order row, many labor rows. Nothing points back the other way. That is the constraint the engine enforces, drawn, and it means the reachable set from any starting table is fixed and knowable before you run anything.

The three numbered cards underneath sit directly below the box each one belongs to, and they hold the whole idea. Card 1 is what survives on DimAircraft once the diagram's E175 filter lands, two aircraft registrations. Card 2 is what is left on FactWorkOrder after the first hop, two work orders. Card 3 is what is left on FactLabor after the second hop, three labor rows with their hours printed beside them. The green card on the right adds those three hours to 17.5. Each card is a set of surviving rows, never a condition, and the measure only appears at the end, on whatever the last card still contains.

Hand trace: Labor Hours for the E175 row

Build a matrix. Put DimAircraft[AircraftType] on rows and one measure in values.

DAXLabor Hours
Labor Hours =
    SUM ( FactLabor[Hours] )
Line 1
The measure name. It aggregates FactLabor, and nothing in its definition mentions aircraft. That matters: the connection to DimAircraft lives entirely in the model, not in the code.
Line 2
SUM adds one stored column across whatever rows survive. Nothing here needs a row by row expression, so SUMX would only add an iterator the engine has to unwind. Use SUM when you are adding a single physical column and save SUMX for the cases where you are multiplying two columns together.

Now trace the E175 row in full. The three cards in the diagram above give you the shape and the answer; what follows is every row at every stage, so you can see what was dropped as well as what was kept. Four steps, because the measure evaluating is a step in its own right, and at each one the only question is which rows are still standing.

Step 1. The visual filters DimAircraft

The row header is a filter on DimAircraft[AircraftType] with the value E175. That column lives on DimAircraft, so the filter lands there first, before any propagation happens at all.

The surviving set is exactly two aircraft registrations, N902TT and N553KD. Note that N553KD survives even though it has never had a work order. Nothing about the dimension knows or cares about that yet.

Step 2. DimAircraft propagates to FactWorkOrder

There is one relationship out of DimAircraft, from DimAircraft[ACREG] to FactWorkOrder[ACREG], and it runs from the one side to the many side. Legal hop. The engine keeps the FactWorkOrder rows whose ACREG is in the surviving set from step 1.

N553KD contributed nothing, because no work order references it. The set from step 1 had two members and the set here has two members, but that is coincidence: one tail supplied both.

Step 3. FactWorkOrder propagates to FactLabor

The header to line relationship runs from FactWorkOrder[WorkOrderID] to FactLabor[WorkOrderID], one side to many side. Legal hop again. FactLabor keeps the rows whose work order is in the surviving set from step 2.

Step 4. The measure runs

SUM over FactLabor[Hours] sees exactly three rows: 8.0 plus 4.5 plus 5.0 equals 17.5. That is the number in the E175 cell. Every step that produced it was a set operation, and the only arithmetic happened at the very end. It is also the production controller's answer. Two work orders, WO-1003 and WO-1007, three labor bookings between them.

Now look at what else the engine did on the way. People skip this part and find it confusing later. The filter context for that one cell is a state of the entire model, and the E175 selection is only the piece of it you asked for.

Two things in that table are worth stopping on. First, FactParts narrowed to two rows without anyone asking, because it hangs off FactWorkOrder exactly the way FactLabor does. Drop a Parts Cost measure into the same matrix and the E175 row returns 10,200 plus 2,480, which is 12,680. You did no extra work to get it. Second, the dimensions listed lower down the table still have every row. Nothing touched them, because reaching them would mean walking a relationship backwards.

The total row is the same measure evaluated one more time, with no filter on DimAircraft at all. Nobody adds the four rows up. The total agrees with their sum here because every labor row belongs to exactly one aircraft, and that agreement is a property of this data. Hold onto the distinction. It breaks in the bridge table chapter, and it breaks again later in this one.

The expanded table, and why it is the abstraction that matters

The planner points at a slicer on part category and asks whether it changes labor hours. You could trace it: filter the part table, walk every relationship out of it, write down what survives. That is twenty minutes with a pen. There is a way to answer her in about ten seconds, and this is it.

Doing that trace by hand every time would be exhausting. There is a shortcut, and once you hold it most propagation questions become something you can settle in your head.

Conceptually, every table in the model is expanded to include the columns of every table you can reach from it by following many to one relationships. Many to one only, in the direction a fact row points at its dimension row. So the expanded version of FactLabor carries its own six columns (LaborID, WorkOrderID, TechnicianID, WorkDate, Hours and HourlyRate). On top of those it carries the columns of FactWorkOrder, plus DimAircraft, DimStation, DimWOType, DimTechnician and DimDate. All of them, as if they had been joined into one very wide table.

Now restate propagation using it. A filter on DimAircraft[AircraftType] is a filter on a column of the expanded FactLabor, so it filters FactLabor. A filter on DimTechnician[EmployeeType] is also a column of expanded FactLabor, so it filters FactLabor too. A filter on DimPart[Category] is not a column of expanded FactLabor, because DimPart sits outside every many to one hop that leaves FactLabor. So it does nothing to labor hours, however prominently the slicer sits on the page. That answers the planner, and it took one look at the expansion list.

Interview-level insight

Expanded tables also explain why CALCULATE filter arguments work the way they do. When you write a filter on a dimension column inside a measure that aggregates a fact, you are filtering a column of the fact's expanded table directly. As far as that filter is concerned, the dimension is already part of the fact. So the filter arrives whether or not the dimension appears anywhere in the visual, and the direction of the relationship decides what is reachable. Your intuition about which table should reach which gets no vote.

Write out the expansion for your own model once, on paper, and keep it. For Meridian it takes ten minutes and it answers roughly eighty percent of the "why doesn't this slicer work" questions you will ever be asked.

Why filters only travel one way

The shift supervisor asks this one first, and then everybody else asks it. Why does the slicer work in one direction and sit there in the other? The stock reply, that this is just how Power BI works, gives you nothing to use the next time the model surprises you. Here is the mechanism.

Going from the many side to the one side is deterministic. Take FactWorkOrder row WO-1003. Its ACREG is N902TT, and DimAircraft[ACREG] is unique, so that row points at exactly one dimension row. Always one. The lookup is a single hash probe and the answer is a scalar. Every fact row in the model behaves this way, which is what makes the expanded table well defined in the first place.

Going the other way loses that guarantee. Take DimAircraft row N771QR. It is referenced by WO-1001, WO-1004 and WO-1008, three rows. A different tail would give a different count. So propagating from the one side to the many side returns a set, and the engine has to build that set before it can apply it. That is more work, and the work scales with how many distinct keys survive.

The second problem is worse than the cost. Sets can arrive by more than one route. Suppose both directions were open by default. A filter on DimStation could then reach FactLabor through FactWorkOrder. Had somebody built the relationship, it could reach the same table through DimTechnician[HomeStation] as well. Those two routes give different answers to the same question. The Meridian model leaves out DimStation[StationCode] to DimTechnician[HomeStation] for exactly this reason. With one direction, the reachable set from any table is unique, and the model has exactly one interpretation.

Many to one
One row, always
One to many
A set, size varies
Default direction
One side to many side
What it buys you

Five ways to make a filter go the other way

The production controller who staffs the LAS line wants hours by the technician's home station. He is asking what his own people booked, wherever the aircraft happened to be sitting. The model holds a work order station and a technician home station, with no relationship between them. He has asked a filter to travel in the one direction this model refuses to send it.

Sometimes you genuinely need the flow reversed. There are five options and they are not equal. They are listed here in the order you should consider them, which is not the order most people try them in.

Option 1 is the one people skip, and it is usually correct. Before reaching for anything clever, check whether the filter could come from a dimension both facts already touch. Labor hours and planned capacity share DimStation and DimDate. You do not need any reverse flow between them, and the utilisation trace at the end of this chapter shows why.

Option 3 has a concrete home in this model. Meridian deliberately refuses to relate DimStation to DimTechnician[HomeStation], because that would give a filter on DimStation two routes to FactLabor. But "how many hours did technicians based at MSP book, wherever they booked them" is a fair question. TREATAS answers it without a relationship.

DAXLabor Hours by Home Station
Labor Hours by Home Station =
VAR SelectedStations =
    VALUES ( DimStation[StationCode] )
RETURN
    CALCULATE (
        [Labor Hours],
        REMOVEFILTERS ( DimStation ),
        TREATAS (
            SelectedStations,
            DimTechnician[HomeStation]
        )
    )
Line 2 to 3
Capture the station codes currently visible. VALUES rather than DISTINCT: VALUES includes the blank row the engine adds for unmatched keys. When you hand a set to a virtual relationship, you want that blank travelling with it. DISTINCT leaves it behind.
Line 5
CALCULATE is the only function that can modify a filter context. A bare FILTER would build a table, but it cannot change what the surrounding measure sees, so it is not an alternative here.
Line 7
REMOVEFILTERS on DimStation stops the original station filter from also propagating through FactWorkOrder. Without it you get the intersection of two different definitions of station. ALL would do the same job, but it reads as a table function and this is a modifier, so REMOVEFILTERS states the intent.
Line 8 to 11
TREATAS takes the captured values and applies them as a filter on DimTechnician[HomeStation], a column with no relationship to DimStation at all. That filter then propagates normally down to FactLabor.
Why this and not that

TREATAS rather than a physical relationship, because a physical relationship here is the exact thing this model was built to avoid. TREATAS and not CROSSFILTER: CROSSFILTER can only change the direction of a relationship that already exists, and here there is none. TREATAS and not INTERSECT on the technician table, because INTERSECT hands you a table to compare against, where what you need is a filter the engine will propagate. The trade is that nothing in the model diagram hints this measure exists.

Run it and the answers differ from the station route, which is the point. Technician home station and work order station are two different facts about the same hours.

LAS is the interesting cell, and it is the production controller's answer. Five hours of work happened at LAS. K. Ibrahim is based there and booked thirteen hours in total, most of them on a Tucson work order. Both figures describe his line. Put the two columns on one page without labelling them clearly and somebody will build a staffing plan on the wrong one.

Performance note

Reversing filter direction has a price, and the price tracks the number of distinct keys that survive. Table size barely comes into it. Making FactWorkOrder to FactLabor bidirectional on eight rows costs nothing you could measure. Do it on a work order table with four million keys and the engine materialises a key set of up to four million values, then hands it across on every query that touches both tables. This is why a bidirectional relationship on a small bridge, where the key is a certification code with four values, is usually fine. It is also why a bidirectional relationship on a transaction identifier is usually what you find at the bottom of a slow report.

When there is no path at all

The finance manager wants parts cost split by employee type. Staff against contract, one figure each, on the Friday pack. It sounds like a five minute job, and the model already holds every column the question names.

Put a slicer on DimTechnician[EmployeeType] with Staff and Contract on it. Put a card next to it showing Parts Cost, defined as follows.

DAXParts Cost
Parts Cost =
    SUMX (
        FactParts,
        FactParts[Qty] * FactParts[UnitCost]
    )
Line 2
SUMX and not SUM, because there is no stored extended cost column on FactParts and SUM cannot multiply two columns. A calculated column would also work and would let you use SUM, but it materialises a value into the model that you only ever need at query time.
Line 3 to 4
The iterator walks whatever rows of FactParts survive the filter context, multiplying quantity by unit cost for each and adding the results.
What you see in the report

The slicer works. Buttons highlight, the selection sticks, the other visuals on the page respond. The Parts Cost card reads 28,245 with Staff selected, 28,245 with Contract selected, and 28,245 with nothing selected. It never moves.

Explain it as a graph walk and the reason is immediate. From DimTechnician the engine can hop to FactLabor, because that relationship runs one side to many side. From FactLabor the only relationship that leads anywhere new is FactWorkOrder to FactLabor, and taking it would mean walking from the many side to the one side. Not allowed by default. The other two relationships touching FactLabor come in from DimDate and DimTechnician, and they point the wrong way as well. The walk stops there. FactParts is never reached, all seven rows survive, and the measure returns the same 28,245 every time. Said the other way: DimTechnician is not in the expanded table of FactParts, so it cannot filter it.

Common mistake

Assuming a slicer that visibly reacts is a slicer that is doing something. Slicer interactivity is a property of the slicer visual. Whether the selection reaches your measure is a property of the model. They are unrelated, and a slicer that filters nothing looks exactly like a slicer that filters everything.

Three fixes get proposed whenever this comes up. One of them can be built against this data. One cannot be built here at all. The third is the correct answer, and it is the one that almost never gets built.

Fix A. Push the filter through with CROSSFILTER

DAXParts Cost Pushed Through Labor
Parts Cost Pushed Through Labor =
    CALCULATE (
        [Parts Cost],
        CROSSFILTER (
            FactWorkOrder[WorkOrderID],
            FactLabor[WorkOrderID],
            BOTH
        )
    )
Line 2
CALCULATE again, because the relationship direction is part of the filter context and only CALCULATE can alter it.
Line 4 to 8
CROSSFILTER names the two columns of an existing relationship and sets its direction to BOTH for this evaluation only. USERELATIONSHIP is the function people reach for first. It wakes an inactive relationship, and this relationship is active already, so it does not apply here. Setting the relationship bidirectional in the model view would work too, and it would change every measure in the file, which is exactly what you are trying to avoid.

Now the filter reaches. DimTechnician narrows FactLabor, FactLabor narrows FactWorkOrder because the direction is temporarily open, and FactWorkOrder narrows FactParts as usual. You get numbers. Read them carefully.

Two independent errors are stacked in that table and both are structural. WO-1001 was worked by TECH-02, who is Staff, and TECH-04, who is Contract, so its 1,240 of brake parts appears in both rows. WO-1003 does the same with 12,680. That is 13,920 counted twice. Meanwhile the rows are missing 1,875 from WO-1005, which has parts but no labor at all, and 4,900 from P-9007, whose work order WO-1009 does not exist in FactWorkOrder. Those two add to 6,775, which is exactly the gap between 28,245 and the 21,470 the rows actually cover. Double count 13,920, omit 6,775, and you land 7,145 above the correct grand total.

Fix B. Denormalise the technician onto the parts fact

Add a TechnicianID column to FactParts in Power Query and relate it to DimTechnician. This is option 5 from the ranked list, and in many situations it is the best answer available. Here it is not available at all, because the source has no such column. PartsIssued arrives with IssueID, WorkOrderID, PartNumber, Qty, UnitCost and IssueDate. There is no technician anywhere in it. You could allocate parts cost to technicians in proportion to hours booked, and that is a legitimate thing to build, but be honest about what it is: an assumption you invented, not a fact you loaded.

Fix C. Change the question

This is the correct answer, and it is the inconvenient one. The stores log records that a part left the shelf against a work order. Nobody wrote down who fitted it, and no amount of relationship configuration will conjure a fact that was never captured. So a part issue in this data belongs to a work order and to nothing else. "Parts cost by employee type" is a question with no defined answer, given these six source tables. The obstacle sits in the source data, and Power BI will hand you a number for it anyway if you ask. Building a model that returns one is worse than returning nothing, because the number looks authoritative.

What you can answer, precisely, is "parts cost on work orders that contract technicians booked time to". That is 13,920, and Fix A computes it correctly. Two rules come with it. You may show it as a single filtered figure. You may never put it in a matrix with a total row, because the moment two employee types appear side by side the shared work orders get counted twice. Rename the measure to say so. A measure called Parts Cost On Work Orders Touched will get questioned by the person reading it. A measure called Parts Cost will sail through. That is the honest version of the finance manager's Friday number, and part of the job is telling him why the other version does not exist.

How the filters stack

The shift supervisor says the report is wrong. His whiteboard shows more MSP work on the A320s this month than your matrix does. He has been counting jobs and the matrix has been adding hours, and neither of you has noticed that yet. There are three filters on that page, and he can see two of them.

One cell usually has more than one filter arriving at it. The sources are report level filters, page level filters, visual level filters, every slicer on the page, the row, column, legend and small multiple fields of the visual itself, cross highlighting from a selection in another visual, row level security if it is configured, and any filter the measure applies with CALCULATE. All of them contribute.

They combine by intersection. Each filter produces a set of surviving rows, and the engine keeps the rows that survive all of them, which is logical AND. There is one exception worth knowing. A filter argument inside CALCULATE overwrites any existing filter on the same column. Everything arriving from outside the measure intersects.

Work an example on the A320-200 row. Three filters, from three different places, landing on three different tables.

WO-1008 survives all three filters and still contributes nothing, because it has no labor rows yet. That is the difference between a work order sitting in the filter context and a work order having something to add. Both are true here, and only one of them shows up in the number. That answers the shift supervisor. He counted two jobs, the matrix added the hours on one of them, and both of you were right.

One habit will save you a great deal of time. When a number looks wrong, start with the visual and leave the DAX alone for a minute. Strip the visual back to one row and one measure, then add the filter sources back one at a time and watch where the number changes. You are looking for the filter that removed a row you expected to keep. The formula is rarely where the trouble lives.

Trace this by hand, row by row: Utilisation at MSP in January

The first trace had a single chain. This one has two branches that converge, which is the more common shape and the one worth practising. The measures:

DAXPlanned Hours and Utilisation
Planned Hours =
    SUM ( FactCapacity[PlannedHours] )

// Utilisation compares booked hours to planned hours
Utilisation =
    DIVIDE ( [Labor Hours], [Planned Hours] )
Line 2
SUM over the unpivoted capacity fact. The trade columns became rows during the unpivot, so a station month now has four rows and adding them is a plain column sum.
Line 6
DIVIDE and not the division operator. LAS has no capacity row for January, so [Planned Hours] is blank there, and DIVIDE returns blank rather than raising an error. The operator would fail on the same cell, and a visual that errors on one cell shows nothing at all.

Put DimStation[StationCode] on rows, DimDate[MonthName] on columns, and read the cell at MSP and January. Two filters land, and neither one touches FactLabor or FactCapacity directly.

Branch one, the station filter

DimStation is filtered to the single row MSP. It has two relationships out, both one side to many side, so both propagate.

  • DimStation to FactWorkOrder leaves WO-1001, WO-1002, WO-1006 and WO-1008.
  • DimStation to FactCapacity leaves the twelve rows that belong to MSP, four trades in each of three months.

The work order set then propagates one more hop to FactLabor, leaving L-501, L-502, L-503 and L-507.

Branch two, the date filter

DimDate is filtered to the thirty-one January dates. It also has more than one relationship out.

  • DimDate[Date] to FactLabor[WorkDate] leaves L-501, L-502, L-503, L-504 and L-505.
  • DimDate[MonthStart] to FactCapacity[MonthStart] leaves every row whose MonthStart is 2025-01-01, which is MSP January, TUS January, and no others.
Where the branches meet

L-506 and L-508 are omitted from that table because they fail both branches. Labor Hours for the cell is 7.5 plus 6.0 plus 9.0, which is 22.5.

Twelve MSP rows from the station branch, intersected with the eight January rows from the date branch (four trades at MSP and four at TUS), leaves four. They add to 14 plus 8 plus 6 plus 2, which is 30. DIVIDE then returns 22.5 divided by 30, which is 0.75, shown as 75.0 percent.

Two things about this trace are worth carrying forward. First, the capacity relationship is on MonthStart, not on Date, so it only matches when the date filter includes the first of the month. Filter the page to January and it works, because 2025-01-01 is in the set. Filter the page to 2025-01-15 alone and FactCapacity keeps nothing. [Planned Hours] goes blank, and DIVIDE returns blank. A blank cell is easier to question than a percentage computed against nothing. That is the grain mismatch behaving as designed, and it is the reason the measure was written with DIVIDE in the first place.

Second, DimDate can reach FactLabor two ways in this model: directly through FactLabor[WorkDate], and indirectly through the active FactWorkOrder[OpenedDate] relationship followed by the header to line hop. For MSP in January both routes land on the same three rows, so 22.5 is correct either way. In a model where labor is booked in a different month from the one the work order opened in, they would not agree. Before you trust a date slicer against a header and line pair, filter to a single day and check that the number is what you expect. If it comes back blank, you have found this.

Working the ranked list

Four requests have landed on your desk this month, one from nearly everybody in this chapter. The planner wants planned hours beside booked hours. The production controller wants hours by home station. Somebody in the training office wants hours by certification, which here means A&P, Avionics, NDT and Engine Run. A&P is the Airframe and Powerplant licence a mechanic holds. The finance manager still wants parts cost by employee type. Four requests, one list, and four different answers.

A ranked list is only useful if you can watch someone climb it and reject rungs out loud. Here are those four requirements. Three of them land on a different rung each, and the fourth never reaches a rung at all.

The second row is the one worth climbing in full, because four of the five rungs are technically available and only one of them is right.

Rung 1, re-point at a shared dimension. Is there a table that both DimCertification and FactLabor already touch? No. DimCertification has exactly one relationship, out to BridgeTechCert. A bridge table is a small table of pairs that joins two tables which cannot relate to each other directly, and this one holds ten rows, one per technician and certification pair. The bridge holds no measures. There is nothing to re-point, and no dimension you could build would change that, because a certification describes a technician and never a labor row. Rung 1 does not apply here at all, and cost never enters into it.

Rung 2, CROSSFILTER inside one measure. This works. Wrap the hours measure in CALCULATE with CROSSFILTER over BridgeTechCert[TechnicianID] and DimTechnician[TechnicianID] set to BOTH, and A&P returns 39.0. The arithmetic is fine. The objection is to the premise of rung 2, which is false in this case. Rung 2 is right when one or two measures need the hop. Hours by certification, cost by certification, headcount by certification and average hours per certified technician all need it. Every one of them then carries its own copy of the modifier, which is four places for the next person to keep in step, and a fifth measure that will be written without it.

Rung 3, TREATAS. Also works, and the next chapter writes it out in full: capture VALUES ( BridgeTechCert[TechnicianID] ) in the outer filter context and restamp it onto DimTechnician[TechnicianID]. Same 39.0. It has the same repetition problem as rung 2, and one extra risk on top, because TREATAS matches by value with no stored relationship behind it. Had the build left the keys untrimmed, the "TECH-04 " on L-505 would fail to match. A&P would come back 34.5, and nothing in the visual would say that 4.5 hours had gone missing.

Rung 4, a bidirectional relationship. Set DimTechnician to BridgeTechCert to Both and every measure gets the hop without asking for it. The joining key has four distinct values, so the reverse materialisation the engine has to perform is four rows wide. This is the answer. It is the documented exception to the general preference for measure scope over model scope. When every query needs the hop, pay for it once in the model. The alternative is paying for it in four measures and forgetting the fifth.

Rung 5, denormalise the certification onto FactLabor. This looks like the cheapest option on the list and it is the only one that damages the data. A labor row has to be repeated once per certification the technician holds. TECH-04 holds three, so L-502 becomes three rows and L-505 becomes three. TECH-01 holds two, so L-507 becomes two. TECH-07 holds none, so L-506 and its ten hours disappear from the fact table altogether. Eight labor rows become twelve. Total labor hours become 7.5 plus 18.0 plus 9.0 plus 8.0 plus 13.5 plus 24.0 plus 5.0, which is 85.0. That figure is then stored, permanently, for every measure and every user in the file. Rung 4 leaves FactLabor at 62.0 and confines the double count to the certification slice, where you can label it. Rung 5 makes 85.0 the truth.

One last thing about the order. It is a sequence of consideration, and the ranking says nothing about quality. Rung 4 beats rung 2 for the bridge, and rung 2 beats rung 4 for a one off requirement on a wide fact. The list is ordered the way it is because the early rungs are the cheapest to undo. A re-pointed model is a conversation. A modifier inside one measure is one delete. A bidirectional relationship is a property that half a dozen reports have quietly come to depend on by the time anybody thinks to question it.

What to remember
  • A filter context is a set of surviving rows on every table in the model at once. The measure runs last, against whatever survived.
  • Propagation is a graph walk in which every hop must go from the one side to the many side. If no such walk exists between two tables, the slicer does nothing and looks perfectly functional while doing it.
  • Every table is conceptually expanded to include the columns of everything reachable by many to one hops. FactLabor expanded carries FactWorkOrder, DimAircraft, DimStation, DimWOType, DimTechnician and DimDate. Learn this and most surprises stop.
  • One direction is the default because many to one always returns exactly one row, while one to many returns a set that can arrive by more than one route. Single direction is what makes the model unambiguous.
  • To reverse the flow, try re-pointing the model first, then CROSSFILTER, then TREATAS, then a bidirectional relationship, then denormalisation. Most people try them in the opposite order.
  • The ranking is an order of consideration. Different Meridian requirements land on different rungs: utilisation on rung 1, hours by certification on rung 4, hours by home station on rung 3. What the order buys you is that the early rungs are the cheapest to undo.
  • Rung 5 is the one to watch. Denormalising certification onto FactLabor turns eight labor rows into twelve, drops TECH-07 entirely, and makes 85.0 the stored total for everybody, where rung 4 leaves the fact at 62.0.
  • Filters from slicers, page filters, visual filters and the visual's own fields intersect with logical AND. A filter argument inside CALCULATE is the exception: it overwrites any filter already on that column.
  • Some questions have no answer in the data you loaded. Parts cost by employee type is one of them, and forcing a number out of it produces 35,390 against a true total of 28,245.
