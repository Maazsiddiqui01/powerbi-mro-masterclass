Part 5 . Hard modelling cases

15Virtual relationships: TREATAS and friends

After this chapter you can push a filter from one table to another with no relationship between them, argue in a design review when that is the right call and when it is laziness, and recognise the two silent failures that make a TREATAS measure return blank with no error to explain it.

The production controller clicks 20 January on the date slicer, because that is the Monday he is asking about. Labor hours hold at 8.0, which is the time L-504 booked at TUS that day. Planned hours go blank. Utilisation divides one by the other, so it comes back empty too, and he wants to know which of the two numbers is broken. Both numbers are correct. The plan is stored by month, he asked for a day, and this chapter is about closing that gap without adding a relationship to the model.

A relationship is a standing instruction. Once it is in the model it applies to every query, every visual, every measure, and every user who opens the report at seven in the morning without asking you first. Most of the joins you need should work that way. A few should last for one calculation and then be gone, and the controller's question needs one of those. Some joins are true for exactly one measure. Some are true only for the question on one page. Some are true in a way the key columns cannot express. That is the gap TREATAS fills.

Meridian has three of these sitting in the model already. The certification bridge needs a filter to travel backwards up a many-to-many join. FactCapacity is keyed on station plus month, and no single column matches that pair. DimTechnician[HomeStation] holds station codes that would be useful as a filter, and the relationship list says in writing that it must never be related to DimStation. Three different problems, one function, no change to the model diagram.

That last part is the point people miss. TREATAS is not a shortcut for a relationship you were too busy to create. It is a way to keep a join out of the model on purpose.

Look at the gap between the two tables, and at the one thing that crosses it. Nothing joins FactCapacity to FactLabor in the model, so the only connection drawn is a dashed teal arrow. Its label reads "TREATAS, no relationship". Read the grain printed under each table as well. Grain means what one row of a table stands for: station and month on the left, day on the right. Those two labels are why no relationship can be drawn there at all. A relationship stored in the model would be a solid line, and a solid line carries a promise with it. The engine validated the keys at refresh, built structures to make the join fast, and will apply it to every query whether you want it or not. The dashed arrow is a virtual relationship, which is a join that lives inside the measure that writes it and nowhere else. It costs nothing at refresh, it stays out of the model view, and it lasts exactly as long as the one CALCULATE that creates it. For the rest of this book a dashed teal line drawn between two tables means that: a join written in DAX, alive for one evaluation, invisible to anyone reading the diagram.

The two cards underneath the tables run ahead of the argument on purpose. The first is headed Utilisation and sketches the shape of the measure that writes this join: a SUMMARIZE over FactLabor feeding a TREATAS inside CALCULATE. Situation 3 builds that skeleton out in full under the name Planned Hours Where Work Happened. Situation 4 turns it into the ratio the card is named for, which is the number the production controller was staring at. The green card beside it gives the two conditions that make the virtual version the better call here. The join needs two columns, and a Power BI relationship takes exactly one column on each side. The grain assumption also stays where a reader can see it, in the text of the measure. The card names the price too: the whole thing is evaluated per query, with no cached structure to help it.

What TREATAS actually does

Before the four situations, the mechanism. The signature is short, and the second half of it repeats.

DAXSignature
TREATAS ( <table expression>, <column> [, <column>] ... )
Argument 1
Any table expression. It can be a table in the model, a function that returns one, or a list of literal values you typed by hand. Its columns are what will be applied.
Arguments 2 onward
One model column per column of the table expression, in the same order. These are the columns that will be filtered.
Return
A table whose values are unchanged but whose lineage now points at the columns you named. Used as a filter argument to CALCULATE, it behaves exactly like a filter on those columns.

Lineage is the whole mechanism. Lineage is the tag every table expression in DAX carries, saying which model column each of its columns came from. VALUES ( DimStation[StationCode] ) returns a one column table, and that column is tagged DimStation[StationCode]. Hand it to CALCULATE as a filter and CALCULATE knows what to filter, because the tag says so. A list you type yourself, such as { "MSP", "TUS" }, arrives as two anonymous strings with the tag missing.

TREATAS rewrites the tag. It takes the values as they are, changes nothing about them, and declares that column one is now DimStation[StationCode]. From that moment they behave as if they had been read from that column, which means they filter it, and the filter propagates outward along the real relationships exactly like any other.

Argument type
Filter argument to CALCULATE
Match rule
Value equality, type sensitive
Column mapping
Positional, not by name
Lifetime
One evaluation of one CALCULATE

Here is the smallest honest example in the Meridian model. MSP and TUS are the two base stations. LAS is a line station and PHX exists only in the planning workbook. Suppose one measure, and only one, should count hours at the base stations regardless of what the station slicer says.

DAXHours at Base Stations
Hours at Base Stations =
    CALCULATE (
        [Labor Hours],
        TREATAS (
            { "MSP", "TUS" },
            DimStation[StationCode]
        )
    )
Line 2
CALCULATE and not CALCULATETABLE, because a visual needs one number in the cell. Both accept a TREATAS filter argument in the same way. The difference is what comes back: a table is what you want when the result feeds an iterator, and useless when it has to fill a cell.
Line 5
The table constructor braces build a two row, one column table with no lineage. Written on its own as a filter argument it is rejected, because CALCULATE has no idea which column those strings belong to.
Line 6
The target column. DimStation[StationCode] and not FactWorkOrder[StationCode]: filter the dimension and the filter reaches both FactWorkOrder and FactCapacity through the existing relationships. Filter the fact column directly and you have restricted one table and left the other wide open.

The result is 57.0 hours: 34.5 at MSP plus 22.5 at TUS. The UNASSIGNED member is excluded by the filter, which costs nothing here because WO-1005 has no labor rows at all, and LAS loses its 5.0 hours as intended.

Interview-level insight

Describe TREATAS as a lineage cast and the rest of its behaviour follows without being memorised. Column order matters, because the cast is positional. Data types matter, because the cast changes the tag and leaves the value alone. It costs what it costs, because nothing is stored. Calling it "a virtual relationship" repeats a phrase. Calling it "restamping the lineage of a table expression so CALCULATE filters the column you named" shows you understood it.

Situation 1: the join that must not become a relationship

The shop manager wants a slicer of target utilisation by station, so a report user can look at only the stations held to a target of fifty percent or better. The targets live in a small table with two columns and four rows. Build it as a calculated table so it stays in the model without a query refresh dependency.

DAXTargetUtil, a disconnected table
// Each target is that station's best Q1 month, from the
// utilisation figures: MSP 75%, TUS 50%, LAS 25%, PHX 0%.
TargetUtil =
    DATATABLE (
        "StationCode", STRING,
        "TargetPct", DOUBLE,
        {
            { "MSP", 0.75 },
            { "TUS", 0.50 },
            { "LAS", 0.25 },
            { "PHX", 0.00 }
        }
    )
Line 4
DATATABLE and not the table constructor { ... }. The constructor works and is shorter, but it names its columns Value1 and Value2 and infers their types from the first row. DATATABLE makes you declare both. Since TREATAS matches on value and is sensitive to type, a table whose types you declared yourself is worth the extra four lines.
Line 6
DOUBLE and not CURRENCY. Utilisation is a ratio, and the fixed four decimal places of the currency type would quietly round a target expressed to more precision later.

Now the measure. The slicer sits on TargetUtil[TargetPct], and whatever stations survive that selection have to filter the labor numbers.

DAXHours at Selected Targets
Hours at Selected Targets =
    CALCULATE (
        [Labor Hours],
        TREATAS (
            VALUES ( TargetUtil[StationCode] ),
            DimStation[StationCode]
        )
    )
Line 5
VALUES reads the station codes that survive whatever the user picked in the slicer. The slicer sits on TargetUtil[TargetPct], a different column of the same disconnected table, so the selection filters TargetUtil itself and VALUES then reads the codes on the rows that are left. No relationship is involved in that step at all.
Line 6
The one model column that receives the values. Note that TargetUtil stays disconnected: no relationship is created, and the only thing that ever crosses from it to the rest of the model is this one filter, inside this one measure.

Select the 0.75 and 0.50 targets in the slicer and VALUES returns MSP and TUS, so the measure reads 57.0 hours again. This time the report user drove it, and nothing is hard coded. Select nothing and all four stations pass through, which gives 62.0, because every hour Meridian booked in Q1 sits at MSP, TUS or LAS.

Why this and not that

VALUES and not DISTINCT. The two differ in one respect. When the column sits on the one side of a relationship, and the many side holds keys that match nothing, VALUES returns an extra blank row for those unmatched members. DISTINCT leaves that row out. TargetUtil is disconnected, so today both return the same four codes. I still write VALUES. If this table is ever related to something and an unmatched key appears, I want the blank member sitting visibly inside the filter where I can find it.

So why not relate TargetUtil[StationCode] to DimStation[StationCode] and stop writing DAX? Two reasons, both structural. Both columns are unique, so Power BI creates the relationship as one to one, and a one to one relationship always cross filters in both directions. The dialog gives you no option to make it single. The target table would then filter DimStation on every query in the report, which is the standing instruction this chapter exists to avoid. Try to route around that by relating TargetUtil straight to the facts and you hit the second reason. Relate it to both FactCapacity[StationCode] and FactWorkOrder[StationCode] and you have closed a loop, since DimStation already reaches both. Power BI accepts the first and refuses to activate the second.

Meridian has a second instance of this and it is written into the relationship list as a deliberate omission. DimStation[StationCode] is never related to DimTechnician[HomeStation], because that would give DimStation two roads to FactLabor, one through FactWorkOrder and one through DimTechnician, which is the ambiguity case from Chapter 8. The relationship stays out. The question it would answer does not have to.

DAXLabor Hours by Home Station
Labor Hours by Home Station =
VAR StationsInContext = VALUES ( DimStation[StationCode] )
RETURN
    CALCULATE (
        [Labor Hours],
        REMOVEFILTERS ( DimStation ),
        TREATAS (
            StationsInContext,
            DimTechnician[HomeStation]
        )
    )
Line 2
Capture the station codes visible right now, before anything is cleared. A VAR and not the expression written inline: a filter argument of CALCULATE is evaluated in the outer filter context anyway, so both forms return the same values, but the variable removes any need for the reader to know that rule to trust the measure.
Line 6
This line is the one people leave out, and leaving it out is why the measure looks broken. DimStation[StationCode] is on the matrix rows, so it is already filtering FactWorkOrder through the physical relationship. Without REMOVEFILTERS the measure returns hours that are both at that station and worked by a technician homed there, so TUS reads 4.5 rather than 10.5 and LAS reads 5.0 rather than 13.0. REMOVEFILTERS and not ALL. Used as a filter modifier inside CALCULATE the two behave identically, and only one of them is named after the job it is doing.
Lines 7 to 10
The captured codes are retagged onto DimTechnician[HomeStation], a plain descriptive text column with no relationship attached to it. That is the whole trick: a column does not need to be a key to be filtered.

Put DimStation[StationCode] on the rows of a matrix and you get a second answer to the question "hours by station". Both answers are right. MSP shows 28.5, being TECH-01 at 12.0 plus TECH-02 at 16.5 plus TECH-06 at zero. TUS shows 10.5, from TECH-03 at zero and TECH-04 at 10.5. LAS shows 13.0, from TECH-05 alone. The UNASSIGNED row picks up TECH-07 and its 10.0 hours, because TECH-07's home station in DimTechnician is the unassigned member and DAX text matching ignores case. PHX comes back blank, since nobody is homed there. Total 62.0, same as before, distributed differently.

TECH-04 is why the two columns differ most sharply. Sandoval is homed at TUS and booked 6.0 hours on WO-1001 at MSP plus 4.5 on WO-1003 at TUS, so 6.0 hours change column when the definition of station changes. A relationship would force the model to pick one of these two meanings and make the other unreachable. Keeping it virtual means both stay available, each in a measure named for what it measures.

Situation 2: replacing a bidirectional relationship

The shift supervisor holds up his whiteboard and says the certification report is wrong. Every row on it reads 62.0. A&P 62.0, Avionics 62.0, NDT 62.0, Engine Run 62.0. He is right, and the reason is a filter that stops halfway across the model. DimCertification filters BridgeTechCert, and the bridge sits on the many side of DimTechnician, so the filter arrives at the bridge and goes no further. FactLabor is left unfiltered, and every cell reports the whole quarter. This is the standard argument for bidirectional cross filtering, and it is the standard argument because the requirement is real.

The wrong way

Set the cross filter direction on DimTechnician to BridgeTechCert to Both. It takes four seconds and the numbers come out right.

What you have actually done is give every future measure in the model a filter path that runs backwards through the bridge. Any measure, on any page, written by anyone. The bridge is small today, at ten rows, so nothing hurts yet.

You have also added a second filter path between DimCertification and anything downstream of DimTechnician, which is how ambiguity errors arrive six months later in a model you no longer remember building.

The fix

Leave every relationship single direction. Read the technician list out of the bridge in the current filter context and push it onto the technician dimension inside one measure.

The join now exists in exactly one place, and that place has a name that says what it is for. Anyone reading the measure sees the join. Anyone reading the model diagram sees a model with no back doors in it.

The four certification numbers are identical to the bidirectional version. No model change, and no arrow to explain in a review.

DAXHours by Certification
Hours by Certification =
    IF (
        ISFILTERED ( DimCertification[CertCode] ),
        CALCULATE (
            [Labor Hours],
            TREATAS (
                VALUES ( BridgeTechCert[TechnicianID] ),
                DimTechnician[TechnicianID]
            )
        ),
        [Labor Hours]
    )
Lines 2 and 3
IF and not SWITCH ( TRUE ( ) ), because there is one condition and SWITCH only earns its place from the third branch onward. ISFILTERED and not HASONEVALUE: HASONEVALUE is false when the user selects two certifications, which would send a legitimate multi-select down the unfiltered branch and report 62.0 for it. ISFILTERED asks the question that matters, which is whether anything at all is restricting this column right now.
Line 7
VALUES reads the bridge as it stands in the current filter context. On the A&P row that context holds three bridge rows, so three technician ids come back. This is the step that walks the many-to-many relationship, and it walks it in the direction the model will not.
Line 8
The target is the dimension key, not FactLabor[TechnicianID]. Filtering the dimension lets the existing one to many relationship carry the filter into the fact, which is the path the engine is already built to serve. Filtering the fact column directly works too and is measurably worse, because you are applying a filter to a large table instead of a small one.
Line 11
The fallback branch. Without it the grand total reads 52.0 where the honest answer is 62.0. The trace below the table works through why the engine is behaving correctly when it does that.
Trace this by hand, row by row

Take the A&P row. The filter context holds DimCertification[CertCode] equal to A&P, which propagates down the one to many relationship into BridgeTechCert and leaves three rows visible: TECH-01/A&P, TECH-02/A&P and TECH-04/A&P. VALUES ( BridgeTechCert[TechnicianID] ) reads those three rows and returns TECH-01, TECH-02, TECH-04, tagged as bridge technician ids.

TREATAS retags them as DimTechnician[TechnicianID] and CALCULATE applies them, which cuts the technician dimension to three rows. That filter travels the existing relationship into FactLabor, and [Labor Hours] sums what is left: 12.0 for TECH-01, 16.5 for TECH-02, 10.5 for TECH-04, giving 39.0.

Avionics resolves to TECH-03, TECH-04 and TECH-06, which is 0 plus 10.5 plus 0, so 10.5. NDT resolves to TECH-01 and TECH-03, which is 12.0 plus 0, so 12.0. Engine Run resolves to TECH-04 and TECH-05, which is 10.5 plus 13.0, so 23.5.

Add the four and you get 85.0 against a true total of 62.0, because TECH-04 holds three certifications and every one of his 10.5 hours is counted three times. That double count belongs to the question, not to TREATAS. A bidirectional bridge produces the identical 85.0.

Now the grand total. On that row DimCertification[CertCode] carries no filter, so VALUES ( BridgeTechCert[TechnicianID] ) returns all six technicians the bridge knows about. TECH-07 is not one of them: he is the recovered orphan from L-506 and has no certification row. The TREATAS branch would therefore report 52.0 and drop his 10.0 hours without saying so, which is what the ISFILTERED wrapper on line 3 prevents. Note that 52.0 is defensible in its own right. If the total is meant to cover certified staff only, keep it and label the visual accordingly.

The option in between: CROSSFILTER

There is a third option, and on the certification bridge it is probably the one to ship. The choice is usually put as bidirectional relationship against TREATAS, as though those were the only two on the table. CROSSFILTER sits between them. It takes a relationship that already exists in the model and changes its filter direction for the duration of one CALCULATE. USERELATIONSHIP does the same trick for which relationship is active. Either way, the Both flag moves out of the model and into the measure, where it applies to one calculation and stops applying to everybody else.

DAXHours by Certification, scoped bidirectional
Hours by Certification (CROSSFILTER) =
    CALCULATE (
        [Labor Hours],
        CROSSFILTER (
            BridgeTechCert[TechnicianID],
            DimTechnician[TechnicianID],
            BOTH
        )
    )
Line 4
CROSSFILTER and not USERELATIONSHIP. Both name a relationship by its two endpoints, which is why the two get mixed up. The technician to bridge relationship is already active, so there is nothing here to activate. Its direction is the problem, and direction is the one thing CROSSFILTER touches.
Lines 5 and 6
The many side column first and the one side column second. The engine resolves the pair to a relationship whichever order you write them in, so treat this as a reading convention. Written this way, the arguments run in the direction the filter is about to travel: up out of the bridge and into the dimension.
Line 7
BOTH is what lets the certification filter climb from the bridge into DimTechnician. The other two accepted values are ONEWAY and NONE. Remember NONE: switching a relationship off for one measure is now and then the shortest way out of a filter you did not ask for.
What is absent
No VALUES, no lineage cast, and no ISFILTERED wrapper. The measure is nine lines against the twelve of the TREATAS version above it. The paragraphs below explain why this version can safely go without the guard.

The four row values are the ones you already know: A&P 39.0, Avionics 10.5, NDT 12.0 and Engine Run 23.5, still summing to 85.0 against a real 62.0, because that double count belongs to the question and no function fixes it. The grand total is where the two approaches part company, and this is the difference to carry out of the chapter.

TREATAS applies a list of values. At the grand total that list is VALUES ( BridgeTechCert[TechnicianID] ) over an unfiltered bridge, which comes to the six technicians the bridge knows about. Applying that list silently drops TECH-07 and his 10.0 hours, giving 52.0. That is why the measure needs ISFILTERED on line 3. CROSSFILTER changes how a filter travels. At the grand total there is no certification filter to travel, so DimTechnician is left alone and FactLabor answers with all eight rows: 62.0, with no guard and nothing to remember. One of these functions is a filter. The other is a route. Everything else follows from that.

Row values, either way
39.0, 10.5, 12.0, 23.5
Grand total, CROSSFILTER
62.0, no guard
Grand total, TREATAS
52.0, or 62.0 with ISFILTERED
Model change
None, either way
Why this and not that

CROSSFILTER needs a physical relationship in the right shape to modify. That single requirement decides which of the four situations in this chapter it can serve. Situation 1 has nothing to modify. TargetUtil is disconnected on purpose, and DimTechnician[HomeStation] is a descriptive text column sitting at neither end of any relationship. Situations 3 and 4 need a filter on a pair of columns, and on a column at a different grain from the one the relationship joins. CROSSFILTER can say which direction, and it has no way to say which values. Situation 2 is the only one of the four where both functions are genuinely available. There CROSSFILTER is the better default: it is shorter, it leaves no total to repair, and it sends the filter along a join the engine already built and indexed.

Reach for TREATAS on the bridge anyway in two cases. When you want the restricted total on purpose, because the visual is about certified staff and 52.0 is the honest number for it, which is the agreement Chapter 14 asks you to make before writing any of this. And when the bridge is loaded with no relationships at all, which is the third implementation in that chapter, since a relationship you have not created is not a relationship CROSSFILTER can modify.

The one line test. If the join already exists as a relationship and the only thing wrong with it is the direction, that is CROSSFILTER. If the join does not exist, cannot exist without creating ambiguity, or has to match on something other than the two columns of a relationship, that is TREATAS. Setting Both on the model itself is what you do when every measure needs the traversal, on every page, forever, and you have accepted the ambiguity risk on behalf of everyone who will ever open the file.

Situation 3: a composite key you do not want to build

The planner asks a fair question about the quarter. Meridian planned 176 hours and booked 62.0, so utilisation reads 35.2 percent, and she wants to know how much of that gap is stations that never opened a work order at all. To answer her you have to filter the plan down to the station and month pairs where labor actually happened. FactCapacity is grained at station plus month. FactLabor is grained at technician per work order per day, and it reaches a station only through FactWorkOrder. Nothing in the model matches those two tables on both parts of the key at once. The usual advice is to build a concatenated key column in Power Query on both sides, something like MSP-202501, and relate on that. It works. It also adds a column to two tables: a column whose only purpose is to be joined on, whose values mean nothing to a human, and which someone will eventually drop into a slicer.

TREATAS takes more than one column, so it can express the composite join without one existing.

DAXPlanned Hours Where Work Happened
Planned Hours Where Work Happened =
VAR ActivePairs =
    SUMMARIZE (
        FactLabor,
        DimStation[StationCode],
        DimDate[MonthKey]
    )
RETURN
    CALCULATE (
        [Planned Hours],
        TREATAS (
            ActivePairs,
            FactCapacity[StationCode],
            FactCapacity[MonthKey]
        )
    )
Line 2
A variable and not the expression written inline. Filter arguments evaluate in the outer filter context either way, so the result is identical, but the variable is evaluated once and carries a name that says what it holds.
Line 3
SUMMARIZE and not SELECTCOLUMNS. SELECTCOLUMNS would return one row per labor row, duplicates included, and TREATAS would then carry eight rows where five distinct pairs exist. SUMMARIZE groups. The advice to avoid SUMMARIZE applies to its extension column syntax, which evaluates in a context most people read wrongly. Used for grouping alone it is the shortest correct form, and DISTINCT ( SELECTCOLUMNS ( ... ) ) is equivalent here if you dislike it on principle.
Lines 5 and 6
Grouping columns reached from FactLabor across many to one relationships: FactLabor to FactWorkOrder to DimStation, and DimDate to FactLabor on WorkDate. SUMMARIZE can traverse those without RELATED, because it groups over the expanded table.
Lines 12 to 14
Two source columns, two target columns, in the same order. Station first because station is the first grouping column. Get this backwards and the measure returns blank, silently. That is the next section.

Five station and month pairs carry labor in Q1. Their planned hours add to 130 of the 176 hours in the plan: 30 plus 25 plus 25 plus 30 plus 20. The missing 46 is MSP in March at 30 planned hours with nothing booked against it, and PHX in March at 16 planned hours at a station that has never opened a work order.

That distinction changes what utilisation means, and it answers the planner's question. Against the full plan, Meridian ran at 62.0 divided by 176, which is 35.2 percent. Against only the station months where work was actually booked, it ran at 62.0 divided by 130, which is 47.7 percent. Both numbers are correct, and the gap between them is the 46 planned hours at stations that stayed quiet. Give her both, each one labelled. The second number exists only because the composite filter can be written without a composite key.

Performance note

A single column TREATAS over a low cardinality column is close to free: the engine can hand the value list to the storage engine as a filter on the column scan, which is roughly what a relationship filter compiles to anyway. A multi column TREATAS is a different shape of work, because a filter on a combination of columns cannot always be expressed as independent column filters and may be resolved as a table the formula engine has to build. On Meridian, at 8 labor rows and 28 capacity rows, none of this is measurable. On a real capacity fact with a few hundred thousand station and month pairs it is. Measure it before you trust any rule about it. Run it in DAX Studio with server timings on, and compare the formula engine share against a version built on a real key column.

Situation 4: plan against actual at different grain

Here is the production controller from the first page of this chapter, still holding his Monday. This is the Meridian capacity problem in its full form, and it is the one that sends people to TREATAS in the first place. DimDate[MonthStart] is related to FactCapacity[MonthStart]. That relationship behaves correctly at month grain, and it returns blank the moment the report filters to a day that is not the first of a month. Select 20 January on the date slicer and planned hours disappear while labor hours stay put, because L-504 booked 8.0 hours at TUS that day. Utilisation then reads as infinity or blank, depending on how the measure divides.

DAXUtilisation across the grain break
Planned Hours in Context =
VAR MonthsInContext = VALUES ( DimDate[MonthKey] )
RETURN
    CALCULATE (
        [Planned Hours],
        REMOVEFILTERS ( DimDate ),
        TREATAS (
            MonthsInContext,
            FactCapacity[MonthKey]
        )
    )

Utilisation =
    DIVIDE ( [Labor Hours], [Planned Hours in Context] )
Line 2
Every day in the selection maps to a month key, and VALUES collapses them to the distinct set. A single day returns one month key, so 20 January still reaches 202501.
Line 6
Without this line the whole measure is theatre. The day filter still travels the month grain relationship from DimDate into FactCapacity, finds no row with a MonthStart of 20 January, and leaves nothing for the TREATAS filter to intersect with. The result stays blank and the fix appears not to work. REMOVEFILTERS and not ALL: both clear the table when used as a filter modifier, and only one of them is named after what it is doing here.
Lines 7 to 10
The month keys are retagged onto the capacity fact's own MonthKey column, which is at the grain the plan is actually stored at. This is the join the physical relationship could not express.
Line 14
DIVIDE and not the slash operator. LAS has no capacity row in January or February and the UNASSIGNED member has none at all, so those combinations give a blank denominator, and DIVIDE returns blank there instead of an error. The slash operator returns infinity for a zero denominator in DAX, which then renders in a card visual and gets screenshotted into an email.

At month grain the numbers are the ones you already know. MSP in January is 22.5 over 30, which is 75.0 percent. TUS in January is 12.5 over 25, which is 50.0 percent. The quarter across all stations is 35.2 percent. Now the inconvenient part, and the production controller should hear it from you before he finds it himself. On 20 January, on the TUS row, this measure returns a denominator of 25. That is the whole month of TUS capacity, set against the 8.0 hours L-504 booked that day. It reports 32.0 percent utilisation for a single Monday. The ratio is arithmetically valid and semantically nonsense. TREATAS has given him a number where he had a blank, and the grain mismatch underneath it is exactly where it was. Allocating a monthly plan down to day level is a modelling decision with at least three defensible answers, and it is what Chapter 16 is about.

The alternatives, compared honestly

Seven ways exist to make a filter cross from one table to another. Two are relationships, one is a modifier that reaches into a relationship you already have, one is TREATAS, and three are older DAX patterns you will meet in inherited files.

Here is the certification measure in the two older forms, because you will open a file next quarter and find one of them.

DAXThe same join, written the old ways
// Pattern from roughly 2015. Still correct, still slower.
Hours by Cert (INTERSECT) =
VAR CertTechs = VALUES ( BridgeTechCert[TechnicianID] )
RETURN
    CALCULATE (
        [Labor Hours],
        INTERSECT (
            ALL ( DimTechnician[TechnicianID] ),
            CertTechs
        )
    )

// Older still, and the one worth rewriting on sight.
Hours by Cert (CONTAINS) =
VAR CertTechs = VALUES ( BridgeTechCert[TechnicianID] )
RETURN
    CALCULATE (
        [Labor Hours],
        FILTER (
            ALL ( DimTechnician[TechnicianID] ),
            CONTAINS (
                CertTechs,
                BridgeTechCert[TechnicianID],
                DimTechnician[TechnicianID]
            )
        )
    )
Why this and not that

All three return 39.0 for A&P. They differ in what the engine has to do to get there. TREATAS produces a filter, and a filter is something CALCULATE can hand down toward the storage engine, so for a single column the value list is applied during the scan. INTERSECT produces a table: the engine computes the common rows first, materialises them, and only then applies the result as a filter. FILTER plus CONTAINS is the expensive one, because FILTER iterates every technician id in the dimension and CONTAINS performs a lookup for each of them, all in the formula engine, one row at a time. Seven technicians costs nothing. Seventy thousand costs you a report that hangs. ALL and not REMOVEFILTERS in both older versions, incidentally, because those two functions do the same job only when used as a filter modifier. Here the result is consumed as a table, and REMOVEFILTERS does not return one.

The second argument for TREATAS is about reading, and it matters as much as the speed. Read the three measures again as English. The TREATAS version says: treat these bridge values as technician ids. The other two say: compute a set, then filter by whether something is in it. The first states the intent. The others state a procedure that implies the intent.

What TREATAS costs

Somebody in a design review will ask you what this costs, because TREATAS gets presented as free. Three of its costs are real, and you should be able to name all three from memory.

It runs on every query. A relationship is validated once at refresh and the structures that make traversing it fast persist. A virtual relationship is rebuilt from nothing every time a visual asks for the measure. Twelve visuals on a page means twelve rebuilds.

It gets no help from the relationship machinery. When a filter crosses a physical relationship the engine has already indexed how the two columns map, and the join is a lookup it prepared for. TREATAS gets none of that.

It scales with key cardinality. Meridian's technician key has seven values, so the value list is trivial. A part number key with three hundred thousand values produces a list with three hundred thousand entries, which has to be built, held in memory and matched. That is where a virtual relationship stops being a clever alternative to a physical one and becomes materially slower, sometimes by an order of magnitude.

Rule of thumb

If the join is permanent and the data supports it, build the relationship. Use TREATAS when the relationship should not be permanent: when it would create ambiguity, when it would need to be bidirectional, when the key is composite and you do not want the key column, or when the join is true for one measure and false for the rest of the model. Keep "I could not get the relationship to validate" off that list. That one is a data quality problem wearing a DAX costume, and it belongs in Power Query.

Two ways it fails silently

You ship the composite measure to the planner and she calls back within the hour. Every row of her utilisation table is blank. No error, no warning, nothing red anywhere on the screen. Two things cause that, and both of them keep quiet about it.

The first is data type. TREATAS matches on value, and a value carries a type. The text "202501" and the whole number 202501 look identical in a table visual, and to the engine they are two different values. Meridian walks straight into this. ShopCapacity[Month] arrives from the planning workbook as the text "2025-01", while DimDate[MonthKey] is a whole number like 202501. If the unpivot leaves the capacity month as text, the composite measure in situation 3 returns blank for every row. Fix it at the source.

MFactCapacity month key
// ShopCapacity[Month] arrives as text, for example "2025-01"
Table.AddColumn (
    Unpivoted,
    "MonthKey",
    each Number.FromText (
        Text.Replace ( [Month], "-", "" )
    ),
    Int64.Type
)
Lines 5 and 6
Number.FromText and not Value.FromText. Value.FromText inspects the content and decides what type to give you, which means one row can come back as a number and another as a date or as text. Number.FromText returns a number or it errors, and an error at refresh is worth far more to you than a silently mistyped column. Text.Replace and not Text.Remove: Text.Remove strips a list of characters wherever they appear, so it would also eat a hyphen that later shows up somewhere it matters. Replace names both what goes and what arrives.
Line 8
The fourth argument of Table.AddColumn declares the type at the point the column is created. Leave it out and the column is typed Any, which the model then resolves however it likes. This one argument is the difference between the join working and the join returning blank.

Equal-looking values of different types do not match. What varies is whether you are told: depending on which side holds which type, you may get a conversion error at authoring time or you may get an empty result and no message. Do not rely on getting the error.

The second silent failure is column order, and it costs people entire afternoons. TREATAS maps positionally. The first column of the table expression goes to the first column you named, and the second goes to the second. The names of the columns in the table expression are ignored completely. Swap the two target columns in the composite measure and you are comparing station codes against month keys, and month keys against station codes. Nothing matches. No error is raised, because you have asked a perfectly legal question that happens to have an empty answer. Once the types on the planner's table check out, this is the other place to look, and it is usually one of the two.

Common mistake

A composite TREATAS returns blank and everything looks right. Check the order before you check anything else. SUMMARIZE ( FactLabor, DimStation[StationCode], DimDate[MonthKey] ) produces station in position one and month in position two, so the targets must be FactCapacity[StationCode] then FactCapacity[MonthKey]. Write those two the other way round and the measure is blank everywhere, with no warning, no error and no red squiggle. The fastest way to confirm it is to drop the CALCULATE and evaluate the table expression on its own in DAX Studio. You then see which column genuinely comes first, in place of the one you assumed.

What to remember
  • TREATAS restamps the lineage of a table expression onto the columns you name, then CALCULATE filters those columns. Call it a lineage cast and the rest of its behaviour follows.
  • A dashed teal line drawn between two tables in this book means a virtual relationship: written in DAX, alive for one evaluation, absent from the model diagram. A dashed border around a table means something else entirely: that table was built inside the model rather than loaded from a source.
  • Four cases earn it. A join that would create ambiguity or force bidirectional filtering, a bridge you refuse to make bidirectional, a composite key you do not want to build, and plan against actual at different grain.
  • The choice is three ways. CROSSFILTER scopes a Both flag to one CALCULATE and is the better default on the bridge, because it needs no ISFILTERED guard: it moves no values, so an unfiltered grand total stays at 62.0 where the TREATAS version silently reports 52.0. It is available only where the relationship already exists, which rules it out of the other three situations.
  • Hours by certification comes out at 39.0, 10.5, 12.0 and 23.5 either way. TREATAS gets there with no model change, and the rows still sum to 85.0 against a true 62.0, because that double count belongs to the question.
  • It costs per query, gets no help from the engine's relationship structures, and scales with key cardinality. If the join is permanent and the data supports it, build the relationship instead.
  • Two silent failures: types that look equal but are not, and column order that does not line up. Both return blank with no error.
  • INTERSECT and FILTER plus CONTAINS do the same job by materialising or iterating. Recognise them in old code, and rewrite the CONTAINS one when you meet it.
