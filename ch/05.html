Part 2 . Shaping the data

05Power Query mechanics that matter for modelling

By the end of this chapter you will be able to predict the exact row count that comes out of every unpivot, append, merge and group in the Meridian load, and you will know which of those steps quietly changes the meaning of a number that is already on a report page.

The finance manager wants one number: what has the shop quoted this quarter. You put a card on the page and it reads 53,600. He has the quotes in front of him and says the figure is 38,100. Nothing in the report shows an error, and every work order looks correct when you drill into it. The card is still wrong by 15,500. A merge you built in the query editor last week is counting two work orders twice.

Most Power Query training is a tour of the ribbon. Your problem is narrower than that. A handful of these transformations change the grain of a table. Grain means what one row of a table stands for. One row of WorkOrders stands for one work order. One row of LaborEntries stands for the hours one technician booked on one day. Grain is the thing your model is built on, so get the grain wrong in the query editor and no amount of DAX will rescue the report.

This chapter works through the transformations that actually move the model: unpivot, append, merge and its six join kinds, expand versus aggregate, group by, and the query dependency choices that decide how often your source gets hit. Each one is also argued against its DAX equivalent. Most of them have one, and it usually returns the same number, which is exactly what makes the choice look optional. Every example runs on Meridian rows. Every row count is one you can check by hand against the source tables.

Unpivot: turning column headers back into data

The planner keeps ShopCapacity in a workbook and edits it by hand every month. She asks for a chart of planned hours by trade, which sounds like five minutes of work. In her workbook the trades are column headings, and a column heading cannot go on the axis of a chart. One step in the query editor turns those headings into data she can slice.

ShopCapacity arrives from the monthly planning workbook as a matrix. Someone in planning built it to be read by a human, so the trades run across the top.

Airframe, Avionics, Engine and NDT are four values of one attribute called Trade. The numbers under them are all the same measurement, planned hours. A model can only slice by a column, and here Trade is spread across four column names. No relationship can point at a column header either. Unpivot fixes both problems in one step.

MFactCapacity, the version that survives change
let
    Source = ShopCapacity,
    Unpivoted = Table.UnpivotOtherColumns(
        Source, {"StationCode", "Month"},
        "Attribute", "Value"),
    Renamed = Table.RenameColumns(Unpivoted, {
        {"Attribute", "Trade"},
        {"Value", "PlannedHours"}}),
    Typed = Table.TransformColumnTypes(Renamed, {
        {"Trade", type text},
        {"PlannedHours", Int64.Type}})
in
    Typed
Line 3
Table.UnpivotOtherColumns takes the list of columns to keep. Everything you leave out of that list gets folded down into two new columns. Read that twice. You name the survivors, and the ribbon label suggests the opposite.
Line 5
The two literals name the output columns. The generated names are always Attribute and Value when you use the ribbon, which is why the next step exists.
Line 6
Rename immediately. Attribute becomes Trade because a column called Attribute tells a report reader nothing, and because a field list full of Attribute columns from four different queries is unusable.
Line 9
Type immediately. Unpivot returns Value as type any. An untyped numeric column will still sum, but it stores as a variant, compresses badly, and any implicit measure you build on it can silently become a text count.

Now the ribbon. The Transform tab offers three commands and their names do not map to the generated functions the way you would expect. Read the formula bar after every unpivot, because the formula bar is the only honest description of what you did.

Unpivot Only Selected Columns generates Table.Unpivot with the four trade names written into the step as a literal list. Unpivot Columns and Unpivot Other Columns both generate Table.UnpivotOtherColumns. They differ only in which columns you had highlighted when you clicked. So the practical test is the function name in the formula bar. Read that, and ignore the menu label you clicked to get there.

MThe hard coded variant, from Unpivot Only Selected Columns
let
    Source = ShopCapacity,
    Unpivoted = Table.Unpivot(
        Source,
        {"Airframe", "Avionics", "Engine", "NDT"},
        "Attribute", "Value")
in
    Unpivoted
Line 5
The trade list is frozen into the query. Today it produces the same 28 rows as the other version. Next month, when planning adds a Structures column to the workbook, this step unpivots the same four trades and carries Structures through as a fifth, still wide, column that nothing in the model reads.
Failure mode
No error, no warning. Planned capacity is understated and the utilisation measure quietly goes up, because the denominator lost hours.

The anchored version behaves the other way. Table.UnpivotOtherColumns names StationCode and Month. Those two are the grain keys, and they are the columns least likely to change. A new Structures column is absent from that list, so it gets unpivoted along with everything else and arrives as a new Trade value on the next refresh. That is why anchoring on keys is the default. You name the stable columns and let everything else flow through. The rule is short. Select the two key columns, use Unpivot Other Columns, and confirm the formula bar reads Table.UnpivotOtherColumns before you move on.

Common mistake

Assuming the auto-generated Changed Type step above the unpivot will catch a source change. It will stay silent and it will keep working. Table.TransformColumnTypes only touches the columns it names. When planning adds Structures, that step ignores it and passes it through as type any. Pair that with Unpivot Only Selected Columns and the refresh succeeds, the query still reports 176 planned hours, and an entire trade is missing from the model. A Changed Type step does fail loudly when a column it names is renamed or removed at source. A column being added is the quiet case. Type after the unpivot instead, on the two columns the unpivot creates, exactly as the query above does.

What the same unpivot costs in DAX

DAX has no unpivot. No function takes a table and a list of columns and returns a longer table. The equivalent is a calculated table that stacks four separately shaped queries on top of each other. It looks like this, and it is the whole reason the transformation belongs upstream.

DAXFactCapacity as a calculated table, do not ship this
FactCapacityDAX =
UNION (
    SELECTCOLUMNS ( ShopCapacity,
        "StationCode", ShopCapacity[StationCode],
        "Month", ShopCapacity[Month],
        "Trade", "Airframe",
        "PlannedHours", ShopCapacity[Airframe] ),
    SELECTCOLUMNS ( ShopCapacity,
        "StationCode", ShopCapacity[StationCode],
        "Month", ShopCapacity[Month],
        "Trade", "Avionics",
        "PlannedHours", ShopCapacity[Avionics] ),
    SELECTCOLUMNS ( ShopCapacity,
        "StationCode", ShopCapacity[StationCode],
        "Month", ShopCapacity[Month],
        "Trade", "Engine",
        "PlannedHours", ShopCapacity[Engine] ),
    SELECTCOLUMNS ( ShopCapacity,
        "StationCode", ShopCapacity[StationCode],
        "Month", ShopCapacity[Month],
        "Trade", "NDT",
        "PlannedHours", ShopCapacity[NDT] )
)
Why this and not that

SELECTCOLUMNS and not ADDCOLUMNS, because ADDCOLUMNS returns every column of the source table plus the ones you add. Each of the four blocks would still carry Airframe, Avionics, Engine and NDT alongside the new Trade column. The union would then produce a table that is long and wide at the same time, with the original matrix still embedded in it. SELECTCOLUMNS returns only the four columns you name, which is the shape a fact table needs.

UNION and not one of the join functions, because there is no key to join on here. You are stacking rows, and the join functions match rows. The cost is that UNION pairs its inputs by column position. Column names are ignored entirely. If a colleague edits the third block and swaps the Month and Trade lines, the engine stays quiet. Month values land in the Trade column, the visual still renders, and station months appear as trade names. Column order is load bearing and nothing checks it.

The deeper objection stands regardless of which functions you pick: the trade list is written four times in the expression. Adding Structures means editing this DAX, republishing, and remembering to do it. The Power Query version needs nothing. That is a maintenance cost you pay forever in exchange for saving one step in the query editor now.

Append versus merge, and why the difference changes your row count

The production controller wants a station slicer on every page, PHX included. You look for a station list and there is no such table. Station codes are scattered across three sources, and PHX appears in only one of them. Building that slicer means stacking three lists on top of each other and keeping one row of each station, which is what append does.

Append
Stacks tables vertically. Rows out equals the sum of rows in. Columns are matched by name. A column present in one input and absent in another produces nulls for the rows that did not have it.
Merge
Joins tables horizontally on one or more key columns. Columns out is the sum of the columns; rows out depends entirely on the join kind and on how many matches each key finds.

The name matching in append is where people get hurt. There is no positional fallback and no warning. Rename StationCode to Station in one of the three inputs and the append succeeds, produces two columns instead of one, and fills each with nulls for the rows that came from the other side. A table visual will show a longer list of stations with a blank in it and nothing will look obviously broken.

Meridian needs an appended station dimension because station codes are scattered across three sources and no single source has all of them. WorkOrders knows about MSP, TUS and LAS, and has one blank. Technicians knows about MSP, TUS and LAS through HomeStation. ShopCapacity is the only place PHX exists at all.

MDimStation, built by append
let
    FromWO = Table.SelectColumns(
        WorkOrders, {"StationCode"}),
    FromTech = Table.RenameColumns(
        Table.SelectColumns(Technicians, {"HomeStation"}),
        {{"HomeStation", "StationCode"}}),
    FromCap = Table.SelectColumns(
        ShopCapacity, {"StationCode"}),
    Stacked = Table.Combine({FromWO, FromTech, FromCap}),
    Deduped = Table.Distinct(Stacked),
    NoBlank = Table.SelectRows(Deduped, each
        [StationCode] <> null
        and [StationCode] <> ""),
    WithUnassigned = Table.Combine({NoBlank,
        #table({"StationCode"}, {{"UNASSIGNED"}})})
in
    WithUnassigned
Lines 4 to 6
The rename is the entire append. Without it, Table.Combine returns a two column table and the six technician rows carry null in StationCode. This is the silent failure described above, reproduced deliberately so you can see how small the fix is.
Line 9
Table.Combine is what the Append Queries button generates. It takes a list of tables, so appending a fourth source later is one more entry in the braces.
Lines 12 to 13
Both tests are needed. A missing station arrives as null from a database and as an empty string from a text or Excel export, and the two are not equal in M.
Line 15
The #table constructor builds a one row table inline, so the Unassigned member is created inside the query itself. There is no separate file for somebody to maintain and forget.

Note what happens in the last two rows. Removing the blank is correct, because an empty key describes nothing. It is missing data, and it belongs out of the dimension. Removing it on its own leaves WO-1005 with a station code that matches no dimension row. A row like that is an orphan: a fact whose key finds nothing on the other side of the relationship. Power BI parks orphans in an automatic blank row where nobody thinks to filter. So add Dimension UNASSIGNED. The append is only finished when the orphan has a named home.

That is the production controller's slicer. Five stations, PHX among them, and WO-1005 sitting under UNASSIGNED where he can see it.

What the same append costs in DAX

DAX can stack tables. UNION takes two or more tables and returns their rows one after another. That is the append operation wearing a different name. You can build the same five row dimension as a calculated table without much effort.

DAXDimStation as a calculated table, the version to argue against
DimStationDAX =
VAR Stacked =
    UNION (
        SELECTCOLUMNS ( WorkOrders,
            "StationCode", WorkOrders[StationCode] ),
        SELECTCOLUMNS ( Technicians,
            "StationCode", Technicians[HomeStation] ),
        SELECTCOLUMNS ( ShopCapacity,
            "StationCode", ShopCapacity[StationCode] )
    )
VAR Cleaned =
    FILTER (
        DISTINCT ( Stacked ),
        NOT ISBLANK ( [StationCode] )
            && [StationCode] <> ""
    )
RETURN
    UNION ( Cleaned, ROW ( "StationCode", "UNASSIGNED" ) )
Stacked
21 rows, 8 plus 6 plus 7, exactly the count in Table 05.3. UNION does not deduplicate, so this intermediate holds every repeat of MSP from all three sources and the DISTINCT below is not optional.
SELECTCOLUMNS
Does the job Table.RenameColumns does in the M version, giving the technician column the name StationCode. Note the reversal, though. In M the rename is load bearing, because append matches by name. In DAX it is cosmetic, because UNION matches by position and takes its output names from the first table. The danger moved from one place to the other, and it is still in the room.
Cleaned
DISTINCT takes 21 down to 5, the four real stations plus the blank from WO-1005, and the filter takes it to 4. Both tests are still needed, for the same reason as in M: a missing station arrives as blank from a database and as an empty string from a spreadsheet.
RETURN
A second UNION adds the Unassigned member and the table lands at 5 rows, the same 5 the query editor produced. The numbers agree at every step. That is exactly why the numbers cannot decide this one for you.
Why this and not that

DISTINCT and not VALUES. On a table expression the two look interchangeable. VALUES can also return an extra blank row, and it does so when its table sits on the one side of a relationship that has unmatched values pointing at it. A dimension that quietly grows a phantom member on some future refresh is the exact failure this build exists to prevent.

ROW and not DATATABLE. DATATABLE makes you declare a type for every column and accepts only constants, which is a lot of syntax for one station code. ROW builds the one row table inline, and it is the closest thing DAX has to the #table constructor on line 15 of the M version.

The functions do their job. The problem is what a calculated table drags into the model behind it. DAX can only read tables that are already in the model, so WorkOrders, Technicians and ShopCapacity all have to be loaded, in full, purely to feed a five row dimension. That is 8 plus 6 plus 7 rows of raw source sitting in the field list beside the model you designed on purpose. In Power Query the same three inputs are queries with Enable Load switched off. They exist in the editor and they never become tables. That matters well beyond tidiness. Every loaded table is a table a report author can drag onto a page. A raw WorkOrders table sitting next to FactWorkOrder is how a report ends up with two work order counts that disagree, and nobody able to say which one is real.

Three more costs follow from that. The calculated table is rebuilt on every refresh, so the 21 row stack and the distinct are re-evaluated whether or not a station was added. It also cannot fold. Folding is Power Query translating your steps into a native query that the source runs on your behalf, and it is the biggest refresh lever you have. Without it, the distinct runs inside the model while the database that holds an index on that very column is never asked. The third cost is that no Power Query step can reference a calculated table. The first time you need to merge a station description onto DimStation, you have to move the whole build upstream anyway, and you write the M version you skipped.

The recommendation here is one sided, and it should be. Append in Power Query. The DAX version is worth writing exactly once, in a DAX query window. Write it on the day you want to prove to yourself that the station list really does come to five members, before you trust the query editor to have done it.

The six join kinds, with the exact Meridian counts

The production controller asks how many work orders are on the board for each aircraft. You merge the work orders to the fleet registry, put a card on the page, and it reads seven. He counts eight on his whiteboard. One work order fell out of the join on its way to the report. Which one fell out, and whether anything fell out at all, is decided entirely by the join kind you picked from a dropdown.

Merge is Table.NestedJoin. It puts a nested table into a new column on the left table. You then decide whether to expand that column or aggregate it. The join kind decides which rows survive to that point, and the six kinds behave differently enough that guessing is not viable. Take WorkOrders as the left table and AircraftRegistry as the right, joining on ACREG. Eight work orders sit across five distinct tails. The registry holds six rows. N338WA on WO-1006 is in the work orders and missing from the registry. N120CE and N553KD are in the registry with no work orders against them.

Left outer keeps all 8 work orders and gives WO-1006 an empty nested table. Inner drops WO-1006 and returns 7. Right outer keeps every registry row: the 7 work orders that match a tail, plus N120CE and N553KD carried in with null work order columns, so 7 plus 2 equals 9 rows. Full outer keeps everything on both sides: all 8 work orders plus the same 2 registry-only tails, so 8 plus 2 equals 10 rows. Left anti returns only the left rows with no match, which is WO-1006 alone. Right anti returns only the unmatched right rows, N120CE and N553KD.

Join kind reference, all six against WorkOrders and AircraftRegistry

Right outer and full outer differ by exactly one row here, and the row is WO-1006. That is worth sitting with: right outer silently discards the very work order you are usually looking for, because WO-1006 has no registry match and right outer only guarantees the right side.

Left anti is the join you should reach for most often, and it is the one people use least. It answers the question you actually have: which keys will fall into the blank row. Run it before you build any relationship.

MOrphan diagnostic, one row: WO-1006
let
    Orphans = Table.NestedJoin(
        WorkOrders, {"ACREG"},
        AircraftRegistry, {"ACREG"},
        "Registry", JoinKind.LeftAnti),
    Kept = Table.SelectColumns(Orphans,
        {"WorkOrderID", "ACREG", "StationCode"})
in
    Kept
Line 5
The nested column is created and then thrown away, because in an anti join it is always empty. The join kind is doing all the work.
Result
One row: WO-1006, N338WA, MSP. That is the production controller's eighth work order, and it fell out because tail N338WA never made it into the registry. It is also 12.0 labor hours that would otherwise sit in a blank aircraft type, and it is the whole reason DimAircraft gets built in the query editor instead of loaded straight from the registry.
Keep it loaded
Set this query to load. Put it on a hidden diagnostic page as a table visual, with a card counting its rows. You then find out on the refresh that introduces a new orphan, rather than in a meeting.

One word on fuzzy matching. Merge offers it. It uses a similarity threshold to pair values that are close, and it will happily match TECH-04 to TECH-05 if you loosen the threshold enough. Keep it away from keys. A key match is a yes or no question, and fuzzy matching turns it into a probability that shifts as the data shifts. The same query can then return different join results next month with no code change at all. Fuzzy matching earns its place cleaning free text categories that a human typed, once, under supervision, with the match table exported and reviewed.

What the same merge costs in DAX

DAX has two join functions, NATURALINNERJOIN and NATURALLEFTOUTERJOIN. That is two of the six kinds in Table 05.4. There is no right outer, no full outer, and neither anti join, so the four kinds DAX does not have include the one you should be reaching for most often.

DAXThe left outer join, in DAX
WOWithAircraft =
NATURALLEFTOUTERJOIN ( WorkOrders, AircraftRegistry )
What it returns
When it works, 8 rows, with WO-1006 carrying blanks in every registry column. The same shape and the same count as JoinKind.LeftOuter.
The join columns
You do not name them, and there is no argument where you could. The function joins on every column the two tables have in common by name. Today that is ACREG and nothing else. The day the fleet spreadsheet gains a StationCode column, this becomes a two column join, the row count changes, and not one character of the expression was edited.
The lineage trap
The two ACREG columns belong to two different base tables. The engine treats them as different columns despite the identical name. The expression then raises an error saying there are no common join columns, rather than joining. Breaking the lineage on one side first is the usual workaround. Having to explain that last sentence to whoever inherits the file is itself an argument for doing the join in the query editor, where you pick the two columns by clicking them.

The anti joins have no direct equivalent at all. The nearest thing works only on the keys.

DAXThe nearest thing to a left anti join
OrphanTails =
EXCEPT (
    VALUES ( WorkOrders[ACREG] ),
    VALUES ( AircraftRegistry[ACREG] )
)
Result
One row, N338WA. Correct as far as it goes: five distinct tails appear in WorkOrders and four of them are in the registry. Reverse the two arguments and you get the right anti answer, N120CE and N553KD, two rows.
What is missing
You get back an aircraft registration and nothing else. The Power Query version returned WO-1006, N338WA, MSP, which is a row somebody can act on without a second lookup. To get that back you write FILTER ( WorkOrders, NOT ( WorkOrders[ACREG] IN VALUES ( AircraftRegistry[ACREG] ) ) ), which is perfectly good code and honestly no worse than the M version for a check you never ship.

So here is the split. For a throwaway check in the DAX query view, either tool is fine and the DAX one is faster to type. For anything the model depends on, merge in Power Query. You get all six join kinds by name from a dropdown. The join can fold into a single native JOIN at the source. And what you leave behind is a query the next person can step through, one applied step at a time.

And for the ordinary case, which is wanting an attribute from a dimension to appear beside a fact, do neither. Build the relationship and let filter context carry the attribute at query time. That costs no refresh time, no memory and no maintenance, and it is the reason the Meridian model relates DimAircraft to FactWorkOrder rather than merging the registry into the work orders. The merge is for building the dimension. The relationship is for using it.

Expand versus aggregate, and the row multiplication trap

This is where the finance manager's 53,600 came from. After a merge you have a nested column and two ways to open it. Expand puts every nested row on its own output row. Aggregate collapses the nested table to one value per left row. Both look like formatting choices in a dropdown. Both change the grain of the table, and grain decides whether the totals on his card are right.

This is the picture from chapter 01, and expand is the operation it was warning about. The box on the left, headed Header grain, holds three work orders with their quoted amounts. The box on the right, headed Line grain, holds the five labor lines that belong to them. The figure labels the two boxes with their model names, FactWorkOrder and FactLabor. Those are the tables this chapter is still calling WorkOrders and LaborEntries. Each curve running between the two boxes is one header row about to be read a second time, which is what the annotation on the curves says: one header row fans out to many line rows.

Then read the red card. Pulling QuotedAmount down to line grain gives the sum it prints: 3,000 plus 3,000 plus 3,200 plus 12,500 plus 12,500, which is 34,200 against a true 18,700 for those three work orders. The 15,500 gap is WO-1001 and WO-1003 counted twice, and it is the same 15,500 that turns up in the full eight row version below. The card names a second and independent error underneath that one. Work orders with no labor line vanish entirely, which is what an inner join does here. The green card opposite shows the shape that avoids both errors. Quoted Amount is summed on FactWorkOrder for 38,100. Labor Cost is summed over FactLabor for 6,326.50. The two meet at the visual, and neither one is written into a column.

The wrong way

Merge WorkOrders to LaborEntries on WorkOrderID with a left outer join, then expand LaborID and Hours.

MExpand
    Merged = Table.NestedJoin(
        WorkOrders, {"WorkOrderID"},
        LaborEntries, {"WorkOrderID"},
        "Labor", JoinKind.LeftOuter),
    Expanded = Table.ExpandTableColumn(
        Merged, "Labor",
        {"LaborID", "Hours"},
        {"LaborID", "Hours"})

The table is now at labor line grain but every row still carries the header's QuotedAmount. Eight header rows became ten. Two work orders got their quoted amount written twice.

The fix

Same merge, but aggregate the nested column instead of expanding it.

MAggregate
    Merged = Table.NestedJoin(
        WorkOrders, {"WorkOrderID"},
        LaborEntries, {"WorkOrderID"},
        "Labor", JoinKind.LeftOuter),
    Rolled = Table.AggregateTableColumn(
        Merged, "Labor",
        {{"Hours", List.Sum, "LaborHours"}})

Still 8 rows, one per work order, with LaborHours alongside QuotedAmount: 13.5, 9.0, 12.5, 10.0, null, 12.0, 5.0, null. Quoted total stays 38,100 and hours total 62.0. Better still, do neither, and load both tables as separate Fact tables joined by a relationship on WorkOrderID.

What you see in the report

A card called Total Quoted reads 53,600 instead of 38,100. Nothing errors. The number is 15,500 too high, which is 40.7 percent. It is wrong in a way nobody can see unless they already know the true figure. Drill into any individual work order and it looks correct.

Here is the arithmetic in full, because the double count is not evenly spread and the size of the error depends on which work orders happen to have multiple labor lines.

Read the two totals columns against each other. The true quoted total is 38,100. After expansion the sum is 53,600. The difference is 15,500, which is exactly the 3,000 of WO-1001 counted a second time plus the 12,500 of WO-1003 counted a second time. That is the finance manager's card, and now you can tell him where the money went. WO-1005 and WO-1008 have no labor rows at all, so a left outer join keeps them as a single row each with null hours. That is why 8 labor lines plus 2 header-only rows give 10 output rows. An inner join would have returned 8 rows and dropped those two work orders entirely, which trades one wrong number for a different wrong number.

Performance note

Be precise about the cost, because the folding story is not the simple one. A merge and expand between two tables that live in the same SQL database usually does fold, into a single JOIN, and that is fine. It stops folding when the two sides come from different connectors, and then the mashup engine pulls both tables down and joins them locally on the gateway machine. Either way the expand multiplies rows before any filter is applied. On eight Meridian rows nobody notices. On a labor table with two million lines, writing the header columns onto every line inflates the dataset by the width of the header. You pay for that twice: once in refresh time and again in model size. Aggregate at the source grain, or keep the tables separate and let the relationship do the work at query time.

Group By, and what it silently drops

The shift supervisor wants a list of work orders with the hours booked against each one. You group LaborEntries by work order, put the result on a page, and eight work orders come out as six. WO-1005 and WO-1008 are gone. Those are the two with nobody booked to them at all, and WO-1008 is still open, so they are the two he was looking hardest for.

Group By is the tool for changing grain on purpose. Rolling LaborEntries from technician-day grain up to work order grain is one step.

MLaborEntries rolled to work order grain
let
    Trimmed = Table.TransformColumns(LaborEntries, {
        {"TechnicianID", Text.Trim, type text}}),
    Grouped = Table.Group(Trimmed, {"WorkOrderID"}, {
        {"LaborHours", each List.Sum([Hours]),
            type number},
        {"LineCount", each Table.RowCount(_),
            Int64.Type}})
in
    Grouped
Line 4
The second argument is the list of grouping keys. Basic grouping in the dialog allows one key and one aggregation, and writes exactly this function with a shorter list. Advanced grouping adds keys and aggregations to the same two lists. Basic and Advanced behave identically. They differ only in how much of Table.Group the dialog lets you fill in, so start in Advanced and save yourself the reopen.
Line 5
List.Sum reads a column out of the group and sums it. Inside the aggregation, [Hours] resolves to a list of values, which is why the function that reads it is List.Sum.
Line 7
The underscore is the whole group as a table, so Table.RowCount counts labor lines. Carrying a line count alongside every rolled-up sum costs nothing and makes fan-out visible the moment it appears.

WO-1005 and WO-1008 are missing from that table. Group By can only return groups that have at least one row. A work order with no labor booked to it has no rows to group, so it is absent from the output. There is no zero in there to find. Use this grouped query as your work order list and the count drops from 8 to 6, with the open work orders the first to go. That is the shift supervisor's two missing jobs. The correct pattern is to group the fact and then merge the result back onto the full WorkOrders list with a left outer join. The two missing work orders come back carrying null hours, and a measure turns null into zero on the page.

The dialog also offers All Rows as an aggregation. It generates each _ and keeps the entire group as a nested table in a column. That is useful when you need to sort within a group or take the first row per key. Treat it as a scalpel. Every nested table is materialised in memory during evaluation, and the step almost never folds. On a large fact table an All Rows group can turn a query that used to stream into one that tries to hold the whole dataset at once. If you use it, add the step that removes the nested column as soon as you are finished with it.

What the same group costs in DAX

This is the transformation where DAX puts up the best fight, so it is worth being exact about which parts it wins. SUMMARIZE produces the same table Table 05.6 shows.

DAXThe same group, in DAX
LaborByWO =
SUMMARIZE (
    FactLabor,
    FactLabor[WorkOrderID],
    "LaborHours", SUM ( FactLabor[Hours] ),
    "LineCount", COUNTROWS ( FactLabor )
)
Result
Six rows and 62.0 hours, identical to the M version, and WO-1005 and WO-1008 are missing here too. The trap belongs to grouping itself, in either language. A group needs at least one row to be a group.
The shape
Aggregations written directly inside SUMMARIZE read plainly and behave on eight rows. On a large fact table the pattern to prefer is ADDCOLUMNS wrapped around a bare SUMMARIZE. Aggregation expressions placed inside SUMMARIZE itself are evaluated in a context the engine finds harder to optimise.

Now the part where DAX is genuinely the better tool. The two missing work orders are easy to recover in DAX and awkward to recover in M. Iterate the header table instead of the fact table and all eight come back.

DAXEight rows, including the two with no labor
LaborByWOAll =
ADDCOLUMNS (
    VALUES ( FactWorkOrder[WorkOrderID] ),
    "LaborHours",
        COALESCE ( CALCULATE (
            SUM ( FactLabor[Hours] ) ), 0 )
)
VALUES over the header
Eight work orders in, eight rows out. WO-1005 and WO-1008 arrive carrying 0.0, and the total is still 62.0. In Power Query the same fix needs a second query and a left outer merge of the grouped result back onto the full header list.
CALCULATE
Context transition. It converts the current WorkOrderID row of the iteration into a filter on FactLabor, which is what makes the sum specific to that work order. Leave it out and every row prints 62.0.
COALESCE
COALESCE and not adding zero. Both turn the blank into 0.0 for the two work orders with no labor rows, and only one of them says so in the formula where the next reader will see it.

DAX wins the readability of that one fix, and loses everything around it. Three things decide it. Grouping in Power Query folds, so against a real source the GROUP BY is executed by the database and only the grouped rows cross the network. On a timesheet table of two million lines that is the difference between two million rows arriving and a few thousand. Grouping in DAX cannot fold. It cannot even start until the whole fact table is already in the model, so you have paid the cost the grouping was supposed to avoid. Third, the grouped table is stored and rebuilt on every refresh, whether or not any visual reads it.

Then the question that gets skipped. Why is this a stored table at all. Put WorkOrderID on the rows of a visual and a Labor Hours measure in the values. The engine groups at query time for nothing. There is no table to refresh and no second copy of the hours to reconcile with the first. So the recommendation has two branches and both are firm. If you only need the grouped number on a page, write the measure and group nowhere. If you need the grouped result as a physical column, because a relationship, a slicer, a sort order or a security filter has to point at it, group in Power Query. It folds there, and the next analyst can read it step by step. Grouping into a stored DAX table pays the cost of materialising and collects none of the benefit of folding.

Reference versus Duplicate, and how often your source gets read

The planner's refresh now runs longer than the slot she has before her scheduling meeting. You open the trace to find out why, and the shop floor work order table is read three times in a single refresh. You only ever wrote one query against it. Three other queries reference that one, and reference turns out to mean something different from what you assumed.

Right clicking a query gives you both options. They do different things, and the difference shows up months later. Duplicate copies the M text. You get a second independent query with its own copy of every step, and from that moment the two drift. Fix a type conversion in one and the other keeps the old behaviour, forever, silently. Reference creates a query whose entire body is = WorkOrdersSource, pointing at the output of the first query. A fix in the source query lands in every referencing query on the next refresh.

The staging pattern follows from that. Build one query per physical source that does connection, promotion of headers, typing and the cleaning that everything downstream needs. Turn Enable Load off on it, so it exists in the query editor but produces no table in the model. Then reference it once per model table you need to build from it.

  1. Create WorkOrdersSource: connect, promote headers, trim keys, set types. Enable Load off.
  2. Reference it as FactWorkOrder: map the blank station on WO-1005 to UNASSIGNED, keep the eight fact columns, load.
  3. Reference it again for the station list that feeds Built DimStation: select StationCode, distinct. Enable Load off, because it is one of three inputs to the append.
  4. Reference it a third time for the distinct tail list that feeds DimAircraft.

Now the part that surprises people, and it is the planner's three reads. Reference does not cache. A referenced query is a definition that gets evaluated again, so when three queries reference WorkOrdersSource the mashup engine is free to run that definition once per consumer. Against a file, the file is opened more than once. Against a database, the query is sent more than once. That is why a colleague swears the staging query hits the source twice and the trace log agrees with them. Power Query does have persistent caching for some connectors and some evaluation paths, so this will not happen on every refresh. What is guaranteed is that you cannot rely on it not happening.

Performance note

Table.Buffer is the usual suggestion at this point, and it does less than people think it does. It materialises a table for the length of one evaluation, so it helps when a single query would otherwise walk the same step twice. Its effect ends with that evaluation. Each referencing query runs its own evaluation of the staging query, buffer step included, so three references can still mean three reads of the source. What buffering does do reliably is end query folding at that point, so every step after it runs in the mashup engine instead of at the source. On the Meridian volumes that is free and pointless. On a folded SQL source it can turn a two second refresh into a two minute one. If the repeated read is the real cost, the fix is upstream: a view, a dataflow, or a staged table that the model reads once.

Why this one has no DAX version at all

The other transformations in this chapter have a DAX equivalent that is worse. This one has no DAX equivalent. There is no way to write a calculated table that means "the output of that other query, without the loading", because both halves of that sentence are things DAX does not have.

The two closest analogues are both the wrong half of the choice you just made. Copying an expression into a second calculated table is Duplicate, with exactly the drift described above. Correct a filter in one and the other quietly goes on being wrong. Building a calculated table on top of another calculated table is Reference, and it is worse than the M version, because it chains process recalc dependencies. The engine has to finish the first table before it can begin the second, on every refresh and on every model change. The chain is invisible unless you go looking for it.

The piece that is simply absent is Enable Load. Every calculated table is in the model: stored, refreshed, and visible in the field list unless somebody remembers to hide it. The staging pattern above depends on the opposite of that. WorkOrdersSource exists so that three other queries can reference it, and it produces no table. The three inputs to the DimStation append exist so the append has something to stack, and 8 plus 6 plus 7 raw rows never reach the model. DAX cannot express any of that, because in DAX a table is the only unit there is and every unit is loaded.

The recommendation is short because there is nothing to weigh. Stage in Power Query, reference rather than duplicate, and turn Enable Load off on every query whose only job is to feed another query. If a staging query being evaluated more than once turns out to cost real refresh time, fix it upstream with a view or a dataflow that the model reads once. That is what the planner needs. A calculated table downstream reads the same source and then keeps a copy of it, which adds a second problem to the first.

Splitting Certifications into a bridge

Technicians[Certifications] holds multiple values in one cell, delimited by a semicolon and a space. Split Column by Delimiter, with rows chosen as the output, is the step that turns it into a bridge table. A bridge table is a two column table that records which technicians hold which certifications, one pair per row, so a relationship can be built on each side of it. Choosing columns instead would give you Cert1, Cert2, Cert3 and reproduce the unpivot problem you just solved.

MBridgeTechCert, 10 rows out of 6
let
    Kept = Table.SelectColumns(Technicians,
        {"TechnicianID", "Certifications"}),
    ToList = Table.TransformColumns(Kept, {
        {"Certifications",
         Splitter.SplitTextByDelimiter("; ",
             QuoteStyle.Csv),
         type {text}}}),
    Split = Table.ExpandListColumn(ToList,
        "Certifications"),
    Renamed = Table.RenameColumns(Split, {
        {"Certifications", "CertCode"}}),
    Typed = Table.TransformColumnTypes(Renamed, {
        {"CertCode", type text}})
in
    Typed
Lines 4 to 8
The splitter turns each text value into a list. The ribbon writes a longer type ascription with metadata attached; it does the same work, and the shorter form above is easier to read in a review.
Line 9
Table.ExpandListColumn is the step that multiplies rows. Six technicians become ten, and this is the one place in the whole load where multiplying rows is exactly what you want.
Delimiter
Split on "; " and not on ";", otherwise every second value arrives with a leading space and NDT will not equal " NDT" when you join it to DimCertification.

Drop Certifications from DimTechnician once the bridge exists. Leaving both means two ways to answer the same question, and the delimited version will keep appearing in report visuals because it is easier to find in the field list.

Types, locale and column names

Set types early, in the staging query, right after headers are promoted. Two reasons, and the second one matters more. First, an untyped column is stored as a variant, and every downstream comparison has to work out what it is holding. Second, type conversion is where bad data announces itself. You want that announcement in a query whose only job is loading. Step 14 of a query that also does business logic is a miserable place to discover it.

The typing step names every column, which is what makes it brittle. The Changed Type step Power Query adds automatically on first connection lists all eight WorkOrders columns. Rename QuotedAmount to QuoteValue at the source and the refresh fails with a column not found error. That failure is loud, so it is the good case. Keep the automatic Changed Type step narrow: type the columns you depend on, and let the rest arrive as they are.

MTyping with an explicit culture
    Typed = Table.TransformColumnTypes(WorkOrders, {
        {"OpenedDate", type date},
        {"PromisedDate", type date},
        {"ClosedDate", type date},
        {"QuotedAmount", Int64.Type}}, "en-US")
Line 5
The third argument is the culture used to parse text into dates and numbers. Without it, the parse uses the locale of whoever opened the file, which means the same query can produce different dates on your desktop and on the gateway.
Why it matters here
Meridian dates arrive as 2025-03-06, which is unambiguous, so this file is safe. The moment the shop floor export changes to 03/06/2025 it stops being safe, and nothing in Power Query will tell you the meaning changed.
Common mistake

Take WO-1007: opened 2025-03-03, closed 2025-03-06, a turn time of 3 days. If the export switches to 03/06/2025 and the gateway parses under en-GB, that closed date becomes 3 June 2025 and the turn time becomes 92 days. The average turn time across the six closed work orders moves from 72 divided by 6, which is 12.0 days, to 161 divided by 6, which is 26.8 days. Every row still looks like a valid date. The fix is to state the culture in the step and to ask the source system for ISO dates, in that order.

Trim, Clean, and the space that survives both

L-505 carries "TECH-04 " with a trailing space. In any table visual it is indistinguishable from TECH-04, it will not match on the relationship, and 4.5 hours end up in the blank technician row while TECH-04 shows 6.0 instead of 10.5. Text.Trim removes leading and trailing whitespace and fixes this particular row. Text.Clean does a different job: it removes non-printable control characters, the ones below code point 32, which is what strips an embedded tab or line feed out of a value pasted from a PDF. Use both, because the two failures look identical in a visual and only one of them is a space.

Here is the inconvenient part. A non-breaking space is code point 160, which is above the control character boundary, so Text.Clean does not touch it, and it is not treated as ordinary whitespace by Text.Trim either. Values copied out of a web page or an HTML mail routinely contain them. Trim plus Clean is the usual advice and it will not fix that case, so add an explicit replace.

MKey cleaning that actually holds
let
    Cleaned = Table.TransformColumns(LaborEntries, {
        {"TechnicianID", each Text.Trim(
            Text.Clean(Text.Replace(_,
                Character.FromNumber(160), " "))),
         type text}}),
    Codes = Table.AddColumn(LaborEntries, "CharCodes",
        each Text.Combine(List.Transform(
            Text.ToList([TechnicianID]),
            each Text.From(Character.ToNumber(_))),
            " "), type text)
in
    Cleaned
Lines 3 to 5
Replace runs first, turning any code point 160 into an ordinary space, so that Trim can then remove it from the ends. Order matters: trimming before replacing leaves the non-breaking space exactly where it was.
Lines 7 to 11
The diagnostic column. It prints the code point of every character in the key. For L-505 it returns 84 69 67 72 45 48 52 32, and that final 32 is the trailing ordinary space. If it came back 160 you would know instantly why Trim was not working. Add this column when a join fails for no visible reason, then delete it.

Surviving a column that changes name

Remove Other Columns generates Table.SelectColumns with a list of names and no third argument, so a missing column raises an error and the refresh stops. Write the function yourself and you get a third option.

MColumn selection that tolerates a source change
    Kept = Table.SelectColumns(WorkOrders,
        {"WorkOrderID", "ACREG", "StationCode",
         "WOType", "OpenedDate", "PromisedDate",
         "ClosedDate", "QuotedAmount"},
        MissingField.Ignore)
MissingField.Ignore
A name that is not present is skipped. The query refreshes. The column is gone from the model and every measure built on it returns blank.
MissingField.UseNull
The column is created and filled with nulls, so downstream steps that reference it by name still run. Usually the better choice, because a column of nulls is visible in a table visual whereas a missing column just vanishes from the field list.
Default, error
Refresh fails with the column name in the message. Loud, immediate, and correct for the eight columns of FactWorkOrder that the model cannot function without.

Be honest about the trade. MissingField.Ignore does not make your query resilient, it makes it quiet. A model that silently loses QuotedAmount reports zero variance against quote for every work order, and somebody makes a pricing decision on it. Reserve the Ignore option for genuinely optional columns. Use UseNull where a downstream step needs the name to exist. Let the mandatory keys fail loudly. Picking which failure you would rather have is the whole of the job here.

All of it in one place, and what I would actually do

Every transformation in this chapter has now been argued against its DAX alternative one at a time. Here they are together, with the Meridian counts that make each case, because the argument is easier to hold as a list than as six separate discussions.

Read down the verdict column and the pattern is narrower than Power Query simply being the better tool. All six of these transformations change the shape of a table. Shape is what the model is built on, so it has to be settled before the model exists. DAX earns its keep when the answer depends on what somebody just clicked. Not one of these six does. Nobody clicks a slicer and expects FactCapacity to stop having 28 rows.

That gives the rule to carry out of the chapter. If the operation changes the row count, the column count or the grain, do it in Power Query. If it changes a number in response to a selection, write a measure. The genuinely contested middle is small: a row level calculation that both tools handle correctly. It is worked through in full in Chapter 4. The answer there is to store it when the inputs are fixed history, and to compute it in a measure the moment a slicer could ever touch one of them.

Interview-level insight

Almost every transformation in this chapter can be described by what it does to the row count: unpivot multiplies by the number of value columns, append adds, merge with expand multiplies by average match count, group divides, split to rows multiplies by average token count. If you can state the expected row count before you click and then check it after, you will catch the majority of load bugs at the moment you create them. The Meridian numbers to hold in your head are 7 to 28 on the capacity unpivot, 21 to 5 on the station append, 8 to 10 on the labor expand, and 6 to 10 on the certification split.

What to remember
  • Anchor an unpivot on the key columns and let the value columns flow through. Read the formula bar: Table.UnpivotOtherColumns survives a new trade appearing, while Table.Unpivot hard codes the list, leaves the new column sitting wide and outside the totals, and says nothing.
  • ShopCapacity goes from 7 wide rows to 28 long rows, and the 176 total planned hours must be identical on both sides of the step.
  • Append matches columns by name only. The DimStation build is 8 plus 6 plus 7 equals 21, distinct to 5 including the blank, 4 after removing the blank, 5 again once UNASSIGNED is added.
  • Left anti join is the fastest orphan diagnostic in Power Query. WorkOrders to AircraftRegistry returns exactly one row, WO-1006. Right anti returns N120CE and N553KD.
  • Expanding a merge multiplies rows and duplicates header values. Expanding WorkOrders to its labor lines turns 8 rows into 10 and inflates quoted amount from 38,100 to 53,600.
  • Group By returns only groups that have rows, so WO-1005 and WO-1008 disappear. Merge the grouped result back onto the full header list if you need all eight.
  • Duplicate copies steps and drifts. Reference points at the output and propagates fixes, but it does not cache, so a staging query can be evaluated more than once per refresh.
  • Trim fixes the trailing space on L-505 and recovers TECH-04 to 10.5 hours. Neither Trim nor Clean removes a non-breaking space, so replace code point 160 explicitly.
  • State the culture in every date conversion. A locale flip on one work order moves average turn time from 12.0 days to 26.8 days with no error anywhere.
  • Every one of these transformations has a DAX imitation that returns the same numbers and costs more: UNION for unpivot and append, two of the six join kinds for merge, SUMMARIZE for group by, and nothing at all for reference versus duplicate. The matching numbers are the trap. They make the choice look optional.
  • The reason to shape data upstream is that a calculated table has to load every source it reads, is rebuilt every refresh, never folds, and cannot be referenced by any later query step. Power Query staging keeps the 8, 6 and 7 raw rows behind DimStation out of the model entirely.
  • The rule in one line: if the operation changes the row count, the column count or the grain, do it in Power Query. If the answer changes when somebody clicks, write a measure.
