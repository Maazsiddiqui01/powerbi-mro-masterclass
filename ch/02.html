Part 1 . Reading the data

02Why the star schema is the right shape

After this chapter you will be able to say, in storage terms, what a wide flat table costs Meridian. You will also be able to decide, for any dimension, whether to flatten it or split it out.

The finance manager wants one number before the quarter closes. What did Meridian quote? Your report says 46,600. Her ledger says 38,100. Nothing on the page is broken and no measure has an error in it, and the answer is still 8,500 dollars wrong. The cause is the shape of the tables underneath. This chapter shows you how to price that shape in storage terms, so you can judge the trade yourself and stop quoting a convention at people.

Most people meet the star schema as a convention. Facts in the middle, dimensions around the edge, someone senior said so. A star schema is one table of measurements, called the fact table, surrounded by the tables that describe those measurements, called dimension tables. As a convention it stops helping the moment it looks like it is costing you something, because a convention gives you no way to price the trade. Storage gives you one, so build the argument up from there.

How the engine actually stores a column

Power BI holds imported data in memory using an engine called VertiPaq. VertiPaq is a column store, which means it keeps each column as its own separate object. So the eight rows of Fact FactLabor you met in Chapter 1 live in memory as six columns. Each one is compressed on its own, in its own region of memory. The engine reassembles rows at query time, and only for the columns the query actually touched. A measure is a calculation the model performs on demand, and a measure that reads FactLabor[Hours] never pays for FactLabor[HourlyRate] sitting next to it.

Each column gets one of two encodings. Value encoding applies to integers. The engine looks for a linear transform, usually subtracting a base, that holds every value in fewer bits. FactLabor[HourlyRate] contains 88, 95, 102, 110 and 120. Subtract 88 and the range becomes 0 to 32, which fits in six bits per row. A plain integer column wants thirty-two. No dictionary is needed here, because the original value is recoverable by arithmetic.

Dictionary encoding handles everything else: text, dates, decimals, and integers where the value trick does not pay. The engine lists the distinct values, gives each an integer id, and stores the column as a list of ids. Table 2.1 does that by hand for FactWorkOrder[StationCode], after the blank on WO-1005 has been mapped to UNASSIGNED.

Four distinct values need two bits to identify. Eight rows times two bits is sixteen bits, two bytes for the whole column, plus one dictionary of four short strings. "MSP" is stored once, not four times. I assigned the ids in order of first appearance for readability; the real assignment is the engine's business, but the count of entries is exactly what you control.

On top of that sits run length encoding. The engine works in segments, and a segment is a block of roughly a million rows in an import model. Inside each segment it reorders the rows so identical values line up, then stores each run as one value and one count. A station column reading MSP two hundred thousand times becomes a single pair. There is a tension in that, and it is worth knowing about. One row order has to serve every column in the segment. An order that gives long runs for StationCode may give short runs for ACREG, and the engine picks its compromise by heuristic. You cannot direct it.

Now the consequence, which is the whole chapter in one line. The cost of a column is set by its distinct count, not by its row count. The number of distinct values in a column is called its cardinality, and that word will come back in every section below. Four distinct values across a hundred million rows is nearly free: four dictionary entries, two bits per row, enormous runs. A hundred million distinct values across a hundred million rows is close to worst case: a dictionary as large as the table, twenty-seven bits per id, no runs anywhere. Every modelling decision below is a decision about cardinality.

The flat table, and the two bills it sends you

Go back to the finance manager and her 46,600. That number came out of the obvious approach, and the obvious approach is genuinely tempting, so build it here and watch it break. Meridian has six source tables. You want hours by aircraft type, by technician and by station, so you join everything in Power Query down to one table and load that. Down to what, though? Grain is the sentence that says what one row of a table means, and the grain you pick here is one row per labor line. Eight rows in, eight rows out, no relationships to explain to anyone. Table 2.2 is that table.

The figure takes the first five of those rows and tints every cell that is a repeat. That tinting separates the harmless repetition from the fatal kind. ACREG and AircraftType repeat because WO-1001 and WO-1003 each carry two labor lines, and neither repeat costs you an answer. The same is true across the wider Table 2.2, where Cascade Air appears four times and D. Sandoval twice. QuotedAmount repeats for exactly the same reason, and there it is fatal. A number that belongs to a work order has been copied onto every labor line that work order happens to have. Sum that column down the five rows drawn and you get 34,200, with 3,000 and 12,500 each counted twice. Sum it down all eight rows of Table 2.2 and you get 46,600, against a true total of 38,100.

The first bill is storage, and here I am going to argue against the version of this you have probably read. Repeating a low-cardinality text value is cheap. That is the exact case dictionary encoding and run length encoding were built for. AircraftType has four distinct values here, and it would still have four across a hundred million rows. The real storage penalty is narrower than the folklore. It comes from high-cardinality header attributes dragged down to line grain, and from the segment sort compromise, because twenty columns force one row order that cannot suit all of them. At eight rows, flattening costs zero bytes. Say so out loud. A reader who has been told the flat table is slow, and then measures it, will stop believing you about anything else.

The second bill is correctness, and that one you have to pay in full. QuotedAmount is an attribute of the work order header, which means it has one value per work order. In Table 2.2 it has one value per labor line instead. WO-1001's 3,000 appears twice and WO-1003's 12,500 appears twice. Meanwhile WO-1005 and WO-1008 have vanished from the table entirely, because neither has a labor row to hang on.

The wrong way

Sum the header amount from the flattened table, because it is right there as a column.

DAXQuoted Total, flat
// FlatLabor is one row per labor line
Quoted Total =
    SUM ( FlatLabor[QuotedAmount] )
Line 3
SUM reads one physical column and adds every value it finds. It cannot know that two of those values are copies, because nothing in the model says so. Returns 46,600.

The usual repair is to deduplicate inside the measure.

DAXQuoted Total, patched
Quoted Total =
    SUMX (
        SUMMARIZE (
            FlatLabor,
            FlatLabor[WorkOrderID],
            FlatLabor[QuotedAmount]
        ),
        FlatLabor[QuotedAmount]
    )
Line 2
SUMX and not SUM, because SUM can only read a column that physically exists. You are adding the rows of a table built at query time, which needs an iterator.
Line 3
SUMMARIZE and not VALUES, because you need the work order key paired with its amount. VALUES returns one column, which would collapse two work orders that share an amount.
Cost
It removes the duplicates and still cannot invent WO-1005 and WO-1008. It also runs this grouping on every visual, every slicer click, forever.
The fix

Keep the header amount at header grain, in its own table, and sum it there.

DAXQuoted Total, star
Quoted Total =
    SUM ( FactWorkOrder[QuotedAmount] )
Line 2
SUM is right here precisely because the grain is right: eight rows, eight amounts, one per work order. No deduplication needed, so no iterator needed.
Result
38,100, which matches what finance quotes. WO-1005 and WO-1008 are included, because they exist whether or not anyone booked time to them.

The measure got shorter. That is the tell. When the shape matches the grain, measures stop containing corrections.

What you see in the report

A card labelled Total Quoted reads 46,600. Nobody questions it. It is roughly the right size, and it sits beside a labor hours card reading 62.0, which is correct. Three weeks later the finance manager says the quarter was 38,100 and asks why you are 8,500 high. You will not find that by staring at the visual, because the visual is doing exactly what you asked it to do.

Trace the 8,500 by hand

Flat sum, straight down the last column of Table 2.2: 3,000 plus 3,000 plus 3,200 plus 12,500 plus 12,500 plus 4,000 plus 7,500 plus 900 equals 46,600.

Reconcile that against the true total of 38,100. Remove WO-1005 at 2,000 and WO-1008 at 5,000, because neither has a labor row to carry it into the flat table. That leaves 31,100. Now add the copies back. WO-1001 sits on two labor lines, so its 3,000 counts twice, and WO-1003 sits on two lines, so its 12,500 counts twice. 31,100 plus 3,000 plus 12,500 equals 46,600. The overstatement is 8,500, which is the figure the finance manager put to you.

A left outer join from work orders to labor does not save you. WO-1005 and WO-1008 come back with blank hours, giving ten rows, and the quoted sum becomes 46,600 plus 2,000 plus 5,000, which is 53,600. You added the missing work orders back and the number got worse. That is the signature of a grain problem rather than a data problem.

Common mistake

Treating the deduplicating measure as the fix. It is a tax, and you pay it on every measure that touches a header column: quoted amount, promised date, turn time, on time percentage. Each has to be written defensively by someone who remembers why. The next person to open the file will write SUM, get 46,600, and ship it.

The star

So the finance manager gets her 38,100 as soon as the quoted amount goes back to the grain it belongs at, one row per work order. That table is the one in the middle of the picture that follows.

One Fact table sits in the centre in terracotta, FactWorkOrder at eight rows, one per work order. The four Dimension tables that describe it sit around it in teal: DimDate above, DimAircraft to the left, DimStation to the right, DimWOType below. Follow any line and count the hops. Each line carries a 1 at the dimension end and a star at the fact end, and every one of them is a single hop. That is the whole idea. A slicer is the filter control a report user clicks, and everything a slicer touches sits one relationship away from the numbers it filters. A dashed border means somebody built the table. Not one of these four arrives from a source system as a table you can simply load.

The full model runs wider than that one star. The facts are FactWorkOrder at eight rows, FactLabor at eight, FactParts at seven and FactCapacity at twenty-eight after the unpivot. Only FactWorkOrder is drawn above. Five dimensions have to be Built, because no source system hands them to you. DimAircraft is the registry appended with the tails found in the work orders, which gives N338WA a home instead of a blank row. DimStation is the union of three sources plus an UNASSIGNED member. DimTechnician gains a row for the orphan TECH-07. DimPart is derived from the fact itself, since no part master exists. DimDate is generated from a start date and an end date.

Two hops

Here is what happens when the production controller clicks A320-200 in that slicer. The engine restricts DimAircraft to the two matching rows, N771QR and N615RB. It reads their ACREG values as a set of dictionary ids and pushes that set onto FactWorkOrder[ACREG]. Then it scans that one column once and keeps the row positions that match: WO-1001, WO-1004 and WO-1008 on N771QR, plus WO-1005 on N615RB. The surviving set propagates on to FactLabor the same way. Hours comes back as 23.5, which is WO-1001 at 13.5 plus WO-1004 at 10.0. WO-1005 and WO-1008 contribute nothing, because neither has a labor row. Nothing was widened and nothing was duplicated. The work is proportional to the number of distinct keys, not to the size of the fact.

Now the inconvenient part, and you should say it out loud in a design review. Meridian's model is a star with one extra layer in it. FactWorkOrder plays two roles at once. It is a fact, because QuotedAmount lives on it and gets summed. It is also the header dimension for FactLabor and FactParts, neither of which is drawn in the star above. That puts DimAircraft two hops from FactLabor instead of one. The chain is what makes hours by aircraft type reachable at all, since neither line table carries an aircraft registration. Two hops is the price of keeping the header amount at header grain, and it is worth paying.

What a relationship costs at query time

The planner has been told that every relationship you add makes the report slower, and he wants to know how many the model can carry. It is a fair question and it has a specific answer, so work out what one relationship actually costs the engine.

A relationship in a tabular model is not a SQL join, and the engine does not evaluate it like one. At load time, for each many-to-one relationship, the engine builds a structure that maps every value on the many side to the position of the matching row on the one side. Following the relationship afterwards is a lookup. There is no matching phase, no hashing of one side against the other, no loop over rows. Many-to-one is the direction almost every relationship in this model runs: many fact rows point at one dimension row.

Be precise about what is certain here. The internal representation is an implementation detail. Microsoft has changed it across versions and does not publish it as a contract. What is stable, and what you design against, is the cost profile. A many-to-one hop costs roughly in proportion to the distinct values involved, and it stays cheap into the millions of rows. So the planner's answer is that relationships of this shape are close to free, and you should add the ones the questions need.

Many-to-many is a different animal. There is no single row on the one side to point at, so that prepared structure cannot exist. The engine expands the filter through a distinct list of the shared key at query time and holds an intermediate result. That work happens per query and per filter combination, and it cannot be prepared at load. It also gives up the property that made the star worth building, because filters that travel both ways can take more than one route.

Rule of thumb

Every relationship should be many-to-one, single direction, from the one side outward. When you want a many-to-many, first check whether you are missing a dimension. Meridian's certification case is genuinely many-to-many, so BridgeTechCert exists for it: ten rows joining the six certified technicians to four certifications, producing hours by certification that add to 85.0 against a true total of 62.0. That gap is real, and it gets its own chapter.

Snowflaking, and when it is worth it

A colleague reviews your model and says the aircraft dimension repeats the operator name seven times, so it should be split out. The instinct behind that is a good one, and here it is wrong. Work through what the split buys and what it costs, because you will have this argument again.

Read this one from the left. DimOperator and DimEngineType both feed DimAircraft, and only DimAircraft touches FactWorkOrder. That is four boxes and three lines, each line labelled 1 at the outer end and a star at the inner end. Count the hops from a filter on Operator to the fact and you get two, where the star figure had one. The selection resolves to operator keys, then to aircraft registrations in DimAircraft, then to fact rows. The picture is tidier. The query has more to do.

Snowflaking means normalising a dimension, which is to say lifting the repeated attributes out into their own table. Here DimAircraft splits three ways. DimAircraft keeps the aircraft registration, the aircraft type and two outer keys, OperatorID and EngineID. DimOperator holds the three real operators plus an unknown member. DimEngineType holds the three engine families plus its own unknown member. The benefit is real. If the customer service desk renames Northwind Regional, there is one row to change and it cannot be changed inconsistently.

Read the last column twice, because it is the argument your colleague needs to hear. Snowflaking is sold as a way to remove duplication. Dictionary encoding has already removed it. "Northwind Regional" is stored once either way. The flat dimension holds seven small ids inside one table. The snowflake holds those same seven ids, plus a four-row operator table, plus a four-row engine type table, plus two more relationships in the model. Rows held goes up: 7 becomes 7 plus 4 plus 4, which is 15. The saving you were promised has already been taken by the compression.

So take a position. Flatten by default. Snowflake in two situations only. First, when the outer table is large enough that duplicating its attributes genuinely costs something, such as a five million row product dimension carrying a two hundred character description, where the dictionary itself becomes the expensive object. Second, when the outer table is truly shared, meaning two or more dimensions need the same attributes and the same maintenance.

Neither situation holds at Meridian, so tell your colleague the split stays out. DimAircraft has seven rows and DimOperator would have four. You would add a table, a relationship and a hop to every operator filter, all to avoid repeating an integer id seven times. There is a second cost you cannot measure in bytes. Report authors open the field list, find aircraft attributes sitting in three places, and start guessing which one to use.

Several facts, one set of dimensions

The production controller wants one line on a page: how busy was MSP in January. Busy against what, though. He means the hours the shop actually worked, set against the hours it planned to have available. Those two numbers live in two different fact tables, and nothing so far in this chapter lets you put them in the same row.

A model with more than one fact sharing the same dimensions is called a galaxy, or a fact constellation. The name matters less than the mechanism. DimStation has a single-direction relationship to FactWorkOrder[StationCode], and a second one to FactCapacity[StationCode]. A dimension used this way is conformed, which means one member list and one meaning serving both facts.

Put DimStation[StationCode] on the rows of a matrix and the engine takes each station in turn, pushing that filter down both relationships independently. Labor hours resolves through the work orders. Planned hours resolves through the capacity rows. Both answers land in the same matrix row, and that is the whole mechanism behind utilisation.

DAXUtilisation
Labor Hours =
    SUM ( FactLabor[Hours] )

Planned Hours =
    SUM ( FactCapacity[PlannedHours] )

Utilisation =
    DIVIDE ( [Labor Hours], [Planned Hours] )
Lines 1 to 2
One physical column of one fact. Under a station filter this gives MSP 34.5, TUS 22.5 and LAS 5.0, adding to 62.0.
Lines 4 to 5
A different fact through the same dimension. MSP 90, TUS 50, LAS 20, PHX 16, adding to 176. PHX has planned hours and no work booked against them. That is a fact about the business, and the report should show it.
Lines 7 to 8
Divides the two. By station and month: MSP January 22.5 over 30 is 75.0%, TUS January 12.5 over 25 is 50.0%, LAS March 5.0 over 20 is 25.0%, PHX March 0 over 16 is 0%, and 62.0 over 176 is 35.2% for everything.
Why this and not that

DIVIDE rather than the / operator, because the denominator goes blank in a way you will actually hit. The relationship into FactCapacity is at month grain, so a report filtered to 7 January returns 7.5 labor hours and a blank planned hours. In DAX a non-blank number divided by blank returns infinity, and your card shows a symbol nobody wants to explain. DIVIDE returns blank, which is the honest answer to a day-level question asked of month-level capacity.

SUM and not SUMX in the two base measures, because both columns physically exist and need no per-row arithmetic. SUMX would build an iteration where a single column scan does the job. It earns its place only when the value has to be computed row by row, such as hours times rate.

So the production controller gets his line. MSP in January is 22.5 hours worked against 30 planned, which is 75.0%. Take DimStation away and that measure has nowhere to stand. The two totals would sit in unrelated tables with no shared filter, and the only way to line them up would be a Power Query merge at a grain that fits neither. The conformed dimension is what makes the comparison expressible at all.

Cardinality as a design input

The shift supervisor asks for something reasonable. Every labor line has a note where the technician types what they did, and he wants it in the report so he can read the story behind a long job. Loading one more column sounds like a two minute job. Before you agree, count what that column would contain.

Cardinality is the distinct count of a column, and once distinct count drives cost, cardinality becomes something you check before you load anything. Table 2.4 is the census for the columns already in the model. The bit width is the smallest number of bits that can address that many distinct values. Treat it as a lower bound on the id width, not a promise about final size.

So make the judgement column by column. FactWorkOrder[ACREG] has five distinct values across eight rows. It would still have five across five million rows, because Meridian works the same small fleet. Three bits per row, a dictionary of five short strings, and it is the key that reaches DimAircraft at all. Keep it without thinking twice. Low-cardinality keys on a fact are the cheapest thing in the model.

Now price the supervisor's column. Call it WorkDescription, one free-text note per labor line. Every value in it would be distinct, because no two people write the same sentence. The dictionary would hold one entry per row, so it would be as large as the table it describes. The ids would need as many bits as there are rows. Run length encoding would find nothing at all to compress. On eight rows that costs nothing. On eight million rows, that one column would outweigh the rest of the model put together.

Cardinality is only half the argument, though. Ask what the column is for. Nobody groups a chart by free text, and nobody filters on it, because it cannot be selected usefully in a slicer. It exists to be read one row at a time, at the level of a single labor line. So the answer to the shift supervisor is that the note stays where it is. He reads it in the shop floor system, one job at a time, which is how he reads it today, and the model carries the hours he wants to group and compare. If he ever needs the note inside Power BI, that is a decision to take again against a real row count and a measured refresh, and to write down. The same logic condemns FactLabor[LaborID]. It is distinct per row, and no visual will ever group by it, so once the relationships are built it is dead weight.

Performance note

Two numbers decide what a column costs you. The first is its distinct count, which sets the width of every id and the length of every run. That is why a five value rate column is free and a per row identifier is expensive. The second is whether anything in the report actually needs the column, which decides whether you should be paying at all. Hiding a column leaves it exactly where it was. A hidden column is still loaded, still encoded, still refreshed, and it still gives the segment sort heuristic one more column to compromise over. Hiding takes it out of the field list and stops there, which makes it a usability choice. If a column has no measure, no relationship and no visual behind it, remove it in Power Query, or stop selecting it in the source query so it never crosses the wire. Two things to check first in any inherited model: the surrogate row id on every fact, and any free-text note field.

The reason that actually matters

The shift supervisor at MSP comes back with a printed page. Your report says his station did 34.5 hours in the quarter. His whiteboard says 28.5, and he has been running that whiteboard for nine years. One of you is wrong, and this section is about the possibility that neither of you is.

First deal with cost, because at Meridian's size every cost in this chapter is zero. Eight work orders, eight labor rows, seven parts rows and twenty-eight capacity rows will not stress anything. If performance were the only argument for the star, the honest answer for this model would be to flatten it and move on.

The real argument is ambiguity, and the supervisor's whiteboard is where it shows up. Look at what the relationship list deliberately leaves out. There is no relationship from DimStation[StationCode] to DimTechnician[HomeStation], even though the columns match and Power BI would happily create it. Draw that line and there are two routes from DimStation to FactLabor. One goes through FactWorkOrder and answers hours performed at this station. The other goes through DimTechnician and answers hours worked by technicians based at this station. Both are legitimate questions. They are different questions.

Work it out from the rows. Through the work order, MSP is 34.5, TUS is 22.5, LAS is 5.0. Through home station it comes out differently. TECH-01 at 12.0 and TECH-02 at 16.5 are both MSP, giving 28.5. TECH-04 at 10.5 is TUS. TECH-05 at 13.0 is LAS. TECH-07 at 10.0 has no home station at all. So the second route reads MSP 28.5, TUS 10.5, LAS 13.0 and unassigned 10.0. Both columns total 62.0. Every single row differs. LAS more than doubles, TUS halves, and nothing on the visual tells you which path the engine took.

So the supervisor is right and so are you. He counts the people who report to him. Your report counts the aircraft that came into his hangar, including the 10.0 hours TECH-07 booked there. Because the model holds one path and only one, you can tell him which of the two his 34.5 is, and build the other number as its own measure if he wants both. In a model carrying both paths at once you could not have answered him, because you would not know which one the visual used.

Interview-level insight

The star schema earns its place on one property above every other. It gives each measure exactly one path from every dimension to every fact, so a number means the same thing in every visual on every page. Performance is the secondary benefit. Ambiguity is what makes a measure behave differently in two visuals that look identical, and it is close to undebuggable from the report surface, because the report shows you a number and never shows you the route it took. Keep one path and the argument about which answer is right never starts.

What to remember
  • VertiPaq compresses each column separately, so a column costs what its distinct count costs, not what its row count costs.
  • Flattening to line grain repeats header attributes. The storage penalty is smaller than folklore claims; the correctness penalty is fatal. Summing QuotedAmount over the flat labor table gives 46,600 instead of 38,100.
  • Meridian's star is four facts, seven dimensions and one bridge, with one extra layer in the middle: FactWorkOrder is also the header for FactLabor and FactParts, which is what makes hours by aircraft type reachable.
  • A many-to-one hop is a prepared lookup, so it is cheap. Many-to-many expands a distinct list per query and gives up the single-path guarantee.
  • Flatten dimensions by default. Snowflake only when the outer table is large enough for its attributes to cost something, or when two dimensions genuinely share it. Seven aircraft rows against four operator rows means the Meridian snowflake buys nothing and costs a hop.
  • Conformed dimensions make cross-fact measures possible. DimStation feeding both FactWorkOrder and FactCapacity is the only reason 62.0 over 176 equals 35.2% can be written.
  • Remove unused columns. Hiding one changes nothing in memory: it is still loaded, still encoded and still refreshed.
  • The payoff is one unambiguous filter path per measure. Hours at MSP is 34.5 through the work order and 28.5 through home station, and a model containing both paths would let the engine pick.
