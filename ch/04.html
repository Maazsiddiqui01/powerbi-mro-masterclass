04Power Query or DAX: deciding where work belongs

After this chapter you will be able to take any transformation request, place it in one of four layers, and say out loud what that choice costs at refresh time and at query time. You will also be able to check whether your Power Query steps are still being pushed back to the source, and fix the ones that are not.

The production controller stops at your desk at nine in the morning. He wants the work order board grouped by how long each job took: under a week, one to two weeks, over two weeks. You already have turn days working. You wrote it last week as a measure, which is a DAX formula Power BI works out fresh every time a visual asks for it. Now you try to put those turn time buckets on the axis of a chart, and Power BI will not let you. Nothing is broken. The calculation is sitting in the wrong layer.

You asked when to use DAX and when to use Power Query in the cases where both would work. That is most cases. Either tool will strip the trailing space from TECH-04 in row L-505, derive the category Brakes out of the BRK-2210 prefix, and work out that WO-1003 took 22 days to turn. Both tools give you the same number. What separates them is when the work runs, how many times it runs, and how much of the world the work can see while it runs.

Four places the work can happen

Every transformation in a Power BI solution lands in one of four layers. They run in a fixed order. Each layer can see things the layer before it could not. Knowing the order is most of the skill. Once you can say where a piece of logic runs, you can say what it costs.

1. The source system, before Power BI is involved

A view in the shop floor database, a computed column in the timesheet system, a corrected data type agreed with the vendor. Work here is done once, by an engine designed for set based work. The result is then available to every report that reads that table, including reports nobody has built yet. If someone else builds a report on the same timesheet table next quarter, they inherit your fix for free. This is the cheapest layer to run and the most expensive layer to get access to. At Meridian it is mostly closed: the WorkOrders extract arrives as a file, the fleet list is a spreadsheet kept by the customer service desk, and ShopCapacity is a planning workbook that a scheduler edits by hand. You cannot push a computed column into a workbook. That is a real limit and it is worth naming early. Half the advice in this chapter only becomes usable the day someone gives you a connection to the system behind the export.

2. Power Query, at refresh

M runs when the semantic model refreshes. A refresh is the scheduled or manual reload that pulls current data out of the source and rebuilds the model from it. Whatever M produces is handed to the storage engine, encoded, sorted and compressed. From that moment it is indistinguishable from a column that came straight out of the source. Power Query is where reshaping belongs: unpivoting, splitting, appending, trimming, deriving row level attributes, building small dimensions. The cost is paid once per refresh and never again.

3. DAX calculated columns and calculated tables, at model load

These are evaluated after the imported data has landed, in the pass usually called process recalc. They can see the whole model, including relationships, which M cannot: RELATED works in a calculated column and has no equivalent in Power Query without a merge. The result is materialised and stored in the model, so it costs memory and it costs refresh time, every refresh.

4. DAX measures, at query time

Nothing is stored. The expression is evaluated when a visual asks for a value, inside whatever filter context the report has produced at that instant. Filter context is the set of filters in force at that moment: the slicers the user clicked, the row and column headings of the visual, and anything else narrowing the data. A slicer is the button, list or date range on a report page that a user clicks to filter it. This is the only layer that can see what the user selected. It is also the only layer that runs again every time anyone touches anything.

Read that diagram as a timeline running left to right. Each band has already finished by the time the band to its right begins. That is why a measure can use a Power Query column and a Power Query step can never use a measure. The three Power BI bands each name the moment they run: at refresh, at load and at query time. The axis underneath turns those moments into a price. At the left hand end the work is computed once, per refresh. At the right hand end it is computed per visual, per user, per click.

The picture leaves one thing for you to carry in your head. Each layer can see a different amount of the world. The source knows nothing about your model. Power Query knows about one query and whatever it merges in. A calculated column knows the whole model and knows nothing about the report page. Only the measure layer can see the slicers. Sight and cost run in the same direction, and that is the reason the order is worth memorising. The line above the green card, push work as far left as you can and then move it right for one reason only, is the rule stated below in upstream and downstream terms. The green card itself is that one reason.

The principle, and why it holds

Rule of thumb

Push each piece of work as far upstream as it will go, because upstream work is computed once and downstream work is computed again for every visual, every user and every interaction.

The arithmetic behind that sentence is dull and decisive. Deriving PartCategory from the prefix of PartNumber in Power Query runs 7 times per refresh, once for each row in PartsIssued, and the answer sits in DimPart as 4 rows afterwards. Deriving the same category inside a measure runs whenever a visual needs it: on the parts page, on every drill through, for the scheduler and the shop manager and the customer service desk, at nine in the morning when all three of them open the report at once. The logic stayed exactly as simple. What changed is the number of times it ran.

There is a second reason, quieter but more important on large models. A column produced in Power Query is compressed by VertiPaq along with everything else in the table. VertiPaq is the storage engine inside Power BI that keeps imported data column by column, and its compression is what makes the model fast. A value computed at query time is never compressed, because it never exists until the query asks for it. Upstream work becomes part of the compressed structure. Downstream work has to be rebuilt on top of it.

Meridian will not make you feel any of this. The finished model is 8 work order rows plus 8 labor rows plus 7 parts rows plus 28 capacity rows plus 10 bridge rows plus 90 date rows plus the dimensions at 7, 5, 7, 4, 3 and 4 rows. That totals 181 rows in the entire model. Every choice in this chapter runs instantly at that size. You are learning the discipline here so that it is already a habit the day the timesheet extract arrives with millions of rows and a four minute refresh turns into forty.

The exception, which is the real dividing line

The planner set the baseline three weeks ago and is now being asked why average turn days moved. She filters the report to MSP and reads 15.0 days. She clears the filter and reads 12.0 days. Both numbers came out of the same model on the same afternoon. Both are correct. Here is why one stored column could never have produced both.

The upstream principle on its own is wrong. Follow it blindly and you produce reports that lie. Work has to move downstream whenever the result depends on what the user selected. Anything a slicer can change cannot be precomputed, because at refresh time nobody has clicked anything yet.

Interview-level insight

Forget the lists of tasks. The question that decides the layer is: can a slicer change this number? If the answer is yes, the number does not exist until query time, and no amount of upstream cleverness can precompute it. Everything else in this chapter is a refinement of that one test.

Turn time on a work order shows both sides of the line in the same calculation. WO-1003 opened on 2025-01-14 and closed on 2025-02-05, which is 22 days. That 22 is a property of the row. It holds whether the user filters to MSP, to March, or to AOG work. It belongs upstream, as a column. Average turn days across closed work orders is a different animal. Across all six closed work orders it is 12.0 days, from a sum of 72 over 6 orders. Filter the report to MSP and the closed work orders are WO-1001 at 10 days, WO-1002 at 5 days and WO-1006 at 30 days. The average becomes 45 divided by 3, which is 15.0 days. Two numbers from one dataset, both correct, and only a measure can produce the second one.

That is the planner's pair of numbers. Her 12.0 and her 15.0 are the same measure read under two filter contexts, which is why nobody moved the baseline. It also answers the production controller from the opening of this chapter. Turn days on one work order is a property of the row, so it belongs in Power Query as a stored column. Once it is stored, you can bucket it, put the buckets on an axis, and count work orders in each bucket. A measure could only ever have printed the number in a card.

The procedure, in the order to run it

  1. Ask whether the answer changes when the user changes a slicer. If it does, it is a measure. Stop here, the remaining questions do not apply.
  2. Check whether it is a row level attribute that you will group by, filter on, sort by, or join on. If it is, it belongs in Power Query as a column. Axes, slicers and relationships all need a stored column to point at.
  3. Ask whether the calculation needs values sitting in the current filter context of another table, for example planned hours from FactCapacity beside actual hours from FactLabor. That combination only exists at query time, so it is a measure.
  4. Decide whether the thing has to exist before relationships are built: a key, a dimension member, an Unknown row. Put it in Power Query. A relationship can be built on a calculated column and it will work, but you have then stored the key twice. The dirty version stays in the model for someone else to pick up by mistake.
  5. Ask whether it is a table that depends on other model tables and could never have been produced upstream, such as a what-if scenario table. That is a DAX calculated table, and you accept that it is rebuilt on every refresh.

Run the questions in that order and take the first match. The order matters because question one dominates everything else. A late flag looks like a row level attribute, and it is one. Then somebody asks for a tolerance slicer that changes the definition of late. The flag stops being an attribute and becomes a measure. Upstream discipline will not save you there.

Fifteen decisions, with the failure mode attached

Three of those rows deserve their function named. Naming a function without a reason is how bad habits spread.

Ranking technicians uses RANKX and not TOPN. TOPN returns a table of the best n rows and never produces a rank number you can put on a visual. RANKX returns a position for the current row in the current filter context, which is what a rank on a visual means.

Year to date hours uses CALCULATE with DATESYTD. TOTALYTD is shorter and it hides the CALCULATE inside itself. It does accept an extra filter argument, but that argument is positional and sits next to an optional year end date. The next person reading the formula cannot see what is filtering what. The explicit form puts the context modification on the page where it can be read. CALCULATE and not a plain filter expression, because only CALCULATE can replace the filter context that the visual has already applied.

If you ever do build turn days as a measure rather than as a column, use DATEDIFF with the DAY interval. Subtracting one date from the other carries the time component with it and hands you a decimal that then needs rounding. DATEDIFF states its unit in the code where the next reader can see it. Average turn days over a stored column uses AVERAGE and not AVERAGEX, because there is nothing left to iterate once the value sits on the row.

Query folding, and how to tell whether you still have it

The planner messages you at seven in the morning. The overnight refresh has gone from four minutes to forty, her report was still building when she needed it, and nobody changed the data. You changed something. You added one step to the labor query on Friday afternoon. That step is the reason, and the reason has a name.

Query folding
The mechanism by which Power Query translates your applied steps into a single native query and sends that to the source, instead of downloading the table and doing the work locally.
Materialised
Stored as real values in memory. Imported columns and calculated columns are materialised, so they occupy space. A measure is computed on demand and stores nothing.
Process recalc
The pass after data load in which the engine evaluates calculated columns, calculated tables and hierarchies, in dependency order.

Filter LaborEntries to Q1 2025 against a real database and Power Query writes a SQL statement with a WHERE clause. The database runs it. Only the Q1 rows ever cross the network. That is folding, and it matters for three reasons that all point the same way: the source is better at set based work than the mashup engine is, far less data travels, and the source can use its own indexes on your behalf. A folded query on a large table is often an order of magnitude faster than the same steps evaluated locally. It is the single biggest refresh lever you have.

To check, right click the last applied step and look at View Native Query. If it is available, everything up to that step folded and you can read the SQL. If it is greyed out, folding has already stopped. Click back up the step list until the option becomes available again; the first step where it goes grey is the one that broke it. This is the whole diagnostic, and it takes twenty seconds.

Folding is a prefix property. Once a step breaks it, everything after that step runs locally, no matter how foldable those later steps look on their own. That gives you the practical rule: filter rows and remove columns first, while folding is still alive. Put the index column, the buffer and your clever custom function at the end, where they can only slow down a table that is already small.

MFactLabor, ordered to keep folding
// Filter and drop columns first, while folding is still alive.
let
    Source  = Sql.Database("shopfloor01", "MRO"),
    Labor   = Source{[Schema="dbo", Item="LaborEntries"]}[Data],
    Kept    = Table.SelectColumns(Labor,
        {"LaborID", "WorkOrderID", "TechnicianID",
         "WorkDate", "Hours", "HourlyRate"}),
    Q1      = Table.SelectRows(Kept, each
        [WorkDate] >= #date(2025, 1, 1) and
        [WorkDate] <= #date(2025, 3, 31)),
    Trimmed = Table.TransformColumns(Q1,
        {{"TechnicianID", Text.Trim, type text}})
in
    Trimmed
Lines 2 to 4
The let block opens, then the connection on line 3 and the table on line 4. Nothing has been fetched yet; M is lazy and only executes when the result is demanded.
Lines 5 to 7
Column removal goes first. It becomes the SELECT list, so the six columns you keep are the only ones that ever cross the network.
Lines 8 to 10
The date filter becomes a WHERE clause. It is written as an explicit range, because a plain comparison is the form the connector translates most reliably. A date helper function is where folding often stops.
Lines 11 to 12
The trim that fixes L-505. Text.Trim and not a text replace of every space, because replacing spaces would also destroy any key that legitimately contains one. Against SQL Server this folds to a trim in the native query. Against another connector, check View Native Query before you assume anything.

The order in that query is the whole lesson. Move the trim to the top and it still gives the right answer. On a large table you may have pulled every column and every year across the wire to get it.

That is the planner's forty minute refresh. The step you added on Friday was an index column, and an index column cannot fold. Because folding is a prefix property, every step after it stopped folding too, including the date filter that used to keep the whole quarter at the source. Move the index column to the end of the query, behind the filter and the column removal, and the database goes back to doing the heavy work.

What a calculated column actually costs

A DAX calculated column appears the instant you type it in a model of a few hundred rows, so most people treat it as free. It costs memory and it costs refresh time, every single refresh. The reason is worth stating plainly.

Performance note

A calculated column is materialised into the model exactly like an imported one, so it consumes memory. It is also usually compressed less effectively, because the engine loads and compresses the imported columns first and picks a segment sort order based on what it can see at that moment. Your calculated column is evaluated after that sort has been chosen, so the sort was never optimised for it. How much worse the compression turns out to be depends entirely on the data, so measure your own model before you quote a ratio. On DimDate at 90 rows this is noise. On a labor table of tens of millions of rows it can be the difference between a model that fits in memory and one that does not.

There are two more costs that surprise people. First, a calculated column is recomputed on refresh and on any model change. That is why adding an innocent measure to a large model sometimes triggers a wait you did not ask for. Second, a calculated column that reads another table creates a dependency. The engine must finish that table before it can evaluate your column. Chain a few of these together and process recalc has to walk the chain in order. Picture a column on FactLabor that reads DimTechnician, and a column on DimTechnician that reads DimStation. Nothing here is catastrophic on its own. Together they turn a refresh you understood into one you have to investigate.

What a measure costs, which is the mirror image

A measure stores nothing, so it adds not one byte to the model. It pays for that at the other end. It is evaluated when a visual asks, and it is asked often. Put technicians on the rows of a matrix and months on the columns. DimTechnician has 7 rows and Q1 has 3 months, so that is 7 times 3, or 21 body cells. Add 7 row subtotals, 3 column subtotals and the grand total, and one measure has produced 32 values in one visual. Add a second visual and a slicer. Then multiply by however many people have the report open.

Be careful with how you picture that. The engine is smarter than the cell count suggests: for a simple aggregation it will often satisfy the whole matrix with one or two storage engine scans and slice the results up afterwards. The cell count becomes real when the measure manipulates filter context in ways the engine cannot batch, and that is where badly written CALCULATE logic hurts. A measure that forces per cell evaluation over a large fact table is the most common cause of a report that feels slow without any single thing looking wrong.

The middle case nobody argues about honestly

The finance manager wants one number for the month: what labor cost. He does not care which table it comes from, and he should not have to. On the face of it this is the easiest request in the chapter, and it is the case that sits exactly on the fence. FactLabor has Hours and HourlyRate on every row. Line cost is one multiplication. You can store it as a Power Query column, or you can never store it and let a measure do the multiplication at query time.

DAXLabor Cost
Labor Cost =
SUMX (
    FactLabor,
    FactLabor[Hours] * FactLabor[HourlyRate]
)
Why this and not that

SUMX and not SUM, because SUM takes a single column and there is no single column here to sum. The product has to be formed row by row before anything can be added up, and SUMX is the iterator that creates that row context. If you had stored a LineCost column in Power Query then SUM would be correct and SUMX would be pointless extra machinery, which is exactly the trade being argued below.

The case for storing the column: the multiplication happens once per refresh instead of on every query, and a plain SUM over a stored column is a pure scan with no expression to evaluate. On a very large fact table that difference is measurable.

The case against: the stored column costs memory, and it costs more than people expect. Cardinality means the number of distinct values in a column. The cardinality of a product is roughly the cardinality of hours multiplied by the cardinality of rates, and high cardinality columns are the expensive ones in a columnar model. Meridian has 8 distinct line costs, so this is invisible here. In a real timesheet table LineCost is often one of the worst compressing columns in the model. The stored column also cannot respond to a what-if rate slicer, ever, because it was computed before anyone selected anything.

DAXLabor Cost at Scenario Rate
Labor Cost at Scenario Rate =
VAR ScenarioRate =
    SELECTEDVALUE ( 'Rate Scenario'[Rate] )
RETURN
    IF (
        ISBLANK ( ScenarioRate ),
        [Labor Cost],
        SUMX ( FactLabor, FactLabor[Hours] * ScenarioRate )
    )
Lines 2 to 3
Read the single rate the user selected. SELECTEDVALUE and not VALUES. VALUES returns a table, and it throws an error the moment more than one value is in context. SELECTEDVALUE returns blank in that same situation and lets you decide what to do about it. Not MIN either, because MIN would silently pick a value when the user has selected several and hide the ambiguity.
Lines 5 to 7
ISBLANK and not a comparison to zero, because in DAX a blank compares equal to zero and a scenario rate of zero is a selection a user could legitimately make. Line 7 falls back to the real Labor Cost measure, so the visual shows actuals until somebody moves the slicer.
Line 8
The scenario branch multiplies hours by the selected rate and ignores HourlyRate entirely. This is the line a stored LineCost column can never produce.
Trace both versions by hand, row by row

Eight rows, one multiplication each. The stored column would hold the right hand values below and SUM would add them. The measure forms them at query time and adds them in the same pass.

Now set the scenario rate to a flat 100 per hour. The measure returns 62.0 times 100, which is 6,200.00, so the scenario sits 126.50 below the actual 6,326.50 (6,326.50 minus 6,200.00). A stored LineCost column returns 6,326.50 no matter where the slicer is, because the numbers in the fourth column above were fixed at refresh time.

So what should you actually do. Store the column when the inputs are immutable and the row level arithmetic is simple. A closed period fits that description: HourlyRate is the rate that was billed and nobody is going to reprice history. Use SUMX the moment the rate could ever be parameterised. Retrofitting a what-if onto a stored column means rewriting every measure that already depends on it.

For the finance manager's monthly number, both versions print 6,326.50 and he will never know which one you built. Choose for the request that comes after his. The day somebody asks what the month would have cost at a flat 100 per hour, only the measure can answer, and the answer is 6,200.00.

The storage argument is also weaker than it used to be. SUMX over a multiplication of two columns in the same table is one of the patterns the storage engine handles well. It can do the arithmetic inside the scan without materialising an intermediate table, so you are paying for a scan you were going to pay for anyway. The stored column usually wins only on very large fact tables. Even then, the compression penalty on a high cardinality product eats into the gain. This decision is genuinely close. A colleague who argues the other side with a measured refresh time and a measured query time in front of them is probably right for their model.

The lookup that should have been a relationship

The shift supervisor tells you the report is wrong. His whiteboard says TECH-04 booked 10.5 hours this week. Your technician page says 6.0. He is right, you are wrong, and the cause is one calculated column that somebody wrote to avoid building a relationship.

Common mistake

Adding a calculated column to a fact table that pulls an attribute across with LOOKUPVALUE, instead of building the relationship. It is the single most common symptom of a model whose author has not committed to the star schema. It is usually written by someone who could not get the relationship to work and quietly went around it.

DAXThe column you should not write
// Calculated column on FactLabor. Do not do this.
TechName =
LOOKUPVALUE (
    DimTechnician[TechnicianName],
    DimTechnician[TechnicianID], FactLabor[TechnicianID]
)
Line 2
A new stored column on the fact table, duplicating text that already exists once per technician in the dimension. On 8 labor rows that is 8 copies of a name. On a large fact table it is millions of copies of a string that VertiPaq already stored efficiently in one small dimension.
Lines 3 to 6
A filtered scan of DimTechnician for every row of FactLabor at process recalc, with no relationship to make it cheap. It also fails hard: L-505 with its untrimmed key returns blank, and if two dimension rows ever matched the same key the expression raises an error rather than picking one.
Everything
The deeper damage is that no relationship exists, so filter context never propagates. Slicing by HomeStation, by EmployeeType or through BridgeTechCert is impossible, and the 10.0 orphan hours from TECH-07 disappear into a blank with nothing to catch them.

The fix is not a better formula. Trim the key in Power Query. Add the Unknown row for TECH-07. Build the relationship from DimTechnician[TechnicianID] to FactLabor[TechnicianID]. Then drag TechnicianName onto the visual straight from the dimension. No column is required at all, and TECH-04 comes back to 10.5 hours, which is the number on the supervisor's whiteboard. If you genuinely need the value materialised on the fact row, for example to sort a fact level visual by an attribute, then this is what it should look like.

DAXOnly if the value must sit on the row
HomeStation = RELATED ( DimTechnician[HomeStation] )
Why this and not that

RELATED and not LOOKUPVALUE, because RELATED follows a relationship that already exists in the model. The engine resolves it through the many to one path it has already built, so it is cheaper, and it cannot silently disagree with what the rest of the model does. LOOKUPVALUE performs an independent filtered lookup with no relationship behind it. That means it works in places RELATED cannot, for example matching on a column pair that is not the relationship key. That case is the only one where reaching for it is defensible. If RELATED will not compile, the honest reading is that your relationship is missing or inactive, and that is the thing to fix.

One last honest note

None of these choices will change a single millisecond on 181 rows. You could put every calculation in this chapter in the wrong layer and Meridian would still render instantly. That is what makes it a good place to build the habit and a bad place to test it. The moment your model stops being a teaching set, the cheapest diagnostic you own is the question at the top of the procedure, asked before you write anything: can a slicer change this number.

What to remember
  • Work happens in four layers that run in order: the source, Power Query at refresh, calculated columns and tables at model load, measures at query time. Each layer sees more than the one before and costs more to run.
  • Push work as far upstream as it will go, because upstream work runs once and downstream work runs for every visual, every user and every interaction.
  • The exception overrides the principle: anything a slicer can change cannot be precomputed, so it is a measure. Ask that question first and take the first match.
  • Row level attributes used to group, filter, sort or relate belong in Power Query, along with keys, unknown members and anything that must exist before relationships are built.
  • Folding means your steps are executed by the source. Check with View Native Query, remember it is a prefix property, and do filtering and column removal before anything that breaks it.
  • Calculated columns are materialised, compress less well because they are computed after the segment sort is chosen, and are rebuilt on every refresh and model change.
  • Measures store nothing and pay for it at query time, which is fine until filter context manipulation forces evaluation cell by cell.
  • LineCost is a genuinely close call. Store it when the rate is fixed history, compute it with SUMX when the rate could ever become a parameter.
  • A LOOKUPVALUE column on a fact table is almost always a relationship someone gave up on.
