06Relationship mechanics: cardinality, direction, active and inactive

After this chapter you can look at any line in the Meridian model diagram and say what the engine stores for it, what it asserts about the data, and which refresh will break it. You will also know why three of the four cardinality options are usually a sign that something upstream is unfinished.

What the engine stores when you draw a line

The production controller stops at your desk with a printout. He wants labor hours by technician, and your report gives TECH-04 six hours flat. His whiteboard says ten and a half. Nothing errored. The refresh ran clean at six that morning, and the line joining the labor table to the technician table sits in the model diagram looking perfectly healthy. Four and a half hours have gone somewhere anyway.

You probably learned relationships as a picture. You drag a column onto another column, a line appears, and the report starts working. That picture hides the thing you need to understand, so start underneath it.

A relationship is a declared mapping. It ties exactly one column on one table to exactly one column on another. When you create it, Power BI does not write a join and it does not run one at query time the way a SQL engine would. It builds a structure and stores it beside those two columns. Every column has already been encoded down to integers by then. Text columns get dictionary encoding: each distinct value is handed an internal identifier, and the column is physically stored as a long run of those identifiers. Many numeric columns get value encoding instead. Different scheme, same consequence for us. The engine compares integers. The relationship is an index built on top of that encoding, and it answers one question fast. Given a set of values on the one side, which row positions on the many side carry them?

The engine builds that structure at refresh, which is the moment the model pulls a fresh copy of the data from the source. You pay for it once. Every visual that uses it afterwards reads something that already exists. The structure is asymmetric too, in a way a SQL join never is. In SQL you write an ON clause, and both tables are then equally available to the WHERE clause, so asking about direction there means nothing. Here the stored structure is tuned for one job: turning one side values into many side row positions. That asymmetry is where the cross filter direction setting comes from. Direction falls out of how the mapping is stored.

Carry one practical consequence with you. What travels along a relationship is a set of values. When a visual filters DimStation to MSP and TUS, the engine resolves those two station codes to their identifiers. It uses the relationship index to find the matching row positions on the fact table. Then it scans only those rows. No joined table is ever built anywhere in the process. That is why a model with a dozen small dimensions around a fact stays quick under a filter, and why a single wide table with everything flattened into it does not.

Fact table
A table of events, one row per thing that happened. FactLabor holds one row per booking of hours by a technician against a work order.
Dimension table
A table of the things you describe events by, one row each. DimTechnician holds one row per technician.
Grain
What one row of a table means, written in one sentence. The grain of FactLabor is one row per labor booking.
Cardinality
Your assertion about uniqueness on each side of the mapping. It is a claim about the data, and the engine will hold you to it on every refresh.
Cross filter direction
Which way filters are allowed to travel along the mapping once it exists.
Active relationship
The one relationship on a given path between two tables that filters are allowed to use without being asked.
Weak relationship
Microsoft's term, also written as limited, for a relationship the engine cannot treat as a clean one to many. Many to many relationships are weak. They behave differently, and the differences are not cosmetic.

Cardinality is a claim about uniqueness

The dropdown offers four options. There are only three ideas in it, because two of the options are the same relationship written with the tables in the other order. Take them one at a time.

Many to one

Many to one means the column on the first table you selected has repeated values and the column on the second table is unique. This is the default, and it is what you should have on nearly every relationship in a working model. In Meridian, Dimension DimTechnician sits on the one side with seven rows, one per technician identifier, and Fact FactLabor sits on the many side with eight rows. Three technician identifiers appear twice in the labor table: TECH-02, TECH-04 and TECH-05. Five distinct identifiers across eight rows. That is a textbook many side.

That count only holds because Power Query trims FactLabor[TechnicianID] on the way in. Power Query is the load and transform layer, the place where data is cleaned on its way into the model. Untrimmed, row L-505 carries "TECH-04 " with a trailing space. The column then holds six distinct values where only five technicians exist, and the relationship still builds without a murmur, because nothing on the many side has to be unique. The 4.5 hours on that row leave TECH-04 and land on the blank row. TECH-04 falls from 10.5 hours to 6.0.

So the production controller's whiteboard was right. The report was right too, about a set of rows that no longer contained L-505. Cardinality validation was never going to catch it, because cardinality validation only ever looks at the one side.

The engine requires one thing of the one side: the key column must contain unique values and no blanks. It will not accept a duplicate, and if a duplicate arrives during a refresh the refresh fails with an error naming the relationship. That failure is loud, which is the good case.

Here is the part people miss. Power BI infers cardinality from the data that happens to be loaded on the day you create the relationship. It scans the two columns, sees that one of them has no repeats, and fills in the dropdown accordingly. That inference is a snapshot of one moment. The source system promised you nothing. DimAircraft in the Meridian model is unique on ACREG, the aircraft registration, because a Power Query step appends the registry to the distinct tails found in the work orders and then removes duplicates. Delete that step, reorder it, or let a tail arrive with different casing or a trailing space, and the one side stops being unique. What fails is the relationship you created in January and have not looked at since. The error names that relationship. The query step that actually caused it goes unmentioned.

Common mistake

Accepting the inferred cardinality without checking whether uniqueness is guaranteed or merely current. Ask a harder question at creation time: what upstream step or source rule makes it impossible for a duplicate to arrive? Uniqueness today answers nothing. If the answer is a Power Query step you wrote, that step is now load bearing and should be commented as such. If the answer is that the source system holds a primary key on the column, you are safe. If the answer is "it just is", you have a relationship that will fail on a refresh you did not schedule, at a time you did not choose, with an error message that blames the wrong object.

One to one

The planner is at your desk now, and she is annoyed. Last month's review put average turnaround at 12.0 days. This month's pack says 12.17. Nothing about January changed, no work order moved, and she signed the baseline herself in December. Two systems in this model record when a check started, and somebody has quietly begun reading the other one.

One to one means both columns are unique. That is a precise statement with a blunt implication: the two tables are at the same grain and describe the same thing. In almost every case where you find yourself reaching for it, the correct action is to merge the two tables in Power Query. A one to one relationship is usually a merge you have not done yet.

Meridian has exactly one pair of tables that would honestly carry that setting, and the shipped model leaves the relationship out, because merging them is the right answer. The pair is HMCCSchedule and Fact FactWorkOrder. HMCC stands for Heavy Maintenance Control Centre. That is the function that owns the heavy check schedule: which aircraft is in which hangar bay, on which planned dates, for which customer. Be careful with those four letters. Work order is a universal term and HMCC is a local one. Plenty of shops call the same function production control, maintenance control, or the base maintenance control centre. On the line maintenance side the equivalent is Maintenance Operations Control, or MOC. The function always exists. The label on the tab does not always say HMCC.

The extract carries seven columns: WorkOrderID, ServiceLine, CheckType, Customer, Bay, PlannedStart and PlannedFinish. Service line is the kind of maintenance the work belongs to, and this shop runs three of them. Light is line maintenance. It is worked on the ramp, at the gate or in a line hangar, often overnight, and it covers service checks, defect rectification and aircraft on ground recovery. Heavy is a hangar visit. The aircraft comes out of service, goes up on jacks and is opened up, for days or for several weeks. Cabin and IFE is the third, where IFE stands for In-Flight Entertainment. It covers seats, monuments such as galleys and lavatories, and the seat-back and head-end entertainment units. Check type names the visit itself. A C-check is a heavy scheduled visit. A defect rectification is a light one. Bay is the physical dock the aircraft occupies, which is why it is blank on WO-1005, the same work order that has no station code. Customer is blank on WO-1006, for the same reason its aircraft registration N338WA is missing from the registry.

Now the grain, which is the only thing that decides cardinality. HMCCSchedule holds eight rows and FactWorkOrder holds eight rows. WorkOrderID appears once and only once in each. Both key columns are unique and neither contains a blank, so Power BI reads the pair as one to one, and here it has the evidence to say so. Compare the two planning tables sitting next to it, which look similar and are not. FactPreInput also has eight rows, and they cover only five work orders. Its grain is one row per work order per trade, and WO-1001 carries an airframe row and an avionics row. Pre-input is the planning step that happens weeks before the aircraft arrives, where a planner builds the work package and totals up the planned hours per trade. FactForecast has eight rows across the same five work orders. Its grain is one row per work order per revision, and three of those checks were re-forecast once as findings landed. Three tables, eight rows each, three different grains. Only one of them is a candidate for one to one.

So the relationship is available and it is honest, and you should still not create it. Merge the two in Power Query instead. Here is the argument from the top of this section, made concrete. Two systems are describing one thing, and the thing is a work order. The shop floor export knows when it opened and what it was quoted at. The control board knows what service line it belongs to and which bay it went into. No report author cares which system a column came from. Merged, ServiceLine is a field on the fact table and a service line split is a single hop. Related, it stays a separate table in the field list holding six descriptive columns, and every report that mentions a service line has to reach through it. Look at what that costs here. ServiceLine and CheckType exist nowhere else in the model. Without the merge, the four heavy work orders, the three light ones and the single cabin and IFE one can only be told apart by way of a second table. Once merged, the distinct values in those columns are what the service line, check type and customer dimensions get built from.

There is also a mechanical reason, and it is the part of one to one that catches people. Cross filter direction is fixed at Both and the dropdown is greyed out. You cannot set it to single. The lock follows from the storage. Direction exists because the stored mapping is asymmetric, one side values translated into many side row positions. When both sides are unique, there is no many side left to be asymmetric about. What remains is a one for one lookup that reads correctly in either direction, so the engine offers both and leaves you nothing to switch off. The consequences are real. A slicer on Bay reduces FactWorkOrder, which is what you wanted. A visual filtered to one work order also reduces HMCCSchedule, which you did not ask for and will not notice. The link also counts as a two way path when Power BI looks for a second route between two tables. A one to one added for convenience can be the reason a relationship elsewhere in the diagram turns dashed.

The merge is two steps and one decision. Steps first.

Line 2
Starts from the cleaned work order query, after the blank station on WO-1005 has been mapped to UNASSIGNED. Merge onto the keys the model will actually use, not onto the raw export.
Line 3
Table.NestedJoin rather than Table.Join. NestedJoin parks the matches in a column that you expand yourself, so the choice of which columns cross over is a visible step someone can read six months later. Table.Join brings the whole second table across in one move, including its own copy of the key you joined on, and you then delete columns afterwards.
Line 6
JoinKind.LeftOuter, and not Inner. The two key lists match row for row today. Left outer keeps all eight work orders on the refresh where the control board has not been updated yet. A missing schedule row then shows up as a null in a column. An inner join would drop that work order out of the model, and report the loss to you as a smaller row count, which is the same trap as the DirectQuery setting at the end of this chapter.
Line 8
Expand by an explicit list. Click the expand arrow and you take the default, which selects everything the nested table happens to hold. The control board is a hand maintained workbook. Naming the six columns keeps a seventh, added by a planner on a Tuesday, out of your fact table on Wednesday.
Line 10
These six come across and sit alongside the columns already on the work order. PlannedStart lands beside OpenedDate, and PlannedFinish beside PromisedDate. That deliberate duplication is the subject of the next paragraph.

Now the decision. Merging two systems into one table is clean only while the two systems agree, and here they do not. Seven of the eight rows line up exactly. Every PlannedStart equals the matching OpenedDate, and every PlannedFinish equals the matching PromisedDate. WO-1003 breaks the pattern. The control board says the C-check on N902TT started on 2025-01-13. The shop floor export says the work order opened on 2025-01-14. One row, one day, and neither figure is a typo. The aircraft was booked into bay TUS-H1 for the thirteenth and arrived on the fourteenth. That is ordinary. Planned input dates and actual input dates routinely differ, because aircraft arrive late. The control board records what was planned. The shop floor export records what happened. Two systems, two owners, and neither column is wrong.

Do not let the size of the gap fool you. Turnaround time is the headline number in a hangar. It runs from input, when the aircraft is inducted into the bay, to output, when it leaves. WO-1003 closed on 2025-02-05. Measured from the opened date that check ran 22 days. Measured from the control board's planned start it ran 23.

Trace this by hand, row by row: which date moves the average

Six of the eight work orders are closed, so six of them have a turnaround time at all. WO-1004 and WO-1008 are still open and drop out of the calculation, which is a separate trap worth naming: an average turn time that silently excludes every job still sitting in the hangar.

Measured from OpenedDate, the six run 10, 5, 22, 2, 30 and 3 days, which is WO-1001, WO-1002, WO-1003, WO-1005, WO-1006 and WO-1007 in that order. They total 72 days, and 72 divided by 6 is 12.0 days.

Now swap in the control board start on every row. Seven of the eight planned starts equal the opened date, so five of the six closed rows do not move at all. Only WO-1003 changes. 2025-02-05 minus 2025-01-13 is 23 days, where the opened date gave 22. The total becomes 73 and the average becomes 73 divided by 6, which is 12.17 days.

One row out of eight, one day out of 72, and the number read out in the monthly review is no longer the number on last month's slide. That is the planner's 12.0 against this month's 12.17. Nobody in that meeting will know which of the two you used unless you tell them.

This is what the merge actually forces on you, and it is worth being precise about. Two related tables let both dates sit in the model while nobody commits to either. That feels like caution, and it hands the decision to whichever report author happens to pick a field. The merge makes the choice visible. The two columns land side by side in one table, and somebody has to write down which one the turnaround measure uses. Keep both columns. Name them so nobody has to guess: OpenedDate for the actual induction, PlannedStart for the control board's plan. Then put the choice in the measure description, where the next analyst will find it. A conversation nobody minuted is worth nothing six months out.

Which date the turnaround measure uses is a decision, and the maintenance lifecycle gives you a steer. The turnaround clock starts when the aircraft physically arrives and is inducted. It stops when certifying staff issue the CRS, the Certificate of Release to Service, which is the signed statement that the aircraft is fit to fly. OpenedDate and ClosedDate record those two events. A turnaround measure built on them measures what the term actually means, and on that basis WO-1003 ran 22 days and the planner's 12.0 stands. PlannedStart answers a different question: whether the slot the customer booked held. Both columns have a reader, and neither substitutes for the other. The indefensible model is the one where two measures on two pages answer the same question differently and neither says so. Write the local definition down, get somebody in production control to agree it, and put it in the model description.

One cost of merging that nobody mentions until the morning it happens. The control board is very often a spreadsheet somebody keeps by hand. After the merge, that spreadsheet writes columns straight into your fact table. Rename a column on it and the fact query fails, and a failed fact query takes the whole model down. Leave the tables apart and the same rename breaks one side table, which you could disable while you sorted it out. Merging is still the right call. Expand by name, as the code above does, and accept that you have taken on a dependency the model diagram will never show you.

Every one of those is an argument about how to merge. The case for keeping two same grain tables apart is narrower than it looks.

There is a legitimate case. You split a wide table on purpose, for one of two reasons. A group of columns is sensitive, and you want row level security or object level security applied to a narrower surface. Row level security limits which rows a given user can see. Object level security hides whole columns or tables from them. The other reason is size: a group of columns is large and rarely used, and you would keep it away from the columns most reports scan. For Meridian, that would mean keeping the seven row DimTechnician as it is, and holding pay band and personal detail in a separate table keyed on TechnicianID. Both are unique on that key, so the relationship is genuinely one to one.

Two things about it are not negotiable. First, a one to one relationship is bidirectional by definition, and the cross filter dropdown is fixed at Both. You cannot make it single direction. A filter on the sensitive companion table then reduces the technician list everywhere in the report, including in visuals that have nothing to do with pay. The link also counts as a two way path when Power BI checks the model for ambiguity, so adding it can get an unrelated relationship elsewhere deactivated. Second, the two tables will not stay perfectly aligned. DimTechnician contains a built row for TECH-07, the orphan identifier from FactLabor. No companion table sourced from human resources, HR, will ever have a matching row for it. That asymmetry is normal, and it is exactly the sort of thing that makes one to one uncomfortable in practice.

Uncomfortable is vague, so put a number on it. The asymmetry here is one row, and one row is enough to move a total that six people are reading.

Trace this by hand, row by row: the six row companion

Load the companion table straight from the HR extract and it arrives with six rows, TECH-01 through TECH-06. DimTechnician has seven, because the build adds TECH-07 to catch the orphan identifier that L-506 books ten hours against. Both key columns are unique and neither contains a blank, so Power BI creates the relationship as one to one and reports no problem with it.

Now put any column from that companion table anywhere a filter can live: a slicer, a matrix row, a visual level filter. The direction is Both and you cannot set it to Single, so the companion filters DimTechnician, and DimTechnician filters FactLabor down the ordinary many to one relationship. Select every member of the companion column, which a report author reads as selecting everything, and the technician set that survives is still only the six rows HR knows about. TECH-07 is not in the companion table, so there is nothing there for it to survive on.

Labor hours then read 52.0 instead of 62.0. The ten hours on L-506 have not been reclassified and they have not moved to a blank row. They have been filtered out of the model, and there is no row anywhere in the visual to account for them. Put DimAircraft[AircraftType] on rows at the same time and A320-200 drops from 23.5 to 13.5, because WO-1004 is an A320 work order and L-506 is the only labor booked to it. Nothing errors. The page simply shows a smaller number than the page next to it.

Rule of thumb

Accept a one to one relationship only when two things are true at once. You genuinely cannot merge the two tables, because one of them needs a narrower security surface or carries columns too wide to sit beside the ones every report scans. And the two key lists are guaranteed to stay identical row for row, held that way by the same upstream rule, for as long as the model lives. Meridian fails the second test by exactly one row. If you have to keep the split anyway, build the companion from the same key list the dimension is built from, appending an unknown row for TECH-07 the way DimAircraft appends N338WA, rather than loading it straight from the source and hoping the two lists stay level.

Many to many

The finance manager wants one number for the month: how busy was the shop. Planned hours sit in the capacity workbook. Booked hours sit in the labor table. He cannot see why dividing one by the other is a day's work, and until you look at what those two tables actually have in common, neither can you.

Many to many means neither column is unique. Power BI will create it without complaint and without asking you for a bridge table. Internally it builds one anyway: a hidden table of the distinct values of the joining column, which it uses to route the filter from one side across to the other. You never see this table and you cannot reference it.

The result is what the documentation calls a weak or limited relationship. Weak relationships behave differently in two ways that matter. First, no blank row is added to hold unmatched values. A key that is present on one side and absent on the other is dropped from cross filtering, and it lands nowhere you can see it. Second, the relationship does not extend the propagation chain the way a regular relationship does. A filter that arrives at a table through a weak link is not guaranteed to carry on to the next table beyond it. If you are relying on a three table chain and one of the links is weak, check the middle result yourself.

The Meridian version of this mistake is tempting. You want utilisation, which is labor hours over planned hours. Planned hours live in Fact FactCapacity, which sits at station and month grain, with one row per trade inside each station month. The shortest looking route is to pull a station column onto FactLabor in Power Query, then relate FactCapacity[StationCode] straight to it. Power BI accepts it. Neither side is unique, so you get many to many.

Trace this by hand, row by row

FactCapacity has 28 rows because the seven wide planning rows were unpivoted across four trade columns. Grouped by station code, those 28 rows fall out as follows: MSP has three station months (January, February, March) times four trades, which is 12 rows. TUS has two station months times four trades, which is 8. LAS has one station month times four trades, which is 4. PHX has one station month times four trades, which is 4. That is 12 plus 8 plus 4 plus 4, or 28 rows, which matches the table.

FactLabor has 8 rows. Taking each labor row's station from its work order: L-501 and L-502 belong to WO-1001 at MSP, L-503 belongs to WO-1002 at MSP, and L-507 belongs to WO-1006 at MSP, so MSP carries 4 rows. L-504 and L-505 belong to WO-1003 at TUS and L-506 belongs to WO-1004 at TUS, so TUS carries 3 rows. L-508 belongs to WO-1007 at LAS, so LAS carries 1 row. That is 4 plus 3 plus 1, or 8 rows.

MSP appears 12 times on one side and 4 times on the other. Neither column is unique, so the cardinality is many to many and there is nothing you can set to change that.

What makes this genuinely awkward is that the arithmetic often looks right. Filter to MSP through the capacity table and labor hours come back as 34.5, which is the correct answer. The damage is structural. You now have two station columns in the field list, and report authors will click whichever one they land on first. PHX exists only in the planning workbook, so it vanishes from any visual built from the labor side. A planner wants PHX sitting on that visual with 16 planned hours against zero labor hours, because the gap is the finding. The blank station on WO-1005 has nowhere sensible to live either. And no blank row is created, so a station code that fails to match is dropped in silence, where a visible blank would have sent somebody looking.

The right answer is Dimension DimStation in the middle. Five rows, unique on StationCode, one to many out to FactWorkOrder and one to many out to FactCapacity. Station becomes one field. PHX shows 16 planned hours against zero labor. MSP January reads 22.5 over 30, which is 75.0 percent, and the all stations all months figure of 62.0 over 176 comes out at 35.2 percent in a single visual. That is the finance manager's one number, and a five row table is what it took.

Which leaves the question of when many to many is the correct setting rather than a symptom. The test is three questions, and a yes to any one of them means you build the dimension. Can you list the distinct values of the joining column? If you can, you can load them as a table, and in Meridian you can: four station codes across all three sources plus one blank, which is an append step and a remove duplicates step. Do you need unmatched keys to stay visible? A weak relationship adds no blank row, so an unmatched code simply goes missing, and PHX takes its 16 planned hours with it. Does a filter have to continue past this hop to a third table? Propagation is not guaranteed to extend beyond a weak link, so a station selection that has to reach FactLabor through FactWorkOrder cannot lean on it.

That leaves a narrow legitimate case. The joining column is an attribute rather than an entity, so a table built on it would hold one column and nothing anybody wants to slice by. You accept losing the blank row and the onward propagation, and in exchange you avoid carrying a table that earns nothing. Nothing in Meridian qualifies. Station, month and work order are all entities with attributes the shop cares about. That is why all three end up as tables, and why none of them ends up as a many to many.

One to many

One to many is many to one with the tables named in the other order. That is the whole difference. Power BI reports cardinality relative to the sequence in which you picked the two tables. Drag FactLabor[TechnicianID] onto DimTechnician[TechnicianID] and you get many to one. Do it the other way and you get one to many. The model you end up with is identical in both cases. Stop treating them as two concepts and you will read the relationship list twice as fast.

Cross filter direction, briefly

Once the mapping exists, direction decides which way filters are permitted to move along it. Single means filters travel from the one side to the many side only: DimTechnician filters FactLabor, and nothing about FactLabor reaches back to reduce the technician list. Both means filters travel either way.

Both panels show the same pair of tables, DimTechnician above FactLabor, with nothing changed but the setting. The left panel is headed Single, the default. One arrow runs down from the dimension to the fact. The note beside it says that a selection on DimTechnician reaches FactLabor, and that a selection on FactLabor stops where it started. The right panel is headed Both, bidirectional. That same line is now double headed, and the note beside it gives the reason people turn it on. A selection on FactLabor narrows DimTechnician, which is what makes a slicer hide technicians with no hours. Read the two cards underneath as the verdict. The green one calls the single version one path, one answer. The red one calls the same convenience the usual source of ambiguity. That is the mechanism behind a complaint you will eventually hear: somebody changed one relationship setting, and a measure on a different page started returning a different number.

The default for many to one and one to many is Single, and the default is correct. Leave it alone. A dimension exists in order to filter facts. The reverse question, something like "which stations had any labor at all this quarter", is a question you answer with a measure rather than with a model setting. This matters enough to have its own chapter for one reason. Both changes what a filter means across the whole model, and it does so quietly, well beyond the relationship you changed. Chapter 8 takes that apart properly, including the cases where Both is the right answer. For now the setting is one checkbox with two values, and a default you should have a written reason to override.

Active and inactive relationships

The finance manager asks how many work orders January had. Your report says three. The shift supervisor, reading the same page over his shoulder, says two, because two is what came out of the hangar that month. Nobody is wrong. Eight work orders, one date table, and three different dates on each row.

Only one relationship may be active on any given path between two tables. Additional relationships between the same pair are stored in the model, drawn in the diagram as dashed lines, and they do nothing until a measure asks for one by name. Dormant is the better word for them. They are still validated and still built at every refresh, which is why an inactive relationship can fail a refresh on a duplicate key.

Meridian has three date columns on FactWorkOrder and one date table. OpenedDate holds the active relationship, because it is the one date every work order carries. ClosedDate is blank on the two jobs still in the hangar, so a default path built on that column would drop them from a count without saying so. PromisedDate and ClosedDate get relationships too, both inactive. The three tell genuinely different stories, and the numbers make that concrete.

One date table on the left, three lines into FactWorkOrder on the right, with the three target columns printed beside the fact box in the order the lines meet them. Only the top line, the one landing on OpenedDate, is solid, and it is the one labelled active. The two below it are dashed and labelled inactive, and they are stored, validated and rebuilt at every refresh exactly like the solid one. The only thing they lack is permission to carry a filter unless a measure asks for them by name. The card headed Why it matters puts the consequence in numbers: the same January selection returns 3 work orders by opened date and 2 by closed date.

Try to make a second one active and Power BI stops you. Depending on where you do it, you either get a refusal naming the existing active relationship, or, in the Manage relationships dialog, the tool deactivates the one that was active so that only one survives. Neither behaviour is arbitrary. Suppose two active paths ran from DimDate to FactWorkOrder. A filter of January against a count of work orders would then have two defensible answers, 3 by opened date and 2 by closed date, and the engine has no basis for preferring either. So it holds one path open and no more. The finance manager's three and the shift supervisor's two both live in that one table. Getting both onto one page means writing the second as a measure that names the dormant relationship. That refusal is a feature. It is also the same check that will bite you later, when a well meant extra relationship creates a second route between two tables you thought were connected one way.

To use a dormant relationship, name it inside a measure.

DAXWork Orders Closed
Work Orders Closed =
CALCULATE(
    COUNTROWS( FactWorkOrder ),
    USERELATIONSHIP( DimDate[Date], FactWorkOrder[ClosedDate] ),
    NOT ISBLANK( FactWorkOrder[ClosedDate] )
)
Line 1
This has to be a measure. The relationship swap happens while a filter context exists, and a calculated column has no filter context at query time.
Line 2
CALCULATE rather than CALCULATETABLE because the result is a single number for a card or a matrix cell. Both accept the same modifiers; the only difference is scalar against table, and USERELATIONSHIP is valid in either.
Line 3
COUNTROWS, and not COUNT( FactWorkOrder[WorkOrderID] ). COUNT counts non blank values in a column, so it silently changes meaning the day that column contains a blank. The question is how many work orders, which is a question about rows.
Line 4
The relationship swap. For the duration of this CALCULATE only, the closed date relationship becomes the active path from DimDate to FactWorkOrder and the opened date relationship steps aside. Nothing about the stored model changes.
Line 5
Excludes the two work orders with no closed date. Without it the measure returns 6 across the quarter and 2 in each of the three months. With no date filter at all it returns 8. The two unmatched rows attach to the blank row on DimDate, and that blank row is included whenever nothing filters the date table.
Why this and not that

USERELATIONSHIP rather than a second date table. Loading DimDate a second time and calling it DimClosedDate also works, and it has one real advantage: the two dates can then be sliced independently on the same page. The cost is that every date attribute exists twice, every slicer has to be duplicated, and a user who filters the quarter slicer is puzzled when half the page does not move. One date table with named relationships keeps a single slicer driving every date measure. Use the second table only when the report genuinely needs two independent date filters at once.

USERELATIONSHIP, and not CROSSFILTER. They look similar and do unrelated jobs. CROSSFILTER changes the direction of a relationship that is already active. It cannot wake a dormant one. Reach for it here and you get either no effect or an error, depending on what else is set.

NOT ISBLANK, and not a comparison against BLANK(). Comparing a column to blank drags in the engine's blank coercion rules, where blank equals zero for numeric types. Copy the same pattern onto an amount column later and it behaves in a way nobody expects. ISBLANK tests emptiness and nothing else.

Interview-level insight

A relationship is a design assertion about the data, and the engine will hold you to it. Most people add one so that a visual will work, which is how the assertion gets made by accident. Many to one asserts that a key is unique on the one side and stays unique through every future refresh. Single direction asserts that this dimension describes the fact, and that the fact says nothing back about the dimension. Active asserts that this, out of every possible route between these two tables, is the one route a report author gets without asking. Every one of those assertions is enforced. So when a relationship fails, look past the relationship. What changed is almost always the world the assertion described.

Four constraints people trip over

One column on each side, and no exceptions

The planner is back, and she wants planned hours beside booked hours, by station and by month. It takes two columns to identify a capacity row, station and month, and Power BI will only let you draw a relationship on one. So you build a key out of both parts. It works. By the end of this section you will have deleted it.

A relationship uses exactly one column on each side. There is no composite key relationship in Power BI. If your two tables share a two part key, you build a single column that holds both parts and relate on that.

Build it in Power Query, and put a separator between the parts. The separator does real work. Join part A straight onto part B and you get a string that another pair of parts could also produce. A station code of AB with a month of C gives the same result as a station code of A with a month of BC. In Meridian that collision cannot happen today. Every station code is three characters and every month key is six digits, so the split point is always in the same place. That safety is a property of the seven rows currently in the planning workbook. Your model does nothing to hold it there. The day somebody adds a two character code, every affected row joins to the wrong parent and nothing errors.

MFactCapacity, station and month composite key
let
    Source = ShopCapacityUnpivoted,
    AddKey = Table.AddColumn(
        Source,
        "StationMonthKey",
        each [StationCode] & "|" & Text.From([MonthKey]),
        type text
    )
in
    AddKey
Line 2
Starts from the unpivoted capacity table, so the key lands on all 28 rows and not on the 7 wide ones.
Line 3
Table.AddColumn rather than Table.TransformColumns because you want a new column beside the two originals. Keep the parts. You will need them for grouping, and a key you cannot decompose is a key you cannot debug.
Line 6
The pipe is the separator. It is chosen because it cannot occur in a station code or a month key, which is the only property a separator needs.
Line 6
Text.From, and not Number.ToText. The planning workbook has already changed the type of that column once. Text.From converts whatever arrives, where Number.ToText errors on anything that is not a number. Also not Text.Combine, which ignores null items and hands back a shorter string, so a row with a missing station code would produce a key that looks perfectly valid.
Line 7
The type is declared, not inferred. A column typed as any will not participate in a relationship, and the failure message does not mention typing.

Now the inconvenient part. You should not do this in Meridian. The composite key gives you MSP|202501, and four trade rows share that value, so it repeats inside FactCapacity. The capacity table would have to be the many side, and you would need a new seven row station month table on the one side. That table is a junk dimension nobody wants to slice by, sitting next to two dimensions that already cover the same ground. Station and month are independent of each other. DimStation and DimDate[MonthStart] filter FactCapacity correctly on their own, and between them they give the planner her report. Build a concatenated key when the parts genuinely cannot be separated into dimensions of their own. Not before.

Rule of thumb

Before you concatenate, try to decompose. A two part key usually means two dimensions, and two dimensions give the report author two independent slicers plus everything each dimension knows. A concatenated key gives one slicer full of strings like MSP|202501 that nobody can read and nobody can filter usefully.

Data types must match

A whole number key will not relate to a text key. The two columns can render identically in a table visual and still refuse to connect. The comparison happens on stored type, and the displayed text has no say in it. DimDate[MonthKey] holds 202501 as a whole number. Derive a month key on FactCapacity by taking the text "2025-01" and removing the dash, and what you have is the text "202501". The relationship dialog refuses to create the link. This is why the shipped model relates DimDate[MonthStart] to FactCapacity[MonthStart], both typed as date. No derived key comes into it.

Fix types in Power Query. A type change there is one operation applied during load, and the relationship is built directly on the loaded column. A calculated column adds a second stored column, materialised after load, and that column cannot fold back to the source.

The one side cannot contain blanks

The engine reserves the blank slot on the one side for its own use, so a genuine blank in your key column collides with something already sitting there. What the engine puts in that slot is the unknown member. When the many side holds a key value with no match on the one side, Power BI adds a blank row to the one side table and attaches the unmatched fact rows to it. That is deliberate design, and the reason for it is arithmetic. A total should never come out quietly smaller than the sum of its parts.

Meridian shows it in one place. FactParts contains issue P-9007 against WO-1009, and WO-1009 does not exist in FactWorkOrder. So FactWorkOrder carries a blank row and P-9007 hangs off it. Total parts cost is 28,245 whatever you do. Slice by anything that comes from the work order table, though, and the labelled rows add up to 23,345, with 4,900 sitting in an unlabelled blank row at the bottom of the visual. Report consumers scroll past that row. They have been trained to read blanks as noise.

The other blank in the dataset behaves differently and is worth separating. WO-1005 has no station code at all, which puts a blank on the many side of the station relationship. Many side blanks are allowed. They fall to the blank row on DimStation. The build handles this one by mapping the blank to an UNASSIGNED member, so the report shows a named row where an anonymous one would have sat. Labor hours by station then read MSP 34.5, TUS 22.5, LAS 5.0, UNASSIGNED 0 and PHX 0, totalling 62.0. Every one of those rows means something to a reader.

Circular paths are rejected

Power BI will not accept a set of active relationships that lets a filter leave a table and arrive back at it. It applies the same refusal to a set that gives one table two routes to another. Meridian has a live example, deliberately left out of the model. DimTechnician[HomeStation] holds station codes, and relating it to DimStation[StationCode] is tempting. Do that and DimStation can reach FactLabor two ways, once through FactWorkOrder and once through DimTechnician. Filtering to MSP would then mean either "labor on work orders raised at MSP" or "labor by technicians based at MSP". Two different questions, two different answers. Power BI will not choose between them, so it deactivates one of the paths. HomeStation stays as a plain descriptive column. If the shop later wants hours by the technician's home station, that is a measure, and Chapter 7 writes it.

Follow the two routes leaving DimStation on the left. Both arrive at FactLabor on the right, one across the top through FactWorkOrder and one across the bottom by way of DimTechnician. The top route is labelled path A and drawn solid. The lower one is labelled path B and drawn dashed, which is what the model looks like after the engine has refused to leave a second route active. The red card underneath is the reason. Select MSP and path A gives 34.5 hours, the work performed at that station, while path B gives 28.5, the hours booked by technicians based there. Both are defensible, and neither is what a bare MSP label on an axis promises. That is the shape the engine will not leave fully active. Train your eye to catch it in a diagram before the tool catches it for you. By the time the tool tells you, you are usually looking at a relationship that has been silently dormant for a fortnight.

Assume Referential Integrity

There is a checkbox on the relationship editor called Assume Referential Integrity. It appears only for DirectQuery relationships, where the model queries the source live at report time. Import mode never offers it. So if your model is fully imported you can skip this section, though you should still know what the checkbox does before somebody hands you a DirectQuery model to fix.

What it does is narrow and specific. It tells the engine that it may write an inner join in the native query it sends to the source. Without the checkbox the engine writes an outer join, which is what preserves unmatched fact rows. Inner joins let the source apply predicates earlier and ship fewer rows back. On a large DirectQuery fact that is a real difference.

It is safe when two things are true and provable: every key value on the many side exists on the one side, and the many side key is never blank. Not "usually true". Provable, by a constraint in the source or a check you run.

The consequence when it is not true is the reason this setting has a bad reputation. Rows that do not match are dropped by the inner join. No error is raised. No blank row appears, because there is nothing left to put in it. The number simply gets smaller. In Meridian, tick this box on the relationship from FactWorkOrder to FactParts in a DirectQuery model and P-9007 drops out entirely. Total parts cost goes from 28,245 to 23,345, with nothing anywhere to tell you that 4,900 has left the building. Now tick it on the station relationship, in a version of the model that has not yet mapped WO-1005's blank station code to UNASSIGNED. That work order disappears from every station sliced result, for the same reason. A blank many side key matches nothing, and an inner join has nowhere to put a row that matches nothing. Once the build maps the blank to a real member, the setting is safe on that relationship. That is a decent illustration of how narrow the safe case is. It depends on a Power Query step, and the checkbox knows nothing about Power Query steps.

Performance note

Assume Referential Integrity trades correctness for speed. Most settings only trade one cost for another, so treat this one with more care than the rest. If a DirectQuery model is slow, exhaust the ordinary work first: reduce the number of visuals on the page, push aggregations into the source, and check whether an import mode aggregation table over the DirectQuery detail would solve it outright. Come back to this checkbox last, and only for relationships where the source enforces the foreign key itself.

Deciding, in one table

One last note on the alternative to a physical relationship. TREATAS applies a set of values to a column as though a relationship existed, entirely inside a measure. That makes it the escape hatch for the case where a physical link would create ambiguity you cannot live with. It leaves no permanent path, so the ambiguity check never sees it. The cost is that the behaviour lives in one measure rather than in the model. A report author dragging raw columns onto a visual gets nothing. Prefer a physical relationship whenever the model can carry one honestly.

What to remember
  • A relationship is a stored mapping from one side values to many side row positions, built at refresh. Direction exists because that mapping is asymmetric.
  • Cardinality is inferred from the data present when you click OK. That makes it a snapshot of one refresh. Know what upstream rule keeps the one side unique, and write it down.
  • Many to one and one to many are the same relationship. One to one usually means a merge you have not done. Many to many usually means a dimension you have not built.
  • Meridian's one genuine one to one is HMCCSchedule to FactWorkOrder: eight rows each, one row per work order, both keys unique. Merge it in Power Query rather than relate it, and accept what the merge forces. The control board says WO-1003 started on 2025-01-13 and the shop floor says 2025-01-14. Somebody has to write down which date the turnaround measure uses, before an average of 12.0 days or 12.17 days means anything.
  • One to one is locked at Both, so the companion table filters the dimension whether you meant it to or not. A six row HR companion beside the seven row DimTechnician takes labor hours from 62.0 to 52.0 and A320-200 from 23.5 to 13.5, with nothing on the page to show where the hours went. Accept it only when you cannot merge and the two key lists are guaranteed identical forever.
  • Before accepting many to many, ask whether you can list the distinct values, whether unmatched keys need to stay visible, and whether a filter has to continue past that hop. A yes to any of the three means build the dimension.
  • Many to many produces a weak relationship: no blank row for unmatched values, and propagation that does not extend through the chain the way a regular relationship does.
  • One active relationship per path. Extra ones are stored and dormant, and a measure wakes one with USERELATIONSHIP inside CALCULATE. In Meridian, OpenedDate is active and PromisedDate and ClosedDate are not.
  • One column each side, matching data types, no blanks on the one side, no second route between two tables. Concatenate a composite key only when the parts cannot become dimensions of their own, and always with a separator.
  • Unmatched many side keys land on a blank row added to the one side. That is how 4,900 of the 28,245 parts cost ends up in a row report consumers ignore.
  • Assume Referential Integrity is DirectQuery only and drops unmatched fact rows without telling you. Turn it on only where the source enforces the key.
