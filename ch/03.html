03Building the dimensions your source does not contain

By the end of this chapter you will be able to build a complete, unique and stable dimension table out of source systems that never shipped one. You will also be able to prove that the dimension covers every key value any fact actually uses.

The planner asks for planned hours by station for the quarter. You build the chart in five minutes. Three bars come back, MSP 90, TUS 50 and LAS 20, and a fourth bar with no label on it holding 16. The total reads 176, which is right, and one station's worth of capacity is sitting in a bar nobody can name. This chapter is about where that unlabelled bar comes from and how to make it impossible.

Meridian's six source tables give you four facts and almost no dimensions. A dimension is the table that describes something a fact refers to: a station, a part, an aircraft, a date. There is no station master, no part master, no calendar and no work order type list. The one dimension that does exist, AircraftRegistry, is missing an aircraft registration that a work order already references. This is normal. Operational systems are built to record transactions, not to describe the world those transactions happen in.

So you build the descriptions yourself. That is the job, and this chapter is how it is done. A dimension is the list of values your model agrees are allowed to exist. The moment a fact holds a value that list does not contain, the model starts telling a quieter kind of lie: the totals stay right and the breakdowns go wrong. The planner's total of 176 is correct, and the breakdown underneath it is the half that fails him.

The four properties every dimension table must have

Before any M code, agree on what you are aiming at. A table qualifies as a dimension when all four of these hold. Miss one and you get a predictable failure, and it is worth knowing which failure belongs to which property.

  1. The key is unique. One row per key value, no exceptions. The engine enforces this on the one side of a relationship and will simply refuse to create the relationship if you break it. The deeper reason is arithmetic: a duplicated key fans the fact rows out across both matching dimension rows, and every measure over that path doubles without warning.
  2. The key has no blank. A blank in a dimension key is ambiguous, because Power BI already uses a blank member for something else. When a fact holds a key the dimension lacks, the engine adds an invisible blank row on the dimension side and parks the unmatched facts there. If your dimension also contains a real blank key, a blank category on a visual could mean either thing and you can no longer tell which.
  3. The key covers every value that appears in every fact referencing it. Complete coverage, across all facts, not just the convenient one. This is the property everyone misses, and it is the direct cause of the blank rows people see in visuals and cannot explain.
  4. The key is stable. The same code means the same thing next refresh. If the shop floor system starts sending MSP1 where it used to send MSP, every report level filter, every bookmark, every saved slicer selection and every measure that tests for "MSP" keeps working syntactically and returns nothing. Filters store the value, not the row. That failure is invisible at build time and expensive at read time.
Common mistake

Taking the distinct values from the largest fact and calling that a dimension. It feels safe because the biggest table surely has everything. At Meridian, WorkOrders is the biggest table that uses a station code, and it does not contain PHX at all. Build DimStation from WorkOrders alone and every capacity row for PHX, 16 planned hours, loses its home and lands behind a blank member. The station list has to be the union of everything that uses the key, not a sample of it.

DimStation, assembled from three partial lists

So where did the planner's fourth bar go. The station code lives in three places at Meridian and no two of them hold the full list. Look at what each source actually contains.

There is the planner's missing bar. Only the planning workbook knows PHX exists. Phoenix has capacity rows and no work orders, which is exactly the situation his chart should be showing him. Leave PHX out of DimStation and the relationship from DimStation[StationCode] to FactCapacity[StationCode] orphans those four capacity rows. An orphan is a fact row whose key has no match in the dimension, and the engine has to park it somewhere. It parks it in an unlabelled row, which splits the planned hours total into a labelled 160 and an unlabelled 16.

The blank on WO-1005 needs a different answer. A blank means nobody recorded a station. Keep it out of the key list you union together, because a key list holds codes and a blank is the absence of one. The work order itself is real, though, and its hours have to land somewhere a person can see, so you add a member with a real code, UNASSIGNED, and map the blank to it on the fact side. Two separate acts, in this order: drop the blank from the key list, then create a member that means "we know this one is missing".

  1. Create three reference queries from WorkOrders, Technicians and ShopCapacity, and reduce each one to the single station column.
  2. Rename HomeStation to StationCode so all three columns carry the same name, because an append matches columns by name and not by position.
  3. Append the three into one stack.
  4. Trim the text, then remove nulls and empty strings.
  5. Remove duplicates. What remains is the key list.
  6. Attach the descriptive attributes, either by merging a maintained mapping table or by joining a small inline table written in M.
  7. Append the single UNASSIGNED row.
MDimStation
let
    // one column from each source, all named StationCode
    FromWorkOrders =
        Table.SelectColumns( WorkOrders, {"StationCode"} ),

    FromTechnicians =
        Table.RenameColumns(
            Table.SelectColumns( Technicians, {"HomeStation"} ),
            {{"HomeStation", "StationCode"}} ),

    FromCapacity =
        Table.SelectColumns( ShopCapacity, {"StationCode"} ),

    Stacked =
        Table.Combine(
            {FromWorkOrders, FromTechnicians, FromCapacity} ),

    Trimmed =
        Table.TransformColumns(
            Stacked, {{"StationCode", Text.Trim, type text}} ),

    NoBlanks =
        Table.SelectRows( Trimmed,
            each [StationCode] <> null
                 and [StationCode] <> "" ),

    Keys = Table.Distinct( NoBlanks ),

    Attributes = #table(
        type table [ StationCode = text, StationName = text,
                     StationRole = text ],
        {
            {"MSP", "Minneapolis", "Line and Base"},
            {"TUS", "Tucson",      "Base"},
            {"LAS", "Las Vegas",   "Line"},
            {"PHX", "Phoenix",     "Planned, no activity"}
        } ),

    Joined =
        Table.NestedJoin( Keys, {"StationCode"},
            Attributes, {"StationCode"}, "attr",
            JoinKind.LeftOuter ),

    Widened =
        Table.ExpandTableColumn( Joined, "attr",
            {"StationName", "StationRole"} ),

    Unassigned = #table(
        type table [ StationCode = text, StationName = text,
                     StationRole = text ],
        {{"UNASSIGNED", "Unassigned", "n/a"}} ),

    DimStation = Table.Combine( {Widened, Unassigned} )
in
    DimStation
FromTechnicians
The rename is the load bearing step. Table.Combine aligns on column name, so an unrenamed HomeStation would produce a second column full of nulls instead of stacking underneath, and you would find out only when the distinct count came back wrong.
Trimmed
Trim before deduplicating, never after. "TUS" and "TUS " are two distinct values to Table.Distinct and one value to your eyes. Meridian already has this exact defect in LaborEntries on TECH-04, so treat the trim as a certainty. It has happened here once already.
NoBlanks
Nulls and empty strings are different values in M and both have to go. This removes the WO-1005 blank from the key list. It does not lose the work order, which still carries its hours and gets mapped to UNASSIGNED on the fact side.
Attributes
An inline #table is honest about what it is: a hand maintained mapping with four rows that a human owns. When it grows past roughly twenty rows or a second person needs to edit it, move it to a real file and merge instead, because nobody outside your team can find a table that only exists inside a query.
Joined
A left outer join keeps every key, even the ones the mapping has no entry for. That is the point of choosing it. If a new station code called RNO appears next quarter, it arrives in DimStation carrying a null name. An inner join would have dropped it on the floor. A null name in a report is a question somebody asks.

The same union can be expressed in DAX as a calculated table, and you should know how. On some datasets you genuinely cannot touch the queries. A live connection, a shared semantic model owned by another team, a certified dataflow you have no rights to edit: any of those leaves you working inside the model instead of upstream of it. Take the block below for what it is. It returns the key list and stops there, so the descriptive columns and the UNASSIGNED member are a second step, described under the code.

DAXDimStation key list, calculated table fallback
DimStation =
VAR Keys =
    DISTINCT (
        UNION (
            DISTINCT ( WorkOrders[StationCode] ),
            DISTINCT ( Technicians[HomeStation] ),
            DISTINCT ( ShopCapacity[StationCode] )
        )
    )
RETURN
    FILTER ( Keys, [StationCode] <> "" )
DISTINCT
DISTINCT is the function to reach for, and VALUES is the trap sitting next to it. The two are identical except for one thing that matters here: VALUES returns the blank virtual row that the engine adds when a relationship has unmatched fact keys, and DISTINCT leaves that row out. Building a dimension out of VALUES would import the very blank member you are trying to eliminate.
UNION
UNION concatenates and keeps duplicates, so MSP would appear three times without the outer DISTINCT. It also matches its arguments by position rather than by name, which is why Technicians[HomeStation] can sit in the middle with a different column name and still land in the same column.
FILTER
FILTER is the operator that applies here, because it iterates whatever table expression you hand it. The habit to break is reaching for CALCULATETABLE. That function works by modifying filter context over model tables, and Keys is an anonymous table held in a variable, which has no filter context to modify.
<> ""
One comparison against "" does the whole job. In DAX a true blank compares equal to an empty string, so that single test removes an empty text value and a real blank together. The obvious looking alternative, NOT ISBLANK, returns FALSE for an empty string and would let it through.
What is not here
One column comes back, StationCode, so this is not yet the five row table in Table 3.2. Wrap the result in ADDCOLUMNS with a SWITCH over the code to attach StationName and StationRole, then UNION that with a one row table constructor holding UNASSIGNED. SWITCH rather than a merge because a calculated table has no join step, and the mapping is small enough that hard coding it in the expression is readable. That is three more layers of DAX to reproduce two Power Query clicks, which is itself an argument for the next box.
Why this and not that

Power Query is the correct home for a built dimension and DAX is the fallback. Three reasons, in order of what they cost you. A calculated table is evaluated during refresh and stored in the model, so no query can reference it, column quality cannot profile it, and a second report cannot reuse it. The DAX version also has no access to the source, so it can only union what is already loaded, which forces you to import ShopCapacity as a model table even if you wanted it only for its station list. Last, and this is the one that bites in a design review, the dimension build becomes invisible: someone auditing the extract and transform layer sees six queries and no station logic anywhere, because it is hiding in a table definition. Use the DAX version when the queries are genuinely out of reach, and write a comment saying why.

Trace the station union by hand, row by row

The append stacks 8 rows from WorkOrders, 6 from Technicians and 7 from ShopCapacity, which is 8 plus 6 plus 7 = 21 rows before anything is removed. One of those 21 is the blank on WO-1005, leaving 20. Deduplicating 20 values leaves 4: MSP appears 4 plus 3 plus 3 = 10 times, TUS 2 plus 2 plus 2 = 6 times, LAS 1 plus 1 plus 1 = 3 times, PHX once, and 10 plus 6 plus 3 plus 1 = 20. Adding the UNASSIGNED member gives the 5 row DimStation. If your row count after deduplication is not 4, the trim step did not run or did not run first.

Load that table and the planner's chart changes. The fourth bar is now labelled Phoenix and carries the same 16 hours it always carried. Nothing about the arithmetic moved. The total was 176 before and it is 176 now, which is the point that makes this defect so easy to ship: the number you would have checked was already right. What the fifth row bought him is a bar he can point at and ask about.

Interview-level insight

A dimension is a contract about what values are allowed to exist. Building it from the union of every source that uses the key is what makes that contract true. Anyone can write a lookup table from the values they happened to see. The discipline is deriving it from every producer of the key, including the producers that generate no transactions at all. PHX is the one that generates none.

DimTrade, where planning and capacity keep different lists

The production controller asks the question the whole shop runs on: do we have the people for the work booked this quarter. You give him a chart with demand and capacity side by side, split by trade. Four bars, all of them comfortably inside their limit, meeting over in ninety seconds. The chart is missing a fifth bar, and the fifth bar is the only one worth talking about.

Meridian has a second key with exactly the same defect as the station code. It is worth working through, because the two sources that produce it sit on opposite sides of the shop and have never had to agree on anything. Start with what a trade is, since the word carries no meaning outside this industry. A trade is the skill group a technician works in: airframe, avionics, engine, NDT (Non-Destructive Testing, the inspection specialism that finds cracks and corrosion without dismantling the structure), and at some shops cabin. Everything about resourcing a hangar is split by trade, for one reason. Ten airframe technicians cannot do an avionics job. A headcount on its own tells you almost nothing about whether the work in front of you can be done.

Two extracts carry a trade code, and neither of them is a list of trades.

ShopCapacity
Supply, at station and month grain. Grain is the sentence that says what one row of a table means, and one row here means one station in one month. It comes out of the monthly planning workbook the resource manager owns. A capacity figure is normally headcount multiplied by shift hours multiplied by an availability factor that strips out holiday, sickness, training and time booked to no job, then split by trade. In this workbook the four trades arrive as column headers: Airframe, Avionics, Engine and NDT. Unpivoting turns a set of columns into rows, one row per column per original row, and until that unpivot runs "Airframe" is the name of a column instead of a value in one. You cannot build a relationship on a column name.
HeavyPreInput
Demand, at work order and trade grain. This is the heavy pre-input tab: the planner's work package for a base maintenance visit, assembled in the weeks before the aircraft physically arrives. Input, also called induction, is that arrival, so pre-input is everything the planner does while the aircraft is still flying. He pulls together four kinds of work: the routine task cards falling due in the window, the ADs (Airworthiness Directives, which are mandatory), the service bulletins and modifications the customer has bought, and the defects carried over from earlier visits. He puts an estimated manhour figure against each card. Then he rolls the total up per trade. One row is one work order and one trade. The figure is then frozen at induction, because a baseline that moves cannot measure anything. Here the trades are values in a column, and there are five of them: the four above, plus Cabin.

That fifth member is the one that matters, and it appears nowhere else in the model. WO-1004 is a cabin retrofit on N771QR at Tucson, carrying 12.0 planned hours. Three systems describe that one job in three vocabularies. The shop floor system types it Mod. The HMCC board records the service line as Cabin and IFE. The planner's pack calls the trade Cabin. HMCC stands for Heavy Maintenance Control Centre. That is what many airlines and MROs (maintenance, repair and overhaul organisations) call the function that owns the heavy schedule. Plenty of shops call the identical function production control, or base maintenance control, so do not expect the acronym to travel with you. IFE is In-Flight Entertainment, the seat-back screens and the head-end equipment behind them. None of those three words appears anywhere in the capacity workbook.

One caution about the figures before you model them. What Meridian calls available hours, other shops call planned, budgeted, estimated or sold. The same word can mean the frozen baseline in one report and the live forecast in the next. Every shop settles this locally and no industry standard settles it for them. So write down the definition your production control team actually uses, get it agreed in writing, and put it in the model description. Note also that the hours column is called PlannedHours in both extracts and means opposite things: demand in one, supply in the other. Name the measures apart even if you leave the columns alone. A report author browsing the field list then sees Available Hours and Capacity Hours, and cannot add them together by accident.

The union arithmetic is smaller than the station one. The capacity workbook names four trades, the pre-input pack names five, the union is five, and the single member that separates the two lists is Cabin.

  1. Reference FactCapacity, the query that has already unpivoted ShopCapacity, and reduce it to the trade column.
  2. Reference HeavyPreInput and reduce it to the trade column.
  3. Append the two into one stack. No rename is needed here, provided the unpivot named its output column Trade and did not leave the default name in place.
  4. Trim the text, then remove nulls and empty strings.
  5. Remove duplicates. Five rows remain, and that is the entire dimension.
  6. Stop. There is no attribute table to join and no unknown member to add.
MDimTrade
let
    // FactCapacity is ShopCapacity after the unpivot, so Trade
    // is a value here and a column header in the source
    FromCapacity =
        Table.SelectColumns( FactCapacity, {"Trade"} ),

    FromPreInput =
        Table.SelectColumns( HeavyPreInput, {"Trade"} ),

    Stacked =
        Table.Combine( {FromCapacity, FromPreInput} ),

    Trimmed =
        Table.TransformColumns(
            Stacked, {{"Trade", Text.Trim, type text}} ),

    NoBlanks =
        Table.SelectRows( Trimmed,
            each [Trade] <> null
                 and [Trade] <> "" ),

    DimTrade = Table.Distinct( NoBlanks )
in
    DimTrade
FromCapacity
Point at FactCapacity and not at Table.ColumnNames( ShopCapacity ). Reading the headers looks like the shorter route and it returns StationCode and Month along with the four trades, so you would have to strip two names by hand. That exclusion list is one more thing a human maintains, and the day planning adds a Notes column to the workbook it starts admitting a trade called Notes. Reading the unpivoted column instead means the values come from a column whose only content is trades.
Both named Trade
This works because the unpivot renamed its output. Table.UnpivotOtherColumns produces columns called Attribute and Value, and Attribute has to become Trade at that step, not at this one. Leave it as Attribute and Table.Combine aligns nothing: you get two columns, each mostly null, and Table.Distinct returns 4 plus 5 = 9 rows that all look plausible in the preview.
NoBlanks
Neither source has a blank trade today. The guard stays because the pre-input pack is a planner's workbook, and workbooks behave the way workbooks behave. A row with hours in it and the trade cell left empty is an ordinary Friday. DimStation got an UNASSIGNED member and this dimension gets none, because there is no blank here to catch. Add the member on the day the data needs it.
Table.Distinct
The key is the whole row, as it will be for DimCertification later in this chapter. Meridian has no trade master, no skill grouping and no rate band, so there is nothing honest to attach. Resist in particular the temptation to add a flag saying whether the trade appears in the capacity workbook. That is a fact about this quarter's rows, it will be wrong the moment planning rosters a cabin technician, and freezing it into a dimension puts a measurable thing where a descriptive thing belongs.
Trace the trade union by hand, row by row

The unpivot turns 7 capacity rows times 4 trade columns into 28 rows, so the capacity side contributes 28 trade values, 7 each of Airframe, Avionics, Engine and NDT. The pre-input pack contributes its 8 rows: Airframe 4 times, on WO-1001, WO-1003, WO-1006 and WO-1008, then one each of Avionics, Engine, Cabin and NDT. The append is therefore 28 plus 8 = 36 values, made up of Airframe 11, Avionics 8, Engine 8, NDT 8 and Cabin 1, and 11 plus 8 plus 8 plus 8 plus 1 = 36 confirms nothing was dropped on the way in. Deduplicating 36 values leaves 5. A result of 4 rows means you appended the capacity side only. A result of 9 means the two columns never shared a name.

Common mistake

Building the trade list from the pre-input pack alone and letting the coverage check bless it. Today that check passes. HeavyPreInput happens to name all four capacity trades as well as Cabin, so the check comes back empty against both facts and the model ships. The list is complete by accident rather than by construction. Delete one row, the 2.0 NDT hours on WO-1008, and the dimension drops to four members while the 13 planned NDT hours in the capacity workbook lose their home. A check that passes on today's rows tells you about today's rows. A rule that keeps passing next quarter is a different thing, and construction is what buys it.

The wrong way

Take the four column headers out of the capacity workbook and call that the trade list, on the reasonable sounding grounds that the resource manager is the person who owns trades.

Available hours by trade then reads Airframe 34.0, Avionics 4.0, Engine 5.0 and NDT 2.0. Those four add to 34.0 plus 4.0 plus 5.0 plus 2.0 = 45.0. The card above the chart says 57.0, because the unmatched 12.0 is still in the total, parked behind the blank member the engine added the moment it met a fact key the dimension did not contain.

No error, no warning, and the one work order in the quarter whose entire package is cabin work has no bar at all.

The fix

Union both producers. Five members, with Cabin among them whether or not anybody has rostered for it.

The same chart now reads Cabin 12.0 against a planned capacity of 0, alongside Airframe 34.0 against 80, Avionics 4.0 against 44, Engine 5.0 against 39 and NDT 2.0 against 13. The labelled rows add to the total, and the one line with a zero on the supply side is the line a planner reads first.

That 12.0 is 21.1 percent of the 57.0 available hours, computed as 12.0 divided by 57.0, and it sits on a single work order out of eight.

What you see in the report

With four members, a demand against capacity chart is four comfortable bars adding to 45.0 against 176 planned hours of capacity. Everything inside its limit, nothing to discuss, meeting over. Two things are wrong with that picture and only one of them is the dimension. The missing bar is the dimension. The other is that the 57.0 covers heavy and cabin work only, because light maintenance never gets a pre-input pack, so the demand side is understated by whatever the line work consumes and the chart flatters the shop twice over.

The comparison also holds only at trade and quarter grain, which is worth knowing before somebody asks for it by month. Capacity sits at station and month. A pre-input row has a work order, a trade and an hours figure, and no date of any kind. So a monthly demand against capacity chart has to borrow a date from the work order, and then decide which of the three dates on it counts. That is an easy problem to solve and a decision somebody has to make out loud. A chart that splits by month before anybody has made it is answering a question nobody asked.

Now the payoff, and it is an operations finding. Cabin carries 12.0 planned hours against zero planned capacity. Read that the way the production controller reads it. The work package says the cabin job needs twelve hours of somebody's time, and the roster for the quarter puts nobody in that trade at any of the four stations, in any month. That is his answer, and it is the opposite of the comfortable one his four bar chart gave him. The five member dimension made a fact that had been sitting in the data all along reachable by a visual. The gap itself was already there, and it stays there until somebody rosters for it. With a four member trade list, nothing in the report could have got near it.

Then stop short of the conclusion, because two different situations produce this identical row and nothing in the extracts separates them. Either nobody was rostered for cabin work, which is a resourcing gap somebody has to answer for before the aircraft is in the bay. Or the capacity workbook runs a coarser trade list than the planning module does, and the people who will do the job are already counted inside Airframe. Cabin work frequently uses trades other than airframe, which is the usual reason a cabin code turns up in a planning extract and is missing from a capacity workbook. Shops genuinely differ on whether cabin is a trade of its own or a specialism sitting inside another one. Your model has produced a question. Production control owns the answer, and it is worth having in writing before the number reaches a page.

One more detail sharpens the question, and stops short of settling it. The only labor ever booked against WO-1004 is 10.0 hours from TECH-07, an identifier that appears nowhere in the HR (human resources) extract. One row takes you exactly this far. The single job with no planned capacity is also the single job whose hours were booked by a technician the roster does not know about. Whether that means a contractor nobody set up in the system, or somebody mistyping a digit, one row of data cannot settle. That combination is worth raising with a human being.

Finish the build the way this chapter finishes every other one. The grain sentence is one row per trade that either producer names. The key is Trade, with 5 distinct values across 5 rows. The coverage check is two anti joins, one for each fact that uses the key. An anti join returns the rows on one side that have no match on the other, so it is the question "which keys does the fact use that the dimension has never heard of" written down. FactCapacity[Trade] holds 4 distinct values with none missing. FactPreInput[Trade], which is HeavyPreInput typed and keyed, holds 5 with none missing. Build the dimension from the capacity workbook alone and the second check returns exactly one row, Cabin, which is this whole section compressed into one output. The model figure later in this chapter leaves out DimTrade and FactPreInput, because that figure is the twelve table core model and the pre-input pack arrives with the heavy maintenance extension. FactCapacity is drawn there, with its Trade column listed and no trade dimension yet attached to it.

DimAircraft, where the dimension you were given is the incomplete one

The finance manager wants labor hours split by aircraft type, because she is preparing a customer conversation about the A320 fleet. Your chart gives her three types adding to 50.0 hours. She has already seen the quarter total on another page and it says 62.0. Twelve hours have gone somewhere between the two pages, and she asks the obvious question.

Here the source did ship a dimension, which makes this the most dangerous case in the chapter. AircraftRegistry has 6 tails, maintained on a spreadsheet by the customer service desk, and it is stale in the way fleet spreadsheets always are. WorkOrders references 5 distinct tails. The two lists overlap, and neither one contains the other.

Notice the asymmetry. N120CE and N553KD sit in the registry with no work orders against them, and that costs you nothing. A dimension member with no facts is legitimate. It returns blank measures and drops out of visuals, unless you switch on "show items with no data". N338WA is the expensive case, and it is where the finance manager's twelve hours went. The fact references a key the dimension does not contain, and the engine has to put those rows somewhere.

MDimAircraft
let
    Registry =
        Table.SelectColumns( AircraftRegistry,
            {"ACREG", "AircraftType", "Operator",
             "EngineType", "YearBuilt"} ),

    FactTails =
        Table.Distinct(
            Table.SelectColumns( WorkOrders, {"ACREG"} ) ),

    // registry first: its rows win the deduplication
    Stacked = Table.Combine( {Registry, FactTails} ),

    Deduped = Table.Distinct( Stacked, {"ACREG"} ),

    Filled =
        Table.TransformColumns( Deduped,
            {
                {"AircraftType",
                 each if _ = null then "Unknown type"
                      else _, type text},
                {"Operator",
                 each if _ = null then "Unknown operator"
                      else _, type text},
                {"EngineType",
                 each if _ = null then "Unknown engine"
                      else _, type text}
            } )
in
    Filled
Stacked
Table.Combine with mismatched column sets fills the absent columns with null, so the N338WA row arrives carrying an aircraft registration and four nulls. That is the shape you want going into the deduplication.
Deduped
Append order decides the outcome here. Table.Distinct with a key column keeps the first row it meets for each key, so putting Registry first means the described rows win. The bare fact key then survives only where the registry had nothing to say. Reverse the append order and you wipe out the attributes for all five tails that appear in both lists.
Filled
Literal text, not a blank. "Unknown type" is a value a report reader can see, filter on, count and complain about. A null is a value they scroll past.
YearBuilt
Deliberately left null. Every other unknown gets a label, but a year is a number that measures will average, and inventing 0 or 1900 would poison the average silently. When the unknown value feeds arithmetic, leave it blank; when it feeds a label, fill it.

Now the payoff. Put the two versions of the chart side by side, because the principle is easier to believe with the arithmetic attached. The measure is total labor hours, sliced by DimAircraft[AircraftType], with the filter travelling from DimAircraft to FactWorkOrder to FactLabor.

The wrong way

Load AircraftRegistry as the dimension, unchanged, six rows.

The three real types sum to 23.5 plus 9.0 plus 17.5 = 50.0. The remaining 12.0 belongs to WO-1006 on N338WA and sits in a row with no name, no operator and no way to drill into it.

The fix

Load the built DimAircraft, seven rows, with the recovered key labelled.

Same 62.0 total, same 12.0. The 12.0 now carries a label the finance manager can act on, and clicking it filters to N338WA and WO-1006. Her missing twelve hours were on an airframe the registry has never listed.

What you see in the report

Both versions total 62.0, which is why this defect survives review. Nobody reconciles a breakdown against its own total. The reader sees three aircraft types adding to 50.0. The fourth row never registers, because a blank category label reads as visual noise, and she leaves believing the fleet consumed 50 labor hours. That understates it by 19.4 percent, computed as 12.0 divided by 62.0. The engine did nothing wrong here. It added the blank member because you asked it to relate a fact key to a dimension that did not contain that key.

Rule of thumb

Never let a fact contain a key value that the dimension does not contain. Not a blank, not an orphan, not a code that arrived last Tuesday. If you cannot describe the value, add it anyway with an explicit unknown label, because a labelled unknown gets investigated and an unlabelled blank gets ignored.

That rule is only useful if you test it, and the test is three lines of DAX you can run in a table visual after every refresh.

DAXCoverage assertion, should return zero rows
Missing Aircraft Keys =
EXCEPT (
    DISTINCT ( FactWorkOrder[ACREG] ),

Why this and not that

EXCEPT and not a FILTER wrapped around NOT CONTAINS. Both return the same rows. EXCEPT is a set operator, so the engine resolves it as one set difference rather than iterating the fact key list and probing the dimension once per value. It also reads as the question you are actually asking: which fact keys are missing from the dimension. The CONTAINS form states that question backwards. It invites the classic error of putting the arguments in the wrong order, which returns dimension members with no facts, a completely different and usually harmless condition. Note that EXCEPT matches columns by position, so both arguments must be single column tables in the same order.

DimPart, built out of the fact that uses it

The finance manager comes back a week later wanting parts cost grouped by category, so she can see how much of the quarter went on brakes. Meridian has no part master anywhere. Nobody holds a list that says BRK-2210 is a brake. You have seven rows in a stores issue log and a customer waiting.

PartsIssued has 7 rows carrying 4 distinct part numbers, and that is the entire universe of parts as far as this model is concerned. When the only producer of a key is a single fact, the fact is where the dimension comes from.

DimWOType, three rows and the argument for bothering

The shift supervisor filters the page to LAS to look at one station, and the work order type slicer beside it loses two of its three options. He calls you and says the report is broken. The slicer is behaving exactly as it was built to, he is right to call, and the fix is a three row table.

WorkOrders[WOType] holds three values across eight rows. Scheduled sits on WO-1001, WO-1003, WO-1006 and WO-1008. AOG (aircraft on ground, unplanned work that the shop learns about when the defect is reported) sits on WO-1002, WO-1005 and WO-1007. Mod sits on WO-1004 alone. Meridian has no work order type master anywhere, and the column has no blank and no orphan in it. This is the smallest built dimension in the model and the one most likely to be skipped, so be explicit about what building it buys and what it costs.

The case for skipping it is real. WOType is already on the fact, it has three values, and dragging FactWorkOrder[WOType] onto a slicer works today. That is the degenerate dimension argument from Chapter 1, and for a key with no attributes it is the right call. The question is whether this key has attributes, and it does: a definition that operations cares about, a display order that is not alphabetical, and the fact that AOG means unplanned while the other two do not.

He was right to call: with the fact column feeding the slicer, he could not tell whether Mod was absent because LAS does no mods, or because somebody had removed the option.

If Meridian had shipped a work order type master, this whole section would be one merge. Whatever you gain here, you do not gain it in bytes. Three distinct values cost two bits per row on the fact either way, and building the dimension leaves that column exactly where it was.

DimCertification and BridgeTechCert, from a delimited column

The production controller wants to know how many hours went to work needing an NDT ticket, because he is deciding whether to send a second technician for the qualification. The certifications are in the model. They are sitting three to a cell in one text column, which means no visual can group by them. Getting from that column to his number takes one new table and one uncomfortable piece of arithmetic.

Technicians[Certifications] holds multiple values per row, delimited by a semicolon. TECH-04 carries "A&P; Avionics; Engine Run". A&P is Airframe and Powerplant, the Federal Aviation Administration mechanic certification. Meridian uses A&P and the European licence categories appear nowhere, which tells you which authority the shop answers to. A column shaped like this cannot be filtered or grouped reliably. "Avionics" as a substring appears inside three different technicians' text, and a text filter for it stops matching anything useful the moment somebody reorders their list. Split it to rows.

MBridgeTechCert
let
    Kept =
        Table.SelectColumns( Technicians,
            {"TechnicianID", "Certifications"} ),

    // split on the semicolon only, then trim
    ToList =
        Table.TransformColumns( Kept,
            {{"Certifications",
              each Text.Split( Text.From( _ ), ";" ),
              type list}} ),

    ToRows =
        Table.ExpandListColumn( ToList, "Certifications" ),

    Clean =
        Table.TransformColumns( ToRows,
            {{"Certifications", Text.Trim, type text}} ),

    Renamed =
        Table.RenameColumns( Clean,
            {{"Certifications", "CertCode"}} ),

    BridgeTechCert = Table.Distinct( Renamed )
in
    BridgeTechCert
Text.Split on ";"
Split on the delimiter you can rely on, then trim what is left. Splitting on "; " works on every current row, because every current row has the space. Then a single row typed as "A&P;NDT" produces one certification called "A&P;NDT" and quietly creates a fifth member of DimCertification.
ExpandListColumn
This is the step that changes the grain. Six technician rows become ten technician and certification rows, which is why this output cannot live on DimTechnician: loading it there would duplicate TECH-04 three times and break the uniqueness property from the start of this chapter.
Table.Distinct
Guards against the same certification being listed twice on one technician, which is a data entry outcome you will eventually meet. A duplicate pair in a bridge multiplies that technician's contribution to a certification, and unlike a duplicate dimension key the engine will not warn you.

DimCertification is then the distinct CertCode from this output: A&P, Avionics, NDT and Engine Run, four rows. Build it from the bridge rather than typing it, so that a new certification appearing in HR cannot reach the bridge without also reaching the dimension. Two queries, one dependency, and the coverage property from the start of this chapter now holds by construction. Vigilance stops being part of the design.

in

Reference the bridge, not Technicians. The bridge has already been split, trimmed and deduplicated, so the dimension inherits every one of those cleaning steps for free and cannot drift away from the values the bridge actually holds. No attributes
The code is the whole row. Meridian has no certification master, no issuing authority, no expiry, so there is nothing honest to add and a fabricated grouping column would be worse than none. Add columns when a source for them exists.
The cost
Deriving the dimension from the bridge means a certification that nobody currently holds cannot appear in the model at all. If Meridian needs to report on a qualification the shop is trying to hire for, this build cannot show it, and you will need a maintained list upstream of the bridge instead. That is a real limitation of the pattern, not a detail to wave past.

Row counts per technician are 2, 1, 2, 3, 1 and 1, and 2 plus 1 plus 2 plus 3 plus 1 plus 1 = 10. A Bridge is its own kind of table, sitting outside Fact and Dimension both. It holds a relationship written down as rows, one row for each pairing that exists, and that is the only way a relational model can carry a many to many association. It has no measures on it, and it has no descriptive attributes and no single column key either, which is why it fits neither of the other two categories. A bridge exists to be traversed by a filter, and nobody should be reading it. Hide it from the field list. An author who drops BridgeTechCert[CertCode] onto a visual instead of DimCertification[CertCode] gets a result that looks plausible and behaves differently under cross filtering.

Now the production controller gets his NDT number, and it comes with a warning about the arithmetic. Grouping the 62.0 total labor hours by certification produces rows of 39.0, 10.5, 12.0 and 23.5, which add to 85.0. Those four rows are the correct answer to the question "hours performed by somebody holding this certification". TECH-04 holds three certifications, so every hour he books lands under all three of them. The number the production controller came for is the NDT row, 12.0 hours, and it overlaps the other rows on purpose. Those 12.0 hours are all TECH-01's, because TECH-01 and TECH-03 are the only two NDT holders and TECH-03 booked nothing this quarter. Every date column in the model needs one shared calendar, and there are six date columns across four facts. Meridian's period runs 2025-01-01 to 2025-03-31, which is 31 plus 28 plus 31 = 90 days.

Mark as Date Table, and what it actually does

Marking a table as the date table changes how the engine behaves, which is why the finance manager's card came back wrong. You nominate the date column, and the engine records that this column is a contiguous, unique, day grain date key for the whole table. The consequence that matters lives inside the time intelligence functions. DATESYTD, TOTALYTD, DATEADD and SAMEPERIODLASTYEAR all work the same way. Each one returns a set of dates and applies that set as a filter. To do it safely, each one must first clear whatever date filters are already in play. When the table is marked, that implicit clearing is a REMOVEFILTERS over the entire date table, every column of it. When the table is unmarked, the clearing reaches only the date column passed into the function.

That difference is the whole reason the setting exists. Put DimDate[MonthName] in a slicer, select Feb, and ask for a year to date total. With the table marked, the function clears the February filter along with everything else on DimDate, and the year to date figure comes back correct. Leave it unmarked and the February filter survives. It intersects with the year to date date set, and you get February's number wearing a year to date label. That is exactly what happened on her page, and marking the table is the whole fix.

Contiguity is the price of that guarantee. Time intelligence treats the date column as a continuous axis and shifts along it by position, so a missing day breaks every shift that crosses it. Power BI therefore refuses to mark a table with gaps, duplicates or blanks in the nominated column. Filtering weekends out of the calendar is how people usually break this. Exclude weekends with a column such as IsWeekend, never by deleting rows.

Here is the inconvenient consequence for Meridian specifically. The calendar covers 90 days, so any measure that shifts a year backwards returns blank. There are no 2024 rows to shift to. Year over year is out of reach in this model, and no amount of DAX will bring it into reach. If the business asks for it, the answer is to extend the calendar and load prior year facts. A cleverer measure will not do it.

Testing the tables you built

You are in a design review and somebody asks the fair question: how do you know these eight tables are right. You have about a minute, and the answer that works is a table of checks that ran during the last refresh. Saying that you built them carefully buys you nothing in that room.

Everything above is a claim. Eight tables now exist that no source system shipped, and each one asserts a grain, a unique key and a complete list of allowed values. Grain is the sentence that says what one row of the table means. Chapter 1 tested the grain of the six source tables with a candidate key check, which is a count of distinct key values set against a count of rows. Run that same check here. Then run the second half of it, the half the source tables did not need: does the key list cover every value the facts actually hold.

Start with the sentences, because a built table needs a grain sentence exactly as much as an extract does. It is easier to write a wrong one when you built the table yourself. You already know what you meant, so nobody checks.

Seven of the eight have a single column key and pass. The bridge is the one that cannot, and that is by design. TechnicianID alone has 6 distinct values across its 10 rows and CertCode alone has 4, so neither column identifies a row and only the pair does. Six technicians times four certifications gives 24 possible pairs, of which 10 exist. A table whose only key is the whole row is the shape of a bridge, and it is why a bridge can never sit on the one side of a relationship.

Note what the DimCertification sentence gives away. It says "held by at least one technician on the roster", not "recognised by Meridian", because the query derives the list from the bridge. The sentence is the honest description of what the query built, and writing it forced the limitation into the open. That is most of what grain sentences are for on tables you assembled yourself.

Now the coverage half. The check is one anti join per relationship, so write it as a function too and point it at every pair.

MfnMissingKeys
// fnMissingKeys( FactLabor, "TechnicianID",
//     Technicians, "TechnicianID" ) returns one row: TECH-07
let
    fnMissingKeys =
        ( Fact as table, FactKey as text,
          Dim as table, DimKey as text ) as table =>
        let
            FactKeys = Table.Distinct(
                Table.SelectColumns( Fact, {FactKey} ) ),
            DimKeys = Table.Distinct(
                Table.SelectColumns( Dim, {DimKey} ) ),
            Missing = Table.NestedJoin(
                FactKeys, {FactKey},
                DimKeys,  {DimKey},
                "match", JoinKind.LeftAnti )
        in
            Table.SelectColumns( Missing, {FactKey} )
in
    fnMissingKeys
JoinKind.LeftAnti
The anti join is the question written down in one step, and it never carries the matched dimension rows through only to throw them away. The alternative people write is JoinKind.LeftOuter followed by an expand and a filter for nulls. That outer form is three steps, and three steps can be reordered by the next person to open the query.
FactKey and DimKey
Two separate parameters because Table.NestedJoin takes a key list for each side and the two columns do not have to share a name. That is not hypothetical here: Technicians[HomeStation] and DimStation[StationCode] hold the same key under two names, and a function that demanded matching names could not check that pair at all.
Table.Distinct on both sides
On the dimension side it is redundant if the dimension is really a dimension. Leave it in anyway: this function gets pointed at half finished tables, and a duplicated dimension key would otherwise multiply the fact key rows in the join and give you an answer whose row count means nothing.
Making it fail
Wrap the call as if Table.IsEmpty( fnMissingKeys( ... ) ) then Source else error "coverage" and the refresh stops. Do that where a gap is genuinely unacceptable. Meridian is the case where you must not: TECH-07 and WO-1009 are known, tolerated orphans, so a hard error would block every refresh over data the business considers normal. Put the output on a page somebody reads instead, and reserve the error for a dimension you control end to end.
Against the DAX form
The EXCEPT expression earlier in this chapter asks the same question, at query time, over data that is already loaded. Use it when the queries are out of your hands. This version answers during refresh, before anybody has looked at a number, which is where you want the answer if you can get it there.

FactParts charges 4,900 dollars to WO-1009, a work order Meridian has never raised. Both are fixed the same way DimAircraft was, by appending the distinct fact key and labelling it, and Chapter 19 covers what that does to the numbers on a report page. So that is your answer in the design review. The table above found both of them during a refresh, before anybody sat down in a meeting.

Read the ClosedDate row carefully as well, because a zero there is easy to misread. Six distinct close dates, no missing keys, and two work orders, WO-1004 and WO-1008, that carry no close date at all. A foreign key is the column on the fact that points at a dimension, and ClosedDate is one. A blank foreign key is not an orphan. It matches nothing, it contributes to nothing, and this check will never report it. Counting closed work orders therefore needs a test of its own, and a coverage check will not supply it.

Why DimStation needs both fact columns checked, not one

Take the two station rows of Table 3.12 apart. FactWorkOrder[StationCode] holds MSP, TUS, LAS and, after the blank on WO-1005 is mapped, UNASSIGNED. Four distinct values, all present in DimStation. FactCapacity[StationCode] holds MSP, TUS, LAS and PHX. Also four distinct values, also all present. Neither fact uses all five members, and no single fact would have told you the dimension was complete.

Now build DimStation from the work orders alone, which is the shortcut in the Common mistake box at the top of this chapter, and re-run both rows. Against FactWorkOrder it still reports zero missing, so the check passes and you ship. Against FactCapacity it reports one: PHX, carrying 8 plus 4 plus 3 plus 1 = 16 planned hours. Planned hours by station now reads MSP 90, TUS 50, LAS 20 and a blank row of 16, and the quarter total of 176 is still correct, which is exactly why nobody catches it.

The UNASSIGNED member goes the other way. It appears in FactWorkOrder and never in FactCapacity, because planning does not publish hours for a station that does not exist. A dimension member with no rows in one of its facts is normal, and a coverage check only ever reads in one direction: from the keys a fact uses, to the list the dimension allows.

Those two station rows are what the word conformed means in practice. DimStation is conformed because one member list, one set of codes and one set of names serves both FactWorkOrder and FactCapacity. MSP therefore means the same thing on both sides of a utilisation figure, and a single slicer drives both. The same holds for DimDate, which serves six date columns across four facts, and for DimTechnician, which serves FactLabor and the bridge. Every dimension here is conformed by construction, because each key list was built from the union of every producer of the key. Whichever table you happened to open first has no say in it.

The counter case is worth naming, so the word does not turn into decoration. Build a station list from WorkOrders for the work order report, and a second one from ShopCapacity for the planning report. Both reports are individually correct. Put them side by side and MSP reads 34.5 hours against 90 planned in one, and 34.5 against 90 in the other, right up until the day somebody adds PHX to the second list and leaves the first alone. Two lists that agree today are still two lists, and two lists drift.

Interview-level insight

Conformance is a property of the member list, not of the relationship. Two facts joined to two separate station tables holding identical values will produce identical numbers and still be unconformed, because nothing keeps them identical: the next refresh, the next station code, the next person to edit one query. Test for conformance with one question. Is there exactly one query that decides what a station is? Whether the numbers currently agree is a weaker question, and it is the one people ask instead. At Meridian the answer to the real question is DimStation, whose inputs are all three producers of the code, which is why PHX cannot be lost and a blank cannot get in.

CrewCodeMap, the table that exists because you typed it

The resource manager wants hours by crew before his Monday call. You have the tables, so you build it in four minutes. Four rows come back. Three carry a crew name, the fourth carries no label at all, and 10.0 hours are sitting in it. He points at the unlabelled row and asks whose crew that is. Nobody at the table can answer him, and the reason is a spreadsheet on your laptop.

Two tables produce that visual. CrewAssignment comes out of the roster system and has 7 rows, one per technician, each carrying a crew code. A crew code is the shop's identifier for a working team, and it looks like CRW-AF1. CrewCodeMap has 6 rows and turns a crew code into two readable things: a crew name and a service line. A service line is the kind of work Meridian sells, and there are four of them, Line, Light, Heavy, and Cabin and IFE. Almost every planning number the shop reports is grouped by service line, so the map decides where the hours land.

Built Every key list in this chapter so far came out of a column that some system produces. The station codes come from three extracts, the part numbers come from the stores issue log, the certifications come from an HR column. CrewCodeMap breaks that pattern. The roster system issues the crew codes and nothing anywhere issues their meaning. No source system holds this table, no extract refreshes it, and the dataset records its source as the analyst. That is you. Six typed rows decide the service line of every hour that reaches a report through a crew.

Two lists of six that overlap on five. The roster uses 6 distinct crew codes across its 7 technician rows, the map holds 6 crew codes, and only 5 of them appear on both sides. That is the same shape as DimAircraft earlier in this chapter, where the registry held 6 tails and the work orders referenced 5 and the union came to 7. The difference is that the registry has a keeper at the customer service desk. The crew map has you.

Read the two red rows, because they are the two ways a mapping table goes wrong and they point in opposite directions. CRW-XX9 is on the roster and missing from the map, so the 10.0 hours TECH-07 booked to WO-1004 have no crew name and no service line. That is 16.1 percent of the quarter, computed as 10.0 divided by 62.0, against a visual whose total still reads a correct 62.0. Look back at Table 3.12 and you will find the same technician in the red row there: FactLabor books hours to TECH-07 and the HR extract has never heard of him. The roster system is the one list that does know him, and it puts him on CRW-XX9. So two lists have a hole, the HR extract and the crew map, and both holes sit on the same 10.0 hours.

CRW-LT2 is the other direction. Light Maintenance B is in the map and no technician is assigned to it, so it contributes nothing to any measure. A dimension member with no facts is ordinary and this chapter has already kept two of them on purpose, PHX with its 16 planned hours and no work orders, and N120CE with no activity at all. What separates those from CRW-LT2 is ownership. PHX sits in a workbook the resource manager maintains, so you can ask him whether Phoenix is a real station and get an answer. Nobody maintains the crew map, so nobody can tell you whether Light Maintenance B is a crew that exists and is currently unstaffed, or a crew that was disbanded last spring and never deleted. The row is evidence that the map and the roster have drifted, and the evidence has been sitting there quietly.

Common mistake

Tidying the map. A row with no hours against it looks like clutter, so during a cleanup somebody deletes CRW-LT2 and the file gets shorter. What went with it was the only visible sign that the typed map no longer matches the roster. The next report reads clean, and the question of whether Light Maintenance B still exists is now unaskable, because there is nothing left to ask about. Keep the row. Let the check flag it every refresh until a human answers.

So hold the map as a proper table with a proper build, the same as every other dimension in this chapter. Seven steps, and the last one happens outside Power Query altogether.

  1. Move the map into a workbook in a shared location, on one worksheet, formatted as a named Excel table called CrewCodeMap with the three columns it has today.
  2. Create a query parameter called CrewMapPath holding the full path to that file, so the path lives in one place a person can see.
  3. Load the named table, set the three columns to text, trim the crew code and the service line, and drop any row with a blank crew code.
  4. Assert that the crew code is unique and fail the refresh when it is not.
  5. Reference that query and append a labelled row for every crew code the roster uses that the map has no entry for. This is the DimAircraft append from earlier in this chapter, done again on a different key.
  6. Build the exception query, load it, and put it on a page the resource scheduler actually opens.
  7. Write down who owns the map and how a change to it gets agreed.
MCrewCodeMapSource
let
    // one workbook, one named table, one owner
    Source =
        Excel.Workbook(
            File.Contents( CrewMapPath ), true ),

    Map =
        Source{[ Item = "CrewCodeMap",
                 Kind = "Table" ]}[Data],

    Typed =
        Table.TransformColumnTypes( Map,
            {{"CrewCode", type text},
             {"CrewName", type text},
             {"ServiceLine", type text}} ),

    Trimmed =
        Table.TransformColumns( Typed,
            {{"CrewCode", Text.Trim, type text},
             {"ServiceLine", Text.Trim, type text}} ),

    NoBlanks =
        Table.SelectRows( Trimmed,
            each [CrewCode] <> null
                 and [CrewCode] <> "" ),

    CrewCodeMapSource =
        if Table.IsDistinct(
               Table.SelectColumns( NoBlanks, {"CrewCode"} ) )
        then NoBlanks
        else error "CrewCodeMap: duplicate crew code"
in
    CrewCodeMapSource
CrewMapPath
A query parameter and not a path typed into the step. The file will move, because files that people edit always move, and a parameter turns that into one edit in a dialog instead of a hunt through M under time pressure. Note where the file has to live: somewhere the resource scheduler can open it. A mapping only one person can reach has already failed, whatever the query does.
Kind = "Table"
Point at a named Excel table inside the workbook, not at the worksheet. Kind = "Sheet" reads the used range, so the day somebody types a note two rows under the data, that note arrives as a crew code with a null service line. A named table has an edge the person editing the file can see on screen, which is the only kind of boundary a hand maintained file ever respects.
Trimmed
Both text columns, for the reason this chapter keeps repeating. "CRW-LT1 " and "CRW-LT1" are one crew code to your eye and two to a join. A person typing into a spreadsheet produces trailing spaces the way a system never does, and ServiceLine gets the same treatment because it is the value every planning visual groups by.
Table.IsDistinct and error
The Making it fail note above said to reserve a hard refresh failure for a dimension you control end to end. This is that dimension. TECH-07 and WO-1009 are orphans the business tolerates, so blocking a refresh over them would be wrong. A crew code typed twice is your own defect in your own file. It fans every technician on that crew across two rows. Stop the refresh and fix the file.
Why not an inline table
DimStation keeps its four station names in an inline #table written into the query, and that was defensible: four rows, no other editor, no expected change. The crew map fails both halves of that test. The resource scheduler has to be able to read it, and the row that is missing today can only be filled in by him. A mapping that changes on somebody else's schedule belongs in data, where they can reach it.

The second query is short enough to describe. Reference CrewCodeMapSource, run the coverage check to find the crew codes the roster uses that the map has no row for, add CrewName as "Unknown crew" and ServiceLine as "Unmapped", and append. That is the move that recovered N338WA into DimAircraft, applied to a different key. The loaded CrewCodeMap then has 7 rows, and the 10.0 hours reach a report under a label somebody can click instead of a blank somebody scrolls past.

Now the check, and it is the piece most people never write. Point fnMissingKeys at the crew code in both directions.

MCrewMapExceptions
let
    NotMapped =
        fnMissingKeys( CrewAssignment, "CrewCode",
            CrewCodeMapSource, "CrewCode" ),

    NotStaffed =
        fnMissingKeys( CrewCodeMapSource, "CrewCode",
            CrewAssignment, "CrewCode" ),

    Flagged =
        Table.AddColumn( NotMapped, "Issue",
            each "On the roster, missing from the map",
            type text ),

    Idle =
        Table.AddColumn( NotStaffed, "Issue",
            each "In the map, nobody assigned to it",
            type text ),

    CrewMapExceptions =
        Table.Combine( {Flagged, Idle} )
in
    CrewMapExceptions
Called twice
The first call is the ordinary coverage check from the previous section, keys used against keys allowed. The second call swaps the arguments, which the EXCEPT box earlier in this chapter described as the classic error, returning dimension members with no facts, a usually harmless condition. On a table you type by hand it is the interesting one. It is how you learn that the map has stopped matching the roster while every number on every page still adds up.
CrewCodeMapSource
Point the check at the typed file, before the recovered row is appended. Run it against the loaded CrewCodeMap instead and it returns nothing at all, because that table already contains a row for CRW-XX9 that the query invented. A dimension that heals itself hides the gap it healed. Check the source, load the healed version, and never let the two swap places.
Issue
Two plain English sentences instead of a code or a flag. The person who can fix either row reads a page, not your query, and "On the roster, missing from the map" tells him what to do without a legend. A column called ExceptionType holding 1 and 2 would need you in the room.
Table.Combine
Both tables carry CrewCode and Issue under the same names, so the append stacks them into one list. Same rule as the station union at the top of this chapter. Table.Combine aligns on column name, so a rename in one branch and not the other gives you two half empty columns and a result that looks fine in the preview.

Here is the part the query cannot do. The check tells you CRW-XX9 exists and is unmapped. It cannot tell you whether that crew does light work or heavy work, and no amount of M will decide it, because the fact is not in any file you can read. Somebody in the roster office knows. Until you ask, the honest label for those 10.0 hours is Unmapped, and a report that shows an Unmapped row is doing its job. The technical fix makes the gap visible. The gap itself closes in a conversation.

That is the governance point, and it is worth stating flatly because it is the one thing in this chapter you cannot solve with a query. This map has no owner, no change control and no test. Without an owner, the day a new crew code is issued nobody is responsible for adding it, and your first warning is a blank row in a meeting. Without change control, nobody records who changed a service line or when, so a number that moved between two months has no explanation anybody can retrieve. Without a test, both kinds of drift stay invisible: codes arriving upstream that never reach the map, and rows in the map that stopped meaning anything. A mapping table with those three holes in it rots quietly, one row at a time, while every total on every page keeps reconciling. Nothing breaks, so nothing gets escalated.

So fix it in the shop as well as in the model. Name a person in resource scheduling who owns the crew list, and get his agreement in writing that a new crew code comes with a service line on the day it is issued. Put CrewMapExceptions in front of him on the same cadence as the month end submission, since he is already looking at hours then. Add two columns to the file that the model will never load, one for who last changed the row and one for when. None of that is Power Query, and all of it is the reason the map still works in a year. The most fragile object in a Meridian dashboard is six rows long, it lives in a spreadsheet, and the tool that keeps it alive is a named human being.

Which answers the resource manager, most of the way. The unlabelled 10.0 belongs to TECH-07, whose crew code is CRW-XX9, and after the append the row on his visual reads Unknown crew instead of nothing. Which service line those hours belong to is a question for the roster office, and you can now put it to them in one sentence with the number attached.

Reference, duplicate, and keeping staging out of the model

Everything above depends on one habit. Use Reference, not Duplicate, when a query starts from another query's output. Duplicate copies the M script, so you get two scripts that agree today and drift the first time somebody fixes a type conversion in one of them. Reference points at the upstream result instead, so a change made once flows downstream to everything built on it.

A reference re-evaluates, and that is the cost you pay. Each downstream query triggers its own run of the upstream chain, so three references over WorkOrders can mean three reads of the source. On eight rows that is free. On eight million rows it is expensive, and the fix is a staging layer that lands the data once. Chapter 5 covers that layer along with query folding. Turn off Enable load on every staging query. A query with load disabled still runs during refresh and still feeds its consumers. What it stops doing is occupying model memory and offering report authors a half finished table to build visuals on.

Performance note

Built dimensions are small: DimStation 5 rows, DimPart 4, DimAircraft 7, DimDate 90. Storage is the smaller bill here. The one you pay is refresh time. Every union re-reads its sources, so the station list alone touches WorkOrders, Technicians and ShopCapacity again, on top of the reads that load the facts. Set that against a breakdown which quietly excludes 12.0 of 62.0 hours and it is an easy trade. Set it against a source that takes four minutes to query and you will want the staging layer first.

What to remember
  • A dimension needs four properties: a unique key, no blank in the key, complete coverage of every key value in every fact that references it, and stability of meaning across refreshes. Coverage is the one people miss.
  • Build the key list from the union of every source that produces the key. At Meridian only ShopCapacity knows PHX exists, and only WorkOrders knows N338WA exists.
  • An unmatched fact key keeps its measure and loses its label. Labor hours by aircraft type totals 62.0 either way, and with the incomplete registry the visible types sum to 50.0 while 12.0 sits in a blank row.
  • Fill unknown text attributes with a readable label, leave unknown numeric attributes blank so nothing averages them.
  • A bridge is a relationship stored as a table. It has no measures and no unique key, it belongs hidden, and it makes category subtotals exceed the grand total by design.
  • Build the small dimensions too. DimWOType holds three rows that were already on the fact, and what it buys is a stable slicer list, a non-alphabetical sort order and one place to say what AOG means.
  • Every built table gets the same treatment as a source table: a grain sentence, a candidate key check, and then a coverage check per relationship. Fourteen of the sixteen key relationships in the core model come back clean, and the two that do not are TECH-07 and WO-1009.
  • Conformed means one query decides what a station is, not that two station lists currently agree. Checking DimStation against FactWorkOrder alone passes and still loses PHX and its 16 planned hours.
  • The one table in this model that no system produces is CrewCodeMap, six rows you type yourself, and it decides the service line of every hour that reaches a report through a crew. CRW-XX9 is missing from it, so 10.0 of the 62.0 hours land unmapped, and CRW-LT2 sits in it with nobody assigned. Give it an owner first, then a labelled unknown member, then a check that runs in both directions.
  • Mark as Date Table gives time intelligence functions an implicit REMOVEFILTERS across the whole date table. Skip it and year to date measures silently inherit filters from your own month and year columns.
  • Power Query is the right home for a built dimension. The DAX calculated table is the fallback for when the queries are out of your control, and it hides the logic from anyone auditing the model.
