Part 4 . Evaluation context and DAX

10Calculated column or measure

After this chapter you will be able to look at any Meridian requirement and decide, before writing code, whether it belongs in a calculated column, a measure, a calculated table or Power Query. You will also be able to name the exact symptom each wrong choice produces, and prove it with the row counts in the model.

The finance manager wants one number. What did Meridian quote for the quarter? You put a card on the page and it reads 46,600. She writes it down and it goes on a slide. The true figure is 38,100.

The card is doing its arithmetic correctly. The mistake was made three weeks earlier, when somebody chose to store a value in a column instead of computing it in a measure. A calculated column and a measure share one formula bar and run on completely different machinery underneath. Most of the reporting bugs that get blamed on DAX come from that choice made wrong. Two failures account for nearly all of them: values that refuse to respond to a slicer, and totals that come out too high. This chapter works through both, and it ends with the 38,100.

One difference, and everything else follows from it

Start with the calculated column. A calculated column is a new column you add to a table with a DAX formula, and the engine evaluates that formula once per row of the table. The evaluation happens during data refresh, which is the load step that pulls source data into the model. It runs before any report is open and before any user exists. The result is written into the model as a real column. It is encoded and compressed next to the columns that came from the source, and it occupies memory whether a single visual uses it or not. Once refresh finishes, the value is frozen until the next refresh.

Now the measure. A measure is a DAX formula that returns one value, and the engine evaluates it once per cell, at query time. Nothing is stored. When a visual renders, the engine works out the filter context for each cell of that visual. Filter context is the set of filters in force at that moment, arriving from slicers, from the rows and columns of the visual, and from page filters. The engine applies that filter context and runs your expression inside it. Change a slicer and every cell is recomputed against a different filter context. The measure has no memory of yesterday and no existence outside the query that asked for it.

That is the whole difference between a calculated column and a measure. Everything else in this chapter follows from it. Hold those two paragraphs in your head and you can derive most of the guidance yourself, with nothing left to memorise.

Symptom one: a number that ignores the slicer

The shift supervisor at TUS wants a leaderboard. Who logged the most labour hours, ranked, so he can put it on the wall. You build it, he opens it, and he clicks TUS in the station slicer. The technician at the top of his list is ranked fourth, and nobody on screen is ranked first. He tells you the report is broken.

Here is how the ranking was built. Ranking feels like an attribute of a person, so it went on DimTechnician as a calculated column. The code below is careful. It handles context transition correctly, which is more than most first attempts manage. Context transition is the step where the row the engine is currently sitting on becomes a filter, and line 5 is where it happens.

DAXDimTechnician[HoursRank], calculated column, wrong tool
// Calculated column on DimTechnician
HoursRank =
RANKX (
    DimTechnician,
    CALCULATE ( SUM ( FactLabor[Hours] ) ),
    ,
    DESC,
    DENSE
)
Line 3
RANKX and not RANK. RANK is the newer window function and it needs an explicit ORDERBY relation. That makes it a good fit for visual calculations and DAX queries, and a poor fit for a stored model object. RANKX takes a table expression and an expression to evaluate over it, which is exactly the shape needed here.
Line 4
The table to rank over is the whole of DimTechnician, all seven rows including the Unknown row that catches TECH-07.
Line 5
CALCULATE earns its place here. Inside a calculated column the engine has row context, which means it knows which row of DimTechnician it is sitting on. It has no filter context at all. So a bare SUM ( FactLabor[Hours] ) would see the entire fact table and return 62.0 on every single row. CALCULATE performs context transition. It converts the current row of DimTechnician into a filter, and that filter propagates down the relationship to FactLabor. SUM and not SUMX because Hours is a stored column, so SUM can be answered straight from the compressed column.
Line 6
The third argument is left empty deliberately. RANKX accepts an optional value to place in the ranking, and omitting it tells the engine to evaluate the expression in the current context and rank that result. The bare comma has to stay, because the two arguments after it are positional. Delete the empty slot and DESC slides into the value position, which changes the meaning of the call rather than raising a clean error.
Lines 7 and 8
DESC so the highest hours get rank 1. DENSE so tied ranks do not leave gaps behind them. TECH-03 and TECH-06 both have zero hours and both sit at the bottom, so DENSE and the default SKIP happen to agree in this dataset. They stop agreeing the moment a tie appears mid-list. Write the argument explicitly every time and the question never comes up.

Refresh the model and the column materialises. It is correct, in the narrow sense that it answers the question it was asked.

Now put a station slicer on the page and select TUS, the way the shift supervisor did. Note carefully which field that slicer has to use. The Meridian model deliberately has no relationship between DimStation and DimTechnician. Creating one would give two filter paths from DimStation into FactLabor: one through FactWorkOrder, one through DimTechnician. The station attribute that filters technicians directly is DimTechnician[HomeStation], and that is the field on the slicer.

Select TUS. The visual now shows two technicians, TECH-03 and TECH-04. The rank column still says 6 and 4. Nobody is ranked first, which is exactly the screen the shift supervisor was looking at. The usual next move is to decide DAX is broken and start adding CALCULATE wrappers to a value that was written to disk before anyone opened the file.

It is not broken. HoursRank was computed at refresh time, when a TUS selection did not exist. The column answers one fixed question, permanently: where does this technician rank among all seven technicians in the model. The user is asking a different one: where does this technician rank among the technicians on screen right now. Only an object evaluated after the click can answer that.

DAXLabor Hours and Technician Rank, measures
Labor Hours =
SUM ( FactLabor[Hours] )

Technician Rank =
RANKX (
    ALLSELECTED ( DimTechnician[TechnicianName] ),
    [Labor Hours] + 0,
    ,
    DESC,
    DENSE
)
Line 6
ALLSELECTED over the technician name column. This removes the filter that the current row of the visual puts on the technician, so each cell can see its peers. It keeps the filters that arrived from outside the visual, and the slicer is one of those.
Line 7
The expression is the measure itself. A measure reference carries no table name, so it is written [Labor Hours], while the column it sums is written FactLabor[Hours]. The ranking is computed from whatever Labor Hours returns under the current filters. The + 0 is deliberate. TECH-03 has no rows in FactLabor at all, so SUM returns a blank, and I do not want the rank order to depend on how blanks sort. Adding zero makes the value explicit and the result deterministic. It also keeps TECH-03 visible in the table, because a blank measure result would drop the row from the visual entirely.
Lines 9 and 10
Same tie handling as the column version, for the same reason. Line 8 is the same empty value slot, kept for the same positional reason.
Why this and not that

ALLSELECTED and not ALL: ALL would strip the slicer as well as the row filter, so under a TUS selection it would rank TECH-04 against all seven technicians and hand back rank 4 again. You would have written a measure that reproduces the calculated column's bug with more effort. ALLSELECTED and not VALUES: VALUES returns the technicians visible in the current filter context. Inside a row of the visual that context has already narrowed to one technician. Every cell would rank a single-row table, and every cell would return 1.

Remove the slicer and Technician Rank returns 4 for TECH-04, matching the column exactly. Same logic as the column, evaluated against a context that is allowed to change. The column is a photograph and the measure is a window. The shift supervisor gets the leaderboard he asked for: with TUS selected, TECH-04 is first on 10.5 hours and TECH-03 is second on 0.0.

Symptom two: duplicated rows and inflated totals

Back to the finance manager and her 46,600. She wants the quoted value of the quarter's work, one number, for a slide. This failure costs money because the number looks completely normal. A stuck rank announces itself on screen. An inflated total sits there looking like a number, in a card, on a slide.

Grain is the question of what one row of a table stands for, and the whole bug lives in the answer. FactWorkOrder is at header grain: one row per work order, eight rows in all. QuotedAmount lives there because a quote is a property of a work order. FactLabor is at line grain: one row per labour line, eight rows spread unevenly across only six work orders. WO-1001 has two labour lines. WO-1003 has two. WO-1005 and WO-1008 have none at all. That uneven spread is the whole mechanism of the bug.

Look at the curved lines leaving the header rows on the left. WO-1001 fans out into two labour lines, L-501 and L-502, and WO-1003 fans out into L-504 and L-505, so anything copied down those lines arrives twice. WO-1002 has a single labour line and looks perfectly healthy. The extract drawn here is three of the eight work orders and five of the eight labour lines. That is enough to show the fan, and not enough to show the opposite failure. The red card states that one in words instead: work orders with no labor line vanish entirely. In the full data those are WO-1005 and WO-1008. That same red card adds only the five lines drawn, 3,000 plus 3,000 plus 3,200 plus 12,500 plus 12,500, and the full eight labour lines take the same arithmetic to 46,600. The green card shows the shape to aim for. Quoted Amount reads 38,100 from FactWorkOrder, Labor Cost reads 6,326.50 from FactLabor, and each measure is left on its own table. The picture is the bug. Everything below is just the arithmetic of that picture.

The page the finance manager was reading is a labour page, built around hours and technicians. She wanted quoted value on it too. The obvious move is to bring the quote down onto the labour table so it sits next to the hours.

The wrong way

A calculated column on FactLabor that pulls the header value down to line grain, then a measure that sums it.

DAXFactLabor[WOQuoted]
WOQuoted =
RELATED ( FactWorkOrder[QuotedAmount] )

Quoted Amount =
SUM ( FactLabor[WOQuoted] )
Line 2
RELATED and not LOOKUPVALUE, because a relationship from FactLabor to FactWorkOrder already exists and RELATED walks it. The DAX on this line is valid. It is pointed the correct way, many side to one side, and it returns exactly what it promises.
Line 5
The damage happens at this line. The line above it is innocent. SUM now aggregates a header value that has been copied onto eight line rows, so the row count of FactLabor decides the answer and the row count of FactWorkOrder stops mattering.

It refreshes without an error, the column populates, the measure returns a plausible currency figure. Result: 46,600.

The fix

Leave QuotedAmount where it belongs, on FactWorkOrder, and aggregate it with a measure.

DAXQuoted Amount
Quoted Amount =
SUM ( FactWorkOrder[QuotedAmount] )
Line 2
SUM and not SUMX, because QuotedAmount is a stored column and there is no row-by-row expression to evaluate, so the engine answers from the compressed column. No CALCULATE either: nothing about the filter context is being modified, and wrapping an aggregation in CALCULATE for decoration only makes the code harder to read.

Eight rows in, eight values summed, one per work order. Result: 38,100, in every filter context that reaches FactWorkOrder.

What you see in the report

A quoted value card that reads 46,600, which is 22 per cent above the truth of 38,100. The damage spreads from there. A margin card built as quoted minus actual reads 16,928.50 instead of 8,428.50. The whole 8,500 of phantom quote lands in the margin and nothing offsets it, so the job book looks roughly twice as profitable as it is. Slice it by station and the individual station figures are wrong too. Each one is wrong by a plausible amount, so nothing triggers suspicion. The number only fails a check if somebody adds the eight quotes up by hand. That is exactly the check nobody performs on a dashboard that has been live for a quarter.

Trace this by hand, row by row

Every row of FactLabor gets the quote of its parent work order stamped onto it. The relationship is many to one from FactLabor to FactWorkOrder, so RELATED resolves cleanly and no error is raised anywhere.

The arithmetic, spelled out: 3,000 plus 3,000 is 6,000. Plus 3,200 is 9,200. Plus 12,500 is 21,700. Plus 12,500 is 34,200. Plus 4,000 is 38,200. Plus 7,500 is 45,700. Plus 900 is 46,600.

The true total is 3,000 plus 3,200 plus 12,500 plus 4,000 plus 2,000 plus 7,500 plus 900 plus 5,000, which is 38,100.

The gap is 8,500, and it is made of two errors pulling in opposite directions.

  1. Over-count. WO-1001 has two labour lines, so its 3,000 is counted twice. WO-1003 has two labour lines, so its 12,500 is counted twice. That adds 15,500 that does not exist.
  2. Under-count. WO-1005 and WO-1008 have no labour lines whatsoever, so they contribute nothing. That silently drops 2,000 plus 5,000, which is 7,000 of real quoted value.

15,500 minus 7,000 is 8,500, which reconciles exactly to the gap. The two errors are independent of each other. Fixing the duplication alone would still leave you 7,000 short. The two work orders that vanished are the ones a shop manager is most likely to ask about, because one of them is still open.

Common mistake

RELATED inside a calculated column on a fact table is the most reliable way to inflate a total in Power BI. The function itself is fine. It is the right choice over LOOKUPVALUE when a relationship already exists, because it follows that relationship instead of scanning the target table for a match. The mistake is what you do next. Pull a header value down to line grain and it inherits the line table's row count, so any SUM over it counts each header once per line. Two labour lines means the quote counts twice. Zero labour lines means it disappears. One question before you type RELATED in a column: is the value I am pulling repeated across the rows I am pulling it into. If yes, write a measure against the table where the value lives.

The correct approach, and then the harder case

The finance manager gets her number here, and it is 38,100. SUM ( FactWorkOrder[QuotedAmount] ) is the model working exactly as designed. Slice by DimStation and the filter reaches FactWorkOrder directly, so MSP returns the sum of its own work orders and nothing else. Slice by DimWOType and the same thing happens. Put labour hours beside it and both measures answer independently at their own grain, which is what measures are for. SUM and not SUMX because QuotedAmount is a stored column that needs no row-by-row expression, so the engine answers from the compressed column without materialising anything.

That claim is worth proving, because "it works under a slicer" is the exact thing the calculated column failed at. Put the same measure on two different fields and add the columns up.

Check the station column by hand: 18,700 plus 16,500 plus 900 plus 2,000 is 38,100. Now the type column: 28,000 plus 6,100 plus 4,000 is also 38,100. Each work order is counted exactly once in each decomposition. Each work order is one row of FactWorkOrder, and it belongs to exactly one station and exactly one type. PHX returns a blank. That is correct, and most report consumers will read it as a bug, so decide deliberately whether you hide the row or coalesce it to zero. A zero would claim PHX quoted nothing, which says something different from PHX having no work orders at all. The same measure over FactLabor[WOQuoted] would have split 46,600 across those members instead, and every one of those station figures would have looked individually defensible.

The genuinely harder case is quoted against actual, because actual comes from two facts at two different grains. Labour is at technician-day grain, parts are at issue-line grain, and neither can be added to the other by putting a column somewhere. Five measures handle it.

DAXThe quoted versus actual measure set
Labor Cost =
SUMX ( FactLabor, FactLabor[Hours] * FactLabor[HourlyRate] )

Parts Cost =
SUMX ( FactParts, FactParts[Qty] * FactParts[UnitCost] )

Actual Cost =
[Labor Cost] + [Parts Cost]

Quoted Amount =
SUM ( FactWorkOrder[QuotedAmount] )

Variance =
[Quoted Amount] - [Actual Cost]
Labor Cost
SUMX and not SUM because the value being summed is a product of two columns and does not exist as a stored column. SUM only accepts a single column reference, so it cannot express this at all.
Parts Cost
Same shape, different fact. Note there is no ACREG on FactParts, so slicing parts by aircraft routes through FactWorkOrder. Solve that routing with a relationship. Adding an aircraft registration column to FactParts would be the same header-to-line error wearing a new costume.
Actual Cost
Plain addition of two measures, and not an iterator over a combined table. Each measure resolves at its own grain in the current filter context, and adding two scalars is safe. Building a UNION of labour and parts rows to iterate over would give the same answer at more cost. It would also need reconciling every time either fact changes shape.
Variance
Positive means Meridian quoted more than it spent. Negative means the job ran over. Written as a subtraction of measures so it inherits both filter contexts automatically and needs no maintenance when either side changes.

WO-1008 deserves a look. It shows 5,000 quoted and nothing spent, which is correct: it opened on 10 March and has neither labour nor parts against it yet. Under the calculated column approach that row did not appear at all. WO-1004 shows a favourable variance of 2,980.00 that will shrink, because the order is still open and the remaining cost has not landed. Both rows are business facts, and the measure is honest enough to put them on screen. The fix is a filter on closed work orders. The calculation stays as it is.

One display detail before you check those figures against your own screen. Where a work order has no rows in a fact, the measure returns a blank. WO-1008 has neither labour nor parts, so Labor Cost, Parts Cost and Actual Cost are all blank on that row. The same is true of the parts columns on WO-1004 and WO-1007. The zeros are written out in the table only so that the arithmetic reads cleanly down each column. The row still appears in the visual because Quoted Amount has a value, and Variance still reads 5,000.00, because subtracting a blank subtracts nothing. If you want the zeros for real, wrap the measure in COALESCE. Adding zero would also work, and COALESCE states the intent in the formula instead of hiding it in an arithmetic side effect.

Now the inconvenient part of that table. The visual on your screen will carry a ninth row, blank, holding 4,900 of parts cost. That is P-9007 charged to WO-1009, and WO-1009 does not exist in FactWorkOrder. A fact row whose key has no match like that is an orphan, and the engine parks every orphan against the blank member. With that row included, Actual Cost totals 34,571.50 and Variance totals 3,528.50, both derived from the same measures. Both figures are correct. They answer a question that includes an orphan. Decide deliberately whether your page shows it, and tell your users what you chose.

Performance note

The measure-first rule has a real cost and you should know what you are buying. Labor Cost iterates FactLabor on every query. On eight rows that is free. On forty million rows it is not. A stored LineCost column computed once at refresh aggregates faster, because the engine scans one compressed column instead of multiplying two. That case is legitimate, precisely because line cost is a property of the labour line that does not change when anyone clicks. Reach for it after you have measured a problem, and compute it in Power Query rather than DAX if the source can produce it.

Deciding, in six questions

Work down this list and stop at the first question that answers itself. It resolves nearly every case without argument.

  1. Ask what the value is a property of. A property of a technician, a date or a work order points toward a column on that table. A property of a set of rows points toward a measure.
  2. Ask whether the answer should change when the user changes a slicer. If yes, it must be a measure. No calculated column responds to selection.
  3. Ask whether the value needs to be aggregated, averaged, ranked or compared across rows. If yes, measure.
  4. Ask whether the value lives at a different grain from the table you were about to put it on. If yes, do not put it there at any price. That is the 46,600 error.
  5. Ask whether you need it on an axis, in a slicer, as a sort-by key, inside a hierarchy, as a relationship key or in a security filter. Those six require a physical column, and a measure cannot do any of them.
  6. If you have reached here you need a column. Ask whether Power Query can compute it, and if it can, compute it there.
Interview-level insight

The real question behind "column or measure" is what the value is a property of. Quoted amount is a property of a work order, so it belongs on FactWorkOrder and stays there. Hours are a property of a labour line. A technician's rank is a property of a comparison, and a comparison only exists once someone has chosen who is in it. That is why rank can never be stored and quoted amount must never be moved. Answer the property question and the DAX object follows.

Ten Meridian tasks, decided

When a calculated column is the right answer

The planner asks for a slicer that splits work orders into small, medium and large jobs. You have just been burned by the 46,600 bug, so your instinct says measure. You spend an afternoon trying to drop a measure into a slicer and Power BI refuses every time.

Analysts burned by that bug swing to a rule of "never write a calculated column", and the planner's slicer is where the rule breaks. Six situations require a physical column, and the size band is one of them.

  • Relationship keys. A relationship binds two physical columns. If the key needs cleaning or concatenating, the cleaned key has to exist as a column.
  • Sort-by columns. DimDate[MonthName] is text and sorts alphabetically, putting February first. Sort by Column fixes it, and it needs MonthNo present as a column on the same table at the same grain.
  • Static row-level classification. The work order size band, an IsWeekend flag, an employee type grouping. Each is decided by the row's own values and by nothing the user does.
  • Anything that goes in a slicer. Slicers read columns. The product enforces that boundary, and the size band the planner asked for is exactly this case.
  • Columns used by a security role. Row-level security filters are written against columns, so a role that restricts a user to their home station needs that station as a column.
  • Hierarchy levels. A hierarchy is an ordered list of columns. Station to work order to labour line needs each level physically present.
Rule of thumb

A calculated column is right when the value is a property of the row and does not depend on what anyone selects. Read that twice, because both halves matter. Line cost passes both tests. Turn time passes both. Technician rank fails the second test. Quoted amount on a labour row fails the first, because it is a property of the work order and the labour line only borrows it. If a requirement fails either half, write a measure.

Calculated tables, briefly and honestly

The production controller puts his check dates on a chart and the months come out in alphabetical order, February first. He asks for calendar order. Meridian's source system has no calendar table to point at, so you have to build one inside the model.

A calculated table is the same idea one level up: a DAX expression returning a table, evaluated at refresh and stored in the model. The case where it earns its place in Meridian is DimDate, and the controller's month order is the reason.

DAXDimDate, calculated table, 90 rows
DimDate =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2025, 1, 1 ), DATE ( 2025, 3, 31 ) ),
    "Year",      YEAR ( [Date] ),
    "MonthNo",   MONTH ( [Date] ),
    "MonthName", FORMAT ( [Date], "mmmm" ),
    "MonthKey",  YEAR ( [Date] ) * 100 + MONTH ( [Date] ),
    "MonthStart",
        DATE ( YEAR ( [Date] ), MONTH ( [Date] ), 1 )
)
CALENDAR
CALENDAR and not CALENDARAUTO. CALENDARAUTO inspects every date column in the model and expands to whole years. That would hand you 365 rows covering all of 2025, when Meridian only reports on Q1. Explicit bounds give exactly 90 rows, 31 plus 28 plus 31, and a date table with no stray empty months.
ADDCOLUMNS
One expression producing the whole table. The alternative is creating the calendar first and then stacking five separate calculated columns on top of it. One expression means fewer objects in the dependency graph and one place to read the definition. The remaining DimDate columns that Meridian needs, Quarter, DayOfWeek and IsWeekend, follow the same pattern and are left out here only to keep the block readable.
YEAR, MONTH
These read the numeric parts straight from the date value. FORMAT could produce them too, but it returns text, and text sorts alphabetically on an axis, which is the problem you are trying to avoid.
FORMAT
Used only where text is actually wanted, for the display month name. Because it returns text, MonthName must then be sorted by MonthNo. That is the sort-by case from the list above, and it is the reason MonthNo is in this table at all. It is also what gives the production controller January, February, March in that order, with February back where it belongs.
MonthStart
DATE and not STARTOFMONTH. STARTOFMONTH is a time intelligence function that operates on a column of dates within a filter context, and inside ADDCOLUMNS you are in row context working with one scalar date. DATE constructs the value directly. This column is what FactCapacity joins to at month grain.

The honest caveats. A calculated table is recomputed at every refresh and stored like any other table, so it costs memory and refresh time. It cannot be edited in Power Query, so the analyst who inherits your file will look for it in the query editor and not find it. DirectQuery restricts it further. Check the current limitation list before you assume Import behaviour carries over. For a date table in an Import model the trade is usually worth it, because the definition is self-contained and does not depend on a source system having a calendar table. For most other tables, if the source or Power Query can produce it, let them.

The third option people forget

Back to the planner and the size band. There is a third place to build that column, and for anything that could be a calculated column and does not need to see the rest of the model, the third place is usually the better answer. Power Query is the load step where you shape a table before it enters the model. The size band belongs there.

Read this left to right. The four bands are the four places a calculation can live: the source system, then Power Query, then DAX calculated columns and tables, then DAX measures. Each band after the first carries the moment it runs, at refresh, at load, at query time. The axis underneath them runs from computed once, per refresh on the left, to computed per visual, per user, per click on the right. That is the cost you trade every time you move one step further along. The rule is printed beneath the bands: push work as far left as you can, then move it right for one reason only. The green card names that reason. If the answer depends on what the user selects, it cannot be precomputed, and no amount of refresh time will make it so.

MFactWorkOrder size band
let
    Source = WorkOrders,
    Banded = Table.AddColumn (
        Source,
        "SizeBand",
        each
            if [QuotedAmount] < 3000 then "Small"
            else if [QuotedAmount] < 7500 then "Medium"
            else "Large",
        type text
    )
in
    Banded
Table.AddColumn
The user interface Conditional Column button writes the same function call, and it omits the final type argument, so the column arrives typed as any. Writing type text by hand gives the engine a known type to encode. On a column destined for a slicer that is worth the extra few characters.
The bands
Under 3,000 is Small, 3,000 to 7,499 is Medium, 7,500 and above is Large. Against the eight Meridian quotes that puts WO-1005 at 2,000 and WO-1007 at 900 in Small, WO-1003 at 12,500 and WO-1006 at 7,500 in Large, and the remaining four in Medium. The planner drops SizeBand straight into a slicer and it works, because it arrived in the model as a real column.

Two reasons to prefer this over the DAX equivalent. First, a Power Query column arrives with the table and is encoded in the same pass as every column that came from the source. A calculated column is added after the table has already been loaded, and it usually compresses less well. Second, and this is the reason I would defend hardest, a calculated column becomes a node in the model's dependency graph. Every measure, relationship, hierarchy and other calculated column that touches it now depends on it. Refresh has to evaluate it in the right order, and changing it later can force recalculation you did not plan for. A Power Query column stays outside that graph. It arrives as a plain column and the engine treats it exactly like the columns that came from the source.

The exception is real and you will hit it. If the expression needs to see another table through a relationship, or needs a measure, Power Query cannot help you. Relationships do not exist yet at that stage of the pipeline. That is when a calculated column is the correct tool, and nobody is compromising. Everything else belongs upstream. Chapter 4 covers where each transformation belongs and why moving work upstream keeps paying you back long after the model is built.

What to remember
  • A calculated column is evaluated once per row at refresh and stored. A measure is evaluated once per cell at query time and stores nothing. Every other difference follows from that one.
  • A calculated column cannot respond to a slicer, because it was computed before the report was opened. HoursRank says 4 for TECH-04 whatever is selected. The measure using ALLSELECTED says 1 under a TUS home station slicer.
  • Pulling a header value to line grain with RELATED inflates totals. Quoted amount on FactLabor sums to 46,600 against a true 38,100: 15,500 over-counted because WO-1001 and WO-1003 each have two labour lines, 7,000 lost because WO-1005 and WO-1008 have none.
  • Keep QuotedAmount on FactWorkOrder and aggregate it with a measure. It returns 38,100 in every filter context that reaches that table.
  • The real question is what the value is a property of, and whether that property depends on what anyone selects.
  • Columns are still required for relationship keys, sort-by columns, static row classification, slicer fields, security filters and hierarchy levels. Build them in Power Query unless they need to see the model.
