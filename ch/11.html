Part 4 . Evaluation context and DAX

11CALCULATE and every filter modifier you need

After this chapter you will be able to predict the number a CALCULATE expression returns before you write it, name which modifier changes which part of the filter context, and explain why a measure that hard filters AOG still shows AOG hours when the slicer says Scheduled.

The production controller sets the work order type slicer to Scheduled. He wants to see the scheduled work and nothing else. The labor hours card drops to 38.0, which is right. The card beside it, the one labelled AOG Hours, still reads 14.0. He asks you why a report filtered to Scheduled is showing him AOG hours, and it is a fair question.

The answer is in one function. CALCULATE is the only function in DAX that can change the filter context an expression is evaluated in. Filter context is the set of filters in force when a value is computed, arriving from slicers, from the rows and columns of a visual, and from page filters. Every other function reads that context. CALCULATE writes it. That is why CALCULATE appears in almost every measure of any substance you will ship, and why almost every measure of any substance you will debug turns out to be a CALCULATE you did not fully understand.

The mechanism is small. There are five things CALCULATE does and they happen in a fixed order. Once you can recite that order you can reason about any expression in the language. One of those five steps is counterintuitive on first contact, and nothing in the interface tells you it happened. That step is what put 14.0 on the controller's screen, and this chapter ends by resolving it.

What CALCULATE does, in order

CALCULATE takes an expression as its first argument and zero or more filter arguments after it. When the engine hits a CALCULATE call it runs this sequence.

  1. It creates a new filter context that starts as a copy of the current one.
  2. It evaluates each filter argument. Every filter argument is evaluated in the outer filter context, the one that existed before CALCULATE started, and in any row context that is open. Filter arguments never see each other. Two filter arguments in the same CALCULATE are evaluated independently, so the second one cannot depend on what the first one did.
  3. If there is a row context, CALCULATE performs context transition. Every column of the table being iterated becomes a filter in the new context. This is the step covered in Chapter 9, and it happens whether you wanted it or not.
  4. It applies the CALCULATE modifiers. ALL, REMOVEFILTERS, ALLEXCEPT, ALLSELECTED, KEEPFILTERS, USERELATIONSHIP and CROSSFILTER belong in a category of their own. They instruct CALCULATE about how to build the context, and they run after context transition, in step four.
  5. It applies the evaluated filter arguments to that context, then evaluates the expression.

This is the same pair of panels you met in Chapter 9, and it repays a second look now that the five steps are in front of you. In the left panel one FactLabor row is outlined and the other four sit there untouched. An iterator knows which row it is on. That knowledge filters nothing until something converts it into a filter. Step three above is that conversion, and CALCULATE is the only function that performs it. Read the full width card along the bottom for the rest of it. Follow the arrow that runs from the words row context to the words filter context. That arrow is the step that makes a measure reference inside an iterator return a different number from the same reference sitting in a card visual on the page. The card gives the Meridian case underneath: SUMX ( DimTechnician, [Labor Hours] ) returns 52.0 and not 62.0.

Step five carries the fact that explains most of the confusion in this language. When CALCULATE applies a filter argument on a column, it does not add that filter to whatever filter was already sitting on the column. It replaces it. The old filter on that column is gone. Filters on every other column survive untouched.

Interview-level insight

Ask why CALCULATE replaces instead of intersecting and the answer is that a filter argument is a table. DimWOType[WOType] = "AOG" expands into a table of the values that satisfy it, built from ALL on that column. Applying a table to a column sets the context for that column to exactly those values. Nothing of what was there survives, because nothing of what was there was consulted. Whether that should have been the default is a fair question. The practical answer is that the opposite behaviour costs you one keyword, KEEPFILTERS. Starting from an intersecting default would instead mean adding a filter remover for every column you touched.

The two syntaxes, and why one is sugar for the other

Take the Meridian measure [Labor Hours], defined as SUM(FactLabor[Hours]), which returns 62.0 across the whole quarter. Now filter it to AOG work.

DAXAOG Hours, boolean shorthand
CALCULATE(
    [Labor Hours],
    DimWOType[WOType] = "AOG"
)

That is the shorthand, and it reads like a condition: keep the rows where WOType is AOG. With nothing selected on the page it returns 14.0, which is WO-1002 at 9.0 plus WO-1005 at 0 plus WO-1007 at 5.0. Here is the same measure written out in full, and the full form is closer to what the engine actually runs.

DAXAOG Hours, table form
CALCULATE(
    [Labor Hours],
    FILTER(
        ALL( DimWOType[WOType] ),
        DimWOType[WOType] = "AOG"
    )
)
Line 4
ALL on the column produces every distinct WOType in the model, ignoring whatever the report has selected. Three values: Scheduled, AOG, Mod.
Line 5
The condition keeps the one row where WOType is AOG, so the FILTER opened on line 3 returns a one row table.
Lines 3 to 6
That one row table becomes the filter on DimWOType[WOType]. It is the whole filter, not an addition to the existing one, because the existing one was discarded by the ALL on line 4.

The two are the same expression. The shorthand is compiled into the table form with ALL on the referenced column. That expansion is the entire explanation for the behaviour people find surprising. The shorthand reads like a condition and behaves like a replacement, and the hidden ALL is why.

You will also meet a variant written as FILTER(ALL(DimWOType), DimWOType[WOType] = "AOG"), with ALL on the whole table instead of on the column. It returns the same 14.0 here, and on a two column dimension you will never see a difference. The expansion underneath differs, though. A table level ALL clears the filters on every column of DimWOType. The moment that dimension gains a description or a priority column that someone slices on, the table form quietly drops that slicer. The shorthand keeps it.

This is the production controller's screen, exactly. Put a slicer on the report page for DimWOType[WOType] and set it to Scheduled. A card showing [Labor Hours] reads 38.0, which is WO-1001 at 13.5 plus WO-1003 at 12.5 plus WO-1006 at 12.0 plus WO-1008 at 0. Put the AOG measure above it on the same page and it reads 14.0. The measure removed the slicer's Scheduled filter from the WOType column and put AOG there instead. He is looking at a card that answers a question he did not ask.

Both rows are correct answers to different questions. The first answers "how many AOG hours are there". The second answers "how many of the hours the user is currently looking at are AOG". The production controller was asking the second question and the report was answering the first. Decide which question your page is asking before you write the measure, because both compile and only one of them is right.

Why this and not that

Use the boolean shorthand for any comparison on a single column against constants. Reach for the explicit FILTER form only when you need it: a condition across two columns, a column compared against a measure, or a filter that has to be evaluated row by row over a fact table. FILTER over a large table forces the engine to materialise and iterate it, while the shorthand compiles to a filter the storage engine can push down. At Meridian's eight work orders that difference is unmeasurable, which is why habits formed on toy models get expensive later.

ALL, the blunt instrument

The finance manager wants a share column. Labor hours by aircraft type, and next to each type the percentage of the quarter it represents. She expects the percentages to add to 100. You put [Labor Hours] in the numerator, and then you need a denominator that holds still at 62.0 while the rows of the visual change underneath it. Holding a denominator still is what ALL is for.

ALL removes filters. What it removes depends on what you hand it. With no arguments at all it clears the entire filter context of the model. That is almost never what a report measure wants, and it is mostly useful inside a scoped calculation. Hand it a table and it clears every filter on that table. Hand it one or more columns and it clears the filters on those columns only, leaving the rest of the table alone.

DAXPct of Total Hours
DIVIDE(
    [Labor Hours],
    CALCULATE( [Labor Hours], ALL( DimAircraft ) )
)
Line 2
The numerator is evaluated in the visual's own filter context. On the E175 row it is 17.5, which is WO-1003 at 12.5 plus WO-1007 at 5.0.
Line 3
ALL(DimAircraft) drops every filter the aircraft dimension is contributing, including AircraftType, ACREG and Operator. The denominator becomes 62.0 on every row of the visual.
Line 1
DIVIDE rather than the slash operator, because DIVIDE returns blank on a zero denominator instead of raising an error, and a divide by zero error kills the whole visual rather than one cell.

The finance manager gets her share column and it adds to 100.0 percent. E175 is 17.5 divided by 62.0, which is 0.28226, shown as 28.2 percent. The fourth row exists only because the aircraft dimension was built by appending the tails found in the work orders. Point this measure at the raw registry instead and the 12.0 hours land in a blank row, while the three real types add to 80.6 percent with nothing on screen saying so.

Why this and not that

ALL(DimAircraft) rather than ALL(DimAircraft[AircraftType]). The visual might later gain a second field from the same dimension, Operator for instance. A column level ALL would leave that new filter in place. The denominator would quietly become the operator total instead of the grand total, and the percentages would still look plausible. Table level ALL is the safer default for a true grand total. Column level ALL is right when you deliberately want to hold some of the dimension's filters and release others.

REMOVEFILTERS, which is ALL with a clearer name

REMOVEFILTERS accepts the same arguments as ALL. In the modifier position inside CALCULATE it does exactly the same thing. Microsoft added the name, and the name is the whole contribution, and it is still worth adopting.

DAXPct of Total Hours, preferred spelling
DIVIDE(
    [Labor Hours],
    CALCULATE(
        [Labor Hours],
        REMOVEFILTERS( DimAircraft )
    )
)

Naming preferences are cheap, so here is REMOVEFILTERS carrying a calculation of its own. Put DimStation[StationCode] on the rows of a matrix and ask what share of the quarter each station worked.

DAXPct of Quarter Hours
Pct of Quarter Hours =
DIVIDE(
    [Labor Hours],
    CALCULATE(
        [Labor Hours],
        REMOVEFILTERS( DimStation )
    )
)
Line 3
The numerator keeps the row's own station filter. On the MSP row it is 34.5, being WO-1001 at 13.5 plus WO-1002 at 9.0 plus WO-1006 at 12.0, with WO-1008 contributing nothing.
Line 6
REMOVEFILTERS( DimStation ) drops the station filter and nothing else, so the denominator is 62.0 on every row of the visual. A month slicer, a WOType slicer or a technician slicer would still apply inside that denominator, because none of them sit on DimStation.

34.5 divided by 62.0 is 0.55645, shown as 55.6 percent. 22.5 divided by 62.0 is 0.36290, shown as 36.3 percent. 5.0 divided by 62.0 is 0.08065, shown as 8.1 percent, and those three add to 100.0. The last two rows are the ones worth pausing on. UNASSIGNED holds WO-1005, which has no labor rows. PHX exists only in the planning workbook and has no work orders at all. Both return a blank, so Power BI hides them from the visual by default. Turn on "Show items with no data" and they reappear with an empty share, which is the honest reading: neither station worked a share of anything.

The reason to prefer it is that ALL is overloaded. In the modifier position it removes filters. In an expression position it is a table function that returns rows. That is the job it is doing on line 4 of the table form earlier in this chapter, inside FILTER(ALL(DimWOType[WOType]), ...). Same identifier, two different jobs, and the reader has to work out which one from the surrounding syntax. REMOVEFILTERS only ever means "clear the filters here", so when a colleague reads your measure six months from now there is nothing to work out.

Why this and not that

Use REMOVEFILTERS in every filter argument position. Keep ALL for the places where you actually need a table of rows returned, typically as the source of a FILTER or SUMMARIZE. They are functionally identical as modifiers, so this costs nothing and buys readability. The one caveat is version support: REMOVEFILTERS arrived later than ALL, so very old Analysis Services models may not accept it. Current Power BI Desktop and current Fabric semantic models do.

The working rule is positional. If the name appears directly as an argument of CALCULATE or CALCULATETABLE, spell it REMOVEFILTERS. If it appears inside another table expression, spell it ALL.

ALLEXCEPT, and the trap it sets

The production controller wants a different share. For each work order, what proportion of its own station's hours did it take? WO-1001 measured against MSP, WO-1003 measured against TUS, one line at a time down the list. The denominator has to change from row to row, following whichever station that row belongs to, and you cannot hardcode a station into a measure that has to serve all of them.

ALLEXCEPT removes filters from a table and everything related to it, except the columns you list. That is the natural way to express "share of the parent group" while leaving the parent to be decided at query time.

DAXPct of Station Hours
DIVIDE(
    [Labor Hours],
    CALCULATE(
        [Labor Hours],
        ALLEXCEPT( FactWorkOrder, DimStation[StationCode] )
    )
)
Line 5
The first argument is the table whose filters are cleared. DimStation, DimAircraft, DimWOType and DimDate all sit on the one side of a relationship from FactWorkOrder. That makes them part of the expanded FactWorkOrder table, so their filters are cleared too.
Line 5
StationCode is named as the exception, so a filter already sitting on that column survives. Note the word already. ALLEXCEPT preserves a filter and it never creates one. The station has to be present in the visual for this measure to mean anything. Table 11.4 puts the work order and the station side by side on the rows, and the denominator becomes that station's total. Drop the station column from the visual and every denominator silently becomes 62.0, because there was no StationCode filter left to keep.

That is the controller's answer. WO-1001 is 13.5 divided by 34.5, which is 0.39130, shown as 39.1 percent. The three MSP work orders with hours come to 39.1 plus 26.1 plus 34.8, which is 100.0 percent. The fourth contributes nothing, because WO-1008 has no labor rows. WO-1005 returns a blank because DIVIDE was used, and that blank is honest: the UNASSIGNED station has no hours to take a share of.

There is a version of this that some architects prefer, which clears the fact table and then puts the visible station back as an explicit filter.

DAXThe explicit equivalent
CALCULATE(
    [Labor Hours],
    REMOVEFILTERS( FactWorkOrder ),
    VALUES( DimStation[StationCode] )
)

This reads better: clear the fact table, then put back the one thing you want to keep. On the visual behind Table 11.4 it produces the same numbers. File the two as different measures, though, because the scope they clear is different. REMOVEFILTERS(FactWorkOrder) clears the filters on the columns of FactWorkOrder itself and stops there. A slicer on DimDate or DimWOType still applies inside that denominator. ALLEXCEPT works on the expanded table and takes those slicers out as well.

Add a month slicer to the page and the two versions stop agreeing. The explicit form gives each work order its share of its station within the selected month. The ALLEXCEPT form gives its share of the station across the whole quarter. The March rows then add to something under 100 percent, and a reader who does not know the measure will report that as a bug. Both forms are correct. Decide which of the two questions the page is asking before you pick one.

Set that slicer to February and the divergence is easy to check by hand. The active date relationship runs to OpenedDate. The visual now shows the three work orders opened in February: WO-1004 at TUS, WO-1005 at UNASSIGNED and WO-1006 at MSP. February labor is L-506 at 10.0 hours on WO-1004 and L-507 at 12.0 hours on WO-1006. The numerators are 10.0, blank and 12.0 in both versions. Only the denominators move.

The explicit form gives 10.0 divided by 10.0 and 12.0 divided by 12.0, because WO-1004 is the whole of TUS in February and WO-1006 is the whole of MSP in February. Both rows with hours on them read 100.0 percent, which is correct and which tells the reader nothing they did not already know. The ALLEXCEPT form gives 10.0 divided by 22.5, which is 0.44444 and shows as 44.4 percent, and 12.0 divided by 34.5, which is 0.34783 and shows as 34.8 percent, both against the quarter totals from Table 11.4. February is the month that shows this cleanly. Try it in March instead and the only station with hours is LAS. The LAS March total and the LAS quarter total are both 5.0, so that row reads 100.0 percent under either form and the difference hides.

Common mistake

ALLEXCEPT(FactWorkOrder, DimStation[StationCode]) clears more than the filters you were thinking about. It clears DimDate, DimAircraft and DimWOType too, because those tables expand into FactWorkOrder. A user who slices to March and to AOG gets a denominator that ignores both selections. It also breaks in the future: add a dimension on the one side of FactWorkOrder next quarter and every ALLEXCEPT in the model starts clearing that one as well, with no error. Now the surprise in the other direction. DimTechnician relates to FactLabor, so it never expands into FactWorkOrder, and a technician slicer survives this ALLEXCEPT untouched.

KEEPFILTERS, the one everybody gets wrong

Here is where the production controller gets his answer. KEEPFILTERS is an instruction that changes how a filter argument is applied. It tells CALCULATE to intersect the argument with the existing filter on the column instead of replacing it. That is the whole function. It takes the default behaviour of CALCULATE and inverts it for one argument.

DAXTwo AOG measures that behave differently
// replaces the WOType filter, ignores the slicer
CALCULATE(
    [Labor Hours],
    DimWOType[WOType] = "AOG"
)

// intersects with the WOType filter, respects the slicer
CALCULATE(
    [Labor Hours],
    KEEPFILTERS( DimWOType[WOType] = "AOG" )
)
Lines 2 to 5
The shorthand expands to ALL on WOType then a filter for AOG. Whatever the slicer had chosen on that column is discarded. With the slicer on Scheduled this returns 14.0, being WO-1002 at 9.0 plus WO-1005 at 0 plus WO-1007 at 5.0.
Lines 8 to 11
KEEPFILTERS suppresses the implicit ALL. The AOG table is intersected with the slicer's table. Scheduled intersect AOG is the empty set, so the measure returns blank.
Trace this by hand, row by row

Slicer set to Scheduled. Outer filter context on DimWOType[WOType] is the one row table { Scheduled }.

Without KEEPFILTERS. The filter argument expands to FILTER(ALL(DimWOType[WOType]), WOType = "AOG"). ALL discards { Scheduled } and returns { Scheduled, AOG, Mod }. FILTER reduces that to { AOG }, and CALCULATE applies it in place of { Scheduled }. Three work orders now pass: WO-1002 with L-503 at 9.0 hours, WO-1005 with no labor rows at all, WO-1007 with L-508 at 5.0 hours. Sum is 14.0.

With KEEPFILTERS. The same { AOG } table is produced, and CALCULATE intersects instead of replacing. { Scheduled } intersect { AOG } is empty, so no work orders pass and no labor rows pass. SUM over zero rows returns a blank. The card shows nothing at all, and a conditional format keyed on "less than 1" will not fire, because a blank never reaches the comparison.

Now select both Scheduled and AOG in the slicer. Outer context is { Scheduled, AOG }. Without KEEPFILTERS you still get 14.0, because the replacement does not care what the slicer said. With KEEPFILTERS the intersection is { AOG }, so you also get 14.0. The two measures agree here, which is why this bug survives testing: it only diverges when the selection and the hardcoded value do not overlap.

KEEPFILTERS matters in a second place that has nothing to do with slicers. When a filter argument spans two columns of the same table, it replaces the filter on each column independently. That can resurrect column combinations the original context had excluded. KEEPFILTERS holds the original pairs intact. This is the difference between filtering on columns and filtering on rows, and it is why a filter argument that touches two columns almost always wants KEEPFILTERS around it.

Meridian has a two column case sitting in Built DimAircraft. Put AircraftType on the rows of a matrix and Operator on the columns and each populated cell is a filter on a pair of values, not two independent filters. There are seven such pairs in the dimension, one per tail, because no two tails share both a type and an operator. Now write a measure that asks for the Airbus fleet plus everything Northwind Regional operates.

DAXFleet Pair Hours, with and without KEEPFILTERS
// replaces the filter on BOTH columns
Fleet Pair Hours =
CALCULATE(
    [Labor Hours],
    FILTER(
        ALL( DimAircraft[AircraftType], DimAircraft[Operator] ),
        DimAircraft[AircraftType] = "A320-200"
            || DimAircraft[Operator] = "Northwind Regional"
    )
)

// intersects with the pair the cell already carries
Fleet Pair Hours Kept =
CALCULATE(
    [Labor Hours],
    KEEPFILTERS(
        FILTER(
            ALL( DimAircraft[AircraftType], DimAircraft[Operator] ),
            DimAircraft[AircraftType] = "A320-200"
                || DimAircraft[Operator] = "Northwind Regional"
        )
    )
)
Line 6
ALL over two columns returns the pairs that exist in the table, not the cross join of the two columns. Seven pairs go in, and the OR condition keeps three of them: A320-200 with Cascade Air, A320-200 with Northwind Regional, and E175 with Northwind Regional. Those three pairs reach N771QR, N615RB and N902TT.
Result of the first
That three row table is applied in place of whatever pair the cell was carrying, on both columns at once. N771QR contributes 23.5 from WO-1001 and WO-1004, N615RB contributes nothing because WO-1005 has no labor rows, and N902TT contributes 17.5 from WO-1003 and WO-1007. Every cell in the matrix returns 23.5 plus 0 plus 17.5, which is 41.0.
Result of the second
KEEPFILTERS intersects the three pairs with the cell's own pair, so only cells whose pair is in the list survive. The Cascade Air A320-200 cell keeps 23.5 and the Northwind Regional E175 cell keeps 17.5. Everything else is an empty intersection and returns blank.

The four shaded rows are the damage. The B737-800 row for Cascade Air reads 41.0, and not one of those 41.0 hours was worked on a B737-800. The pair filter replaced the cell's type and the cell's operator, then went and found aircraft the cell had excluded. The kept version puts blanks there instead. Its two surviving cells, 23.5 plus 17.5, add to exactly the 41.0 that the replace version was printing everywhere. That is the tell. When a measure repeats one number across every cell of a matrix, a filter argument has replaced the axis it was supposed to respect.

Performance note

KEEPFILTERS is cheap but not free. It adds no iterator and forces no materialisation. What it can do is reshape the query plan enough that a filter which used to be pushed to the storage engine now resolves in the formula engine. On Meridian's 8 fact rows this is undetectable. Take a high cardinality column on a fact table with 200 million rows. Measure that before you ship. The plan change is real even though the function is light.

ALLSELECTED, the one to verify before you trust it

The shift supervisor selects MSP and TUS in the station slicer, because those are the two stations he covers. The share column beside the hours now adds to 91.9 percent. He asks where the missing 8.1 percent went. He will not accept "it is at LAS, which you filtered out" as an answer on a page that shows him two stations and one total.

ALLSELECTED is built for exactly this. It restores the filter context that existed outside the current visual. Slicers, page filters and report filters survive. The filters the visual itself is applying, its rows, columns and legend, are removed. The denominator then equals what the user can currently see, and the model total stops leaking into it.

DAXPct of Visible Hours
DIVIDE(
    [Labor Hours],
    CALCULATE(
        [Labor Hours],
        ALLSELECTED( DimStation )
    )
)

Put stations on the rows of a matrix and set a station slicer to MSP and TUS only. The visible hours are 34.5 plus 22.5, which is 57.0. Compare the two denominators.

The REMOVEFILTERS column divides by 62.0 and lands at 91.9 percent, which is correct and which most users read as a defect. That is the shift supervisor's missing 8.1 percent, and it is at LAS. The ALLSELECTED column divides by 57.0 and adds to 100 percent, which is what people expect from a share column sitting next to a slicer. 34.5 divided by 57.0 is 0.60526, shown as 60.5 percent. 22.5 divided by 57.0 is 0.39474, shown as 39.5 percent. Give the supervisor the second column and tell him it is a share of what he selected.

Why this and not that

Use ALLSELECTED when the reader will compare the percentages to each other and expect them to total 100 within what they selected. Use REMOVEFILTERS when the reader will compare the percentage to an absolute baseline, such as share of the whole quarter. Do not use ALLSELECTED as a general purpose "remove filters but nicer". Its result depends on where it is called from, and the concept of "outside the visual" is defined by shadow filter contexts that the report author never sees.

Common mistake

Nest ALLSELECTED inside an iterator, inside another CALCULATE, or inside a calculated table, and it stops meaning what the same expression means in a measure a visual evaluates directly. Its formal semantics involve shadow filter contexts, and it has genuine edge cases. What is certain is the simple case shown above. Anything more nested should be checked in your own report against numbers you worked out by hand. This is the one function in this chapter where I would not defend a claim in a design review without a screenshot of the actual result.

VALUES and DISTINCT

Both return a one column table of the values visible in the current filter context. The difference is the blank row.

When a fact table contains a key that does not exist in the dimension, Power BI adds an invisible blank row to the dimension so those fact rows have somewhere to go. In the finished Meridian model that never happens for aircraft, because Built DimAircraft was created by appending the tails found in the work orders, which recovered N338WA. Point the relationship at the raw AircraftRegistry instead, with its 6 rows, and WO-1006 becomes an orphan and the blank row appears.

DAXTwo ways to count tails
Tails with VALUES =
    COUNTROWS( VALUES( AircraftRegistry[ACREG] ) )

Tails with DISTINCT =
    COUNTROWS( DISTINCT( AircraftRegistry[ACREG] ) )
Why this and not that

COUNTROWS wrapped around the table function, and not DISTINCTCOUNT, because the point of this pair is to make the blank member visible and DISTINCTCOUNT buries the choice of table function inside a single name. Its own treatment of blanks is then a separate question you have to go and look up, which is one lookup more than this comparison needs. Use VALUES when you are reapplying a filter, as in the ALLEXCEPT rewrite earlier. Dropping the blank member there would exclude the orphaned facts from your denominator, and the percentages would stop adding up. Use DISTINCT when you are counting real dimension members for a human to read, because "7 aircraft" against a fleet list of 6 is a number you will have to explain in a meeting. The right answer at Meridian is neither: fix the dimension so the blank row cannot occur, and the choice stops mattering.

SELECTEDVALUE, HASONEVALUE, ISFILTERED and ISCROSSFILTERED

SELECTEDVALUE is a wrapper. SELECTEDVALUE(DimWOType[WOType], "all types") is shorthand for "if exactly one value is visible in that column return it, otherwise return the alternate result". It is the safe way to read what a slicer is set to.

DAXDynamic title driven by a slicer
WO Type Header =
    "Labor hours, " &
    SELECTEDVALUE( DimWOType[WOType], "all types" )
Line 3
Slicer on AOG alone returns "Labor hours, AOG" and the card beneath it shows 14.0. Slicer on Scheduled and AOG together returns "Labor hours, all types" because two values are visible, which is honest: the header no longer claims a single type.
Why this and not that

SELECTEDVALUE rather than IF(HASONEVALUE(col), VALUES(col), "all types"). The long form is three functions where one will do, and a bare VALUES used as a scalar throws a runtime error the moment two values are visible. Keep the long form only when you need different branches for the zero value case and the many value case, since SELECTEDVALUE collapses both into one alternate result. Do not reach for FIRSTNONBLANK, which older blog posts suggest. It returns a value even when several are selected, so it will label your card AOG while the numbers behind it include Mod.

The last three are inspection functions, and the distinction between the first two is a standard interview question because it is a clean test of whether you understand propagation.

Say it precisely. ISFILTERED asks whether a filter was placed on that column. ISCROSSFILTERED asks whether the column ends up restricted for any reason, including a filter placed elsewhere that reached it. A direct filter restricts the column too, so ISFILTERED being TRUE always implies ISCROSSFILTERED is TRUE. The reverse holds only sometimes. Cross filtering also follows relationship direction. Meridian's relationships are single direction, so a filter on FactWorkOrder leaves DimAircraft uncrossfiltered: filters travel from the one side to the many side, and back the other way only when the relationship is bidirectional.

Composing filter arguments

Multiple filter arguments in a single CALCULATE are combined with AND. Each is applied independently to its own columns.

DAXThree ways to compose
// AND across two arguments: AOG work at MSP
CALCULATE(
    [Labor Hours],
    DimWOType[WOType] = "AOG",
    DimStation[StationCode] = "MSP"
)

// OR inside one argument: unplanned plus modification work
CALCULATE(
    [Labor Hours],
    DimWOType[WOType] = "AOG"
        || DimWOType[WOType] = "Mod"
)

// same thing with IN, which is easier to extend
CALCULATE(
    [Labor Hours],
    DimWOType[WOType] IN { "AOG", "Mod" }
)

AOG and MSP intersects to WO-1002 alone, since WO-1005 has a blank station that was mapped to UNASSIGNED and WO-1007 is at LAS. AOG or Mod is the 14.0 AOG hours plus WO-1004's 10.0 Mod hours, which is 24.0. The IN form and the || form compile to the same thing, so choose IN. Adding a third work order type later costs you one token inside the braces, where the || form costs you a whole new clause.

Here is the limitation that trips people. The boolean shorthand can reference only one column. Write DimWOType[WOType] = "AOG" || DimStation[StationCode] = "MSP" and it will not compile, because there is no single column for CALCULATE to place the resulting table on. OR across two columns needs a real table expression, typically FILTER over a summarised table or a TREATAS of value pairs. Treat that as information about cost. The language is telling you that OR across dimensions costs more than AND across dimensions, and it will be slower on a large model.

CALCULATE and variables

The planner opens the work order type breakdown you sent her and every row of the share column reads 100.0 percent. Scheduled, AOG, Mod, and the total underneath them. She asks whether the report is finished. The measure behind that column looks correct, and one variable in it was declared one line too early.

A variable declared with VAR is evaluated once, at the point of declaration, in the filter context that exists there. It holds a value from then on, and using it somewhere else re evaluates nothing. Move a VAR inside a CALCULATE and its value changes. Reference a VAR inside a CALCULATE and its value stays exactly what it was.

The wrong way
DAXPct of All Types, broken
VAR Hours = [Labor Hours]
RETURN
DIVIDE(
    Hours,
    CALCULATE(
        Hours,
        REMOVEFILTERS( DimWOType )
    )
)

The author expected CALCULATE to recompute Hours without the WOType filter. It cannot. Hours was already resolved to a number on line 1, in the row's own context. CALCULATE is handed a constant and returns that constant.

The fix
DAXPct of All Types
VAR Hours = [Labor Hours]
VAR AllTypes =
    CALCULATE(
        [Labor Hours],
        REMOVEFILTERS( DimWOType )
    )
RETURN
    DIVIDE( Hours, AllTypes )

The measure reference sits inside CALCULATE, so it is evaluated in the modified context. Each VAR now holds the number it was supposed to hold.

What you see in the report

The broken version shows 100.0 percent on the AOG row, 100.0 percent on the Scheduled row, 100.0 percent on the Mod row and 100.0 percent on the total. That is the planner's screen. Every cell divides 14.0 by 14.0, or 38.0 by 38.0, or 10.0 by 10.0. A column of identical values is the signature of a variable captured too early. Learn to recognise it on sight, because the formula bar gives you no hint at all. Move the measure reference inside the CALCULATE, as the fix on the right does, and the planner gets a column she can read: 14.0 over 62.0 for AOG, 38.0 over 62.0 for Scheduled, 10.0 over 62.0 for Mod.

The same behaviour is a tool. Because a variable freezes the current context, it is the cleanest way to hold onto "what this row is" before you go and change the context to get a comparison base.

DAXPct of Station Hours, variable form
VAR ThisWO = [Labor Hours]
VAR StationTotal =
    CALCULATE(
        [Labor Hours],
        ALLEXCEPT( FactWorkOrder, DimStation[StationCode] )
    )
RETURN
    DIVIDE( ThisWO, StationTotal )
Line 1
Captured in the work order's own context. On the WO-1001 row this is 13.5 and it stays 13.5 for the rest of the expression, no matter what happens below.
Lines 2 to 6
Evaluated in a context where everything except the station has been cleared. On the WO-1001 row this is the MSP total, 34.5.
Line 8
13.5 divided by 34.5, which is 39.1 percent, matching Table 11.4.
Rule of thumb

Name variables for the context they were captured in, not for the value they hold. ThisWO and StationTotal tell the next reader that one was taken before the context change and one after. Hours1 and Hours2 tell them nothing, and this class of bug is invisible unless the names carry the information.

The order of evaluation, restated

Every question about CALCULATE resolves against this list. When a measure returns something you did not expect, walk it.

  1. Copy the current filter context.
  2. Evaluate every filter argument in the outer filter context and any outer row context, independently of each other.
  3. Perform context transition if a row context is open, turning the iterated row's column values into filters.
  4. Apply the modifiers. REMOVEFILTERS, ALL, ALLEXCEPT and ALLSELECTED run here, after context transition. That ordering is why CALCULATE([Labor Hours], REMOVEFILTERS(FactWorkOrder)) inside an iterator over work orders returns the grand total. The transition put the row filter in, and the modifier took it straight back out.
  5. Apply the filter arguments, replacing existing filters on the same columns unless KEEPFILTERS asked for intersection.
  6. Evaluate the expression in the resulting context.

The last two rows of that table are the only entries that change the wiring of the model instead of the filters running through it, and they get a chapter to themselves. Chapter 12 works both through on Meridian: USERELATIONSHIP counting the same eight work orders as 8 opened, 6 closed and 8 promised through three relationships into one date table, and CROSSFILTER opening the certification bridge to produce 39.0, 10.5, 12.0 and 23.5 hours, which add to 85.0 against a true total of 62.0.

What to remember
  • Filter arguments replace the existing filter on the columns they touch. They do not add to it. That one rule accounts for most CALCULATE results that look wrong.
  • The boolean shorthand compiles into FILTER(ALL(column), condition). The hidden ALL is why replacement happens, so you never have to memorise the behaviour separately.
  • With a slicer on Scheduled, CALCULATE([Labor Hours], DimWOType[WOType]="AOG") returns 14.0 and the same expression wrapped in KEEPFILTERS returns blank. Both are correct answers to different questions.
  • A filter argument that spans two columns replaces the filter on both of them at once. Fleet Pair Hours prints 41.0 into every cell of an aircraft type by operator matrix, including the B737-800 cells that contributed none of those hours. Wrapped in KEEPFILTERS the same argument leaves 23.5 on A320-200 with Cascade Air, 17.5 on E175 with Northwind Regional and blank everywhere else, and those two add back to 41.0.
  • One number repeated across every cell of a matrix is the signature of a filter argument that replaced the axis it was meant to respect. Wrap it in KEEPFILTERS and check the cells again before you look anywhere else.
  • REMOVEFILTERS(DimStation) holds the denominator at 62.0, so MSP is 55.6 percent of the quarter, TUS 36.3 and LAS 8.1. ALLEXCEPT(FactWorkOrder, DimStation[StationCode]) looks like the same instrument and behaves differently. With a February slicer the TUS and MSP work orders read 44.4 and 34.8 percent under it, against 100.0 percent each under REMOVEFILTERS(FactWorkOrder) plus VALUES, because ALLEXCEPT removed the month as well.
  • Prefer REMOVEFILTERS over ALL as a modifier. They behave identically and only one of them says what it means.
  • ALLEXCEPT clears the expanded table, including dimensions you did not list and dimensions that do not exist yet. Audit every use whenever you add a relationship.
  • Modifiers apply after context transition, which is what lets REMOVEFILTERS undo a transition that has already happened inside an iterator.
  • Variables are evaluated where they are declared. A column of identical percentages is the symptom of one captured too early.
  • ALLSELECTED is the one function here whose nested behaviour you should verify against hand calculated numbers before you rely on it.
